<Problem>
On 2026-11-12 at 11:14 UTC, someone checked this lab's Kafka logs with a regular expression filter over 90 minutes of the namespace `kafka`, where crash-looping brokers had been logging a lot. Two minutes later they ran it again. The lab's object store went from about 670 to about 900 MiB of memory, and 50 minutes later it still held about 770. Less than an hour later it was killed for using too much.
</Problem>

Nothing in Loki stopped those two queries. They were allowed to read as much as they wanted, as fast as the queriers could fetch it.

<Idea>
A query costs what it reads, and Loki reports that with every answer: bytes, lines and chunks processed. Compare two queries for the same answer by those numbers, and the cheaper one is the one with the narrower selector and the earlier filters. Limits such as `max_query_bytes_read` stop a query that would read too much, with an error.
</Idea>

## What the story's numbers say

The lab's records of that day show 40 warnings in one minute from the object store, all of the same kind: a reader had closed a stream of `loki-chunks/lab/...` before its end. The queries had been sent through a port-forward that was closed as soon as an answer came, which cut off the reads still running. The object store's memory taken for the burst stayed taken, and further work later that day pushed it over its 1 GiB limit. The fix on the object store's side was a higher limit, recorded in `lgtm/docs/adr/l5b-rustfs-memory.md`. The same record points at Loki as the other place to act.

## Reading the statistics

Every query answer carries statistics. The `summary` gives `totalBytesProcessed`, `totalLinesProcessed`, `execTime` and `queueTime`. The `store` part says how many chunks the index pointed to and how many were downloaded; the `ingester` part says how much came from the ingesters' memory. The query frontend logs the same numbers in its `metrics.go` line, with `splits` and `shards`, as step 8 showed. Explore shows the total as "Total bytes processed" above the logs, and before you run a query it shows an estimate from the index: "This query will process approximately ...". Logs Drilldown shows the total too.

The numbers make the rules of steps 4 and 5 visible. A selector that matches every namespace reads every namespace's lines, even if a filter later throws almost all of them away. A parser before a line filter parses lines that the filter would have dropped. A regular expression costs more per line than a plain filter. And the time range multiplies everything: the 90 minutes of the story were 18 times this step's five.

## The limits that bound a query

All but one are per-tenant limits; `max_concurrent` is a setting of each querier. Each comes with Loki's default and this lab's value:

- `max_query_bytes_read`, default 0 (no limit), 500MB on this lab: the most bytes one query may fetch. It applies to log queries with a filter and to metric queries, with TSDB.
- `max_querier_bytes_read`, default 150GB, 150MB on this lab: the same for each piece after splitting and sharding.
- `tsdb_max_query_parallelism`, default 128, 16 on this lab, and `max_query_parallelism`, default 32, 8 on this lab: how many pieces of one query the frontend schedules at once.
- `max_concurrent`, 4 per querier, the default on this lab too: how many pieces a querier runs at the same time. With two queriers, that is 8 pieces reading chunks from the object store at once.
- `query_timeout`, 1 minute, also on this lab, and `max_query_length`, default 30 days and one hour, 49 hours on this lab: how long a query may run against the backends, and how long its time range may be.

Before it schedules a query, the query frontend asks the TSDB index how many bytes the query's streams hold in its time range. If that is more than `max_query_bytes_read`, Loki answers at once with HTTP status 400 and the message `the query would read too many bytes`, followed by the estimate and the limit, and no querier fetches a chunk. Loki reads `500MB` in its configuration as 500 MiB, so the message says `limit: 500 MiB`. The story's queries ran before this lab had the limit; now a query whose estimate is over 500 MiB fails in milliseconds instead of reading on. Lower parallelism spreads the reads of the queries that do pass over time.

Since 2026-11-14 the lab's Loki runs with query limits: `max_query_bytes_read` 500MB, `max_querier_bytes_read` 150MB, `tsdb_max_query_parallelism` 16, `max_query_parallelism` 8, `max_query_length` 49 hours (`/config` shows `2d1h`) and `query_timeout` 1 minute. `max_concurrent` stays at 4, and the chart sets `split_queries_by_interval` to 15 minutes. On that day, by the index, tenant `lab` held between 110 and 195 MB of log lines per hour across all services, so a filtered or metric query over every service for more than a few hours is refused.
</InLab>

<Trap>
A query that returns a small answer is not a cheap query. The cost is what Loki read to find the answer, so look at the bytes processed, not at the size of the result.
</Trap>

<Remember>
Read the statistics, not the result. Narrow the selector, filter before parsing, keep the time range short, and set max_query_bytes_read so that a runaway query fails with an error.
</Remember>

<Trap practice>
The first query reads every namespace's logs. Keep it at 5 minutes, as written: the same query over hours is the one from the story. Run action 5 only after action 4 shows `max_query_bytes_read: 500MB`: without the limit, Loki would read a whole day of every service's logs. On a lab rebuilt only a few hours ago, the query is small enough to pass.
</Trap>

<Question id="q-m12-s15" answer="b">
Two queries return the same count over one hour. Query A processed 2.4 GB and 9 million lines, query B 90 MB and 300,000 lines. Query A is `sum(count_over_time({namespace=~".+"} | logfmt | app="billing" |= "timeout" [1h]))`. Which change explains most of the difference?

- B uses a regular expression filter, which is faster than a plain filter.

  Plain filters are the fast ones; regular expressions cost more per line.

- B selects `{app="billing"}` and filters before parsing, so it reads and parses little.

  A reads every namespace and parses every line before it filters. B lets the index pick one stream and drops lines with a cheap filter first.

- B was served from the results cache, so its statistics count fewer bytes.

  The two queries have different text, so one cannot reuse the other's cached result, and the gap matches what each selector reads.

- B ran with a shorter `split_queries_by_interval`, so each piece read less.

  Splitting changes how the work is divided among queriers, not the total bytes a query reads.
</Question>
