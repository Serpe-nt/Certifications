<Problem>
A colleague says "Loki is slow" and wants to give it more memory. The lab's Loki is fifteen pods of ten kinds. Which of them is slow, and which would more memory help? You cannot tell until you know what each one does with a line and with a query.
</Problem>

Loki is one program that can play many parts. In this lab, each part runs as its own set of pods.

<Idea>
A write goes through the distributor to three ingesters, which keep recent lines in memory and later write chunks to the object store. A query goes through the query frontend, which splits it into pieces. Queriers run the pieces against the ingesters and the object store, with the index gateway's help. The compactor and the ruler work in the background.
</Idea>

## The write path

A sender pushes lines to the distributor. The distributor checks them: valid labels, timestamps that are not too old or too far ahead, lines that are not too long, and the tenant's limits. It sorts each stream's labels so that the same set always looks the same. Then it hashes the tenant and the label set, looks the hash up in the ingesters' hash ring, and sends the stream to as many ingesters as the replication factor says. With a factor of 3, the write succeeds once two of the three have answered.

Each ingester keeps the stream's newest lines in memory, in a chunk that is still open. It writes them to a write-ahead log on its disk, so a restart does not lose them. When a chunk is full, too old, or has been idle for a while, the ingester compresses it and writes it to the object store, along with index files. The three copies of one chunk usually produce one object, because the object's name is a hash of its content.

<Flow caption="One push">
  <Stage title="Gateway" kicker="nginx">Routes /loki/api/v1/push and /otlp/v1/logs.</Stage>
  <Stage title="Distributor" kicker="2 pods">Validates, applies limits, hashes the stream.</Stage>
  <Stage title="Ingesters" kicker="3 pods">Each stream to all three; two answers are enough.</Stage>
  <Stage title="Object store" kicker="loki-chunks">Chunks and index files, written later.</Stage>
</Flow>

## The read path

A query reaches the query frontend. The frontend splits it by time (every 15 minutes in this lab) and, with the TSDB index, into shards by the amount of data. It puts the pieces in the query scheduler's queue, one queue per tenant, so that one tenant cannot block another. Queriers take pieces from the queue. Each querier asks all ingesters for recent lines and asks the index gateway which chunks in the object store hold the rest. It reads those chunks, runs the pipeline, and removes the duplicates that replication created. The frontend merges the answers, caches the results of metric queries, and logs one line per query with its statistics.

<Flow caption="One query">
  <Stage title="Query frontend" kicker="1 pod">Splits by time and shard, merges, caches.</Stage>
  <Stage title="Scheduler" kicker="1 pod">A fair queue per tenant.</Stage>
  <Stage title="Queriers" kicker="2 pods">Ask ingesters and the index gateway, read chunks.</Stage>
</Flow>

## The background workers

The compactor merges the many small index files the ingesters write into one file per tenant and day. It also applies retention and deletes data on request, as steps 10 and 11 show. It runs as a single instance. The ruler evaluates rules on a schedule, as step 13 shows. Two memcached instances cache chunks and query results. In front of all of them, Loki's own nginx gateway sends each path to the right component.

<Question id="q-m12-s08" answer="b">
In a Loki with three ingesters and a replication factor of 3, one ingester pod restarts. What happens to writes while it is down?

- Writes fail until it is back, because each stream must reach all three of its ingesters.

  The distributor waits for a quorum, not for all three. Two answers out of three are enough.

- Writes go on: each stream still reaches two of its ingesters, which is a quorum of three.

  A write succeeds when half of the ingesters plus one answer. With three, two are enough, so one ingester can be down.

- Writes go on, but they skip the ingesters and go straight to the object store.

  Writes always go through ingesters. They build the chunks that end up in the object store.

- Writes queue up in the distributor and are sent when the ingester returns.

  The distributor is stateless and keeps no queue of writes. It answers the sender as soon as the quorum has answered.
</Question>
