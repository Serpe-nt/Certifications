<Problem>
A service logged customers' card numbers for an hour before someone noticed. The logs are kept for 30 days, and you are asked to remove those lines today, not in a month. The rest of the service's logs must stay.
</Problem>

Loki removes old data on a schedule, and it can remove chosen lines on request. The compactor does both.

<Idea>
Retention removes data older than a period, per tenant or per stream. Deletion removes the lines that match a query in a time window, on request. Both are carried out by the compactor: it first removes chunks from the index, and deletes them from the object store later.
</Idea>

## How retention runs

Retention is off until `retention_enabled` is set on the compactor; without it, logs are kept forever. Once on, the compactor runs two schedules: compaction every 10 minutes by default, and retention on its own interval, which with that default comes to every 15 minutes. On each retention run it works through each day's index table. It finds the chunks older than their retention, removes them from the index, and writes them to a list of marked chunks. A sweeper deletes the marked chunks after `retention_delete_delay`, 2 hours by default. The delay gives the index gateways time to load the new index, so no query asks for a chunk that is gone. It also leaves a short window to stop a deletion caused by a wrong setting. Retention needs the 24-hour index period that TSDB uses, and a store for delete requests.

## How long, and for which streams

The period is a limit in `limits_config`. `retention_period` applies to every stream of a tenant. `retention_stream` sets a period for the streams that match a selector, with a priority to settle overlaps. Both can be set per tenant in the runtime overrides. Loki takes the first that applies: a matching per-tenant stream rule, then a matching global stream rule, then the tenant's period, then the global period. A change of the period is not applied to logs already stored. A stream rule's period must be at least 24 hours.

<Layers caption="Which retention a stream gets, first match wins">
  <Layer title="Per-tenant retention_stream">The matching rule with the highest priority.</Layer>
  <Layer title="Global retention_stream">Only if the tenant has no stream rules of its own.</Layer>
  <Layer title="Per-tenant retention_period">The tenant's own period.</Layer>
  <Layer title="Global retention_period" hot>The default for all tenants; 0 means keep forever.</Layer>
</Layers>

## Deleting chosen lines

A delete request is a POST to the compactor's `/loki/api/v1/delete`, with a stream selector, an optional line filter, and a start and end time. It runs through the same machinery as retention, so `retention_enabled` must be on. The tenant's `deletion_mode` decides what is allowed: `filter-and-delete`, the default, removes the lines from storage; `filter-only` only hides them from queries; `disabled` refuses requests.

A request can be cancelled during `delete_request_cancel_period`, 24 hours by default; only after that does the compactor process it. Once processing has started, cancelling needs `force=true`, and some lines may already be gone. On this lab, the lines stayed visible to queries while the request waited. A request with a line filter is split into pieces of at most a day each. Deleting with a line filter is one of the compactor's heaviest jobs.

<Trap>
Deleting data is not instant, even though the API answers 204 at once. Nothing is removed during the cancellation period. Plan for more than a day: the 24-hour cancellation period, then a compactor run, then the two-hour delete delay.
</Trap>

<Remember>
The compactor applies retention every few minutes and deletes chunks two hours after marking them. A delete request waits 24 hours, in case you cancel it, before it is carried out.
</Remember>

<Question id="q-m12-s11" answer="c">
Loki's global limits set `retention_stream` to 24h for `{namespace="dev"}`. Tenant `shop` has its own overrides: `retention_period: 720h` and a `retention_stream` of 72h for `{container="nginx"}`. How long does tenant `shop` keep the stream `{namespace="dev", container="api"}`?

- 24 hours, because the global rule for `namespace="dev"` matches the stream.

  A global stream rule is only considered when the tenant has no stream rules of its own, and this tenant has one.

- 72 hours, because the tenant's own stream rule takes priority over everything else.

  The tenant's stream rule only applies to streams it matches, and this stream's container is `api`, not `nginx`.

- 720 hours, the tenant's own retention period.

  No tenant stream rule matches, the global stream rules are skipped because the tenant has its own, so the tenant's period applies.

- Forever, because the stream matches none of the rules.

  When no stream rule applies, the tenant's `retention_period` does. Only with no period set at all would logs be kept forever.
</Question>
