<Problem>
An application that exposes no metrics logs one line per request, with the time it took. You want a graph of requests per second by status code, and the 95th percentile of the time, without changing the application.
</Problem>

The numbers are already in the logs. LogQL can compute them when you query.

<Idea>
A metric query wraps a log query in a function over a time window. `count_over_time` and `rate` count lines; `unwrap` takes a field's value instead, for sums, averages and quantiles. Aggregations such as `sum by (...)` then group the results, as in PromQL.
</Idea>

## Count lines in a window

A log query followed by a range in brackets, such as `[5m]`, is a range vector, the same idea as in PromQL. Functions turn it into numbers:

- `count_over_time` counts the lines in the window, `rate` divides that count by the window's seconds;
- `bytes_over_time` and `bytes_rate` do the same with the size of the lines;
- `absent_over_time` returns 1 when the window has no lines, which suits an alert on a source that went quiet.

The window can follow the selector or the end of the pipeline. `offset` shifts it into the past and must come right after the brackets: `count_over_time({job="x"}[5m] offset 1h)`.

## Every label set is a series

A range function returns one series for each distinct set of labels. That includes stream labels, structured metadata and every field a parser extracted. A `| json` on an access log adds a field per key, and some of them, such as a request ID, change on every line. Without care, each line becomes its own series.

Loki stops a metric query that returns more than 500 series, its default `max_query_series`. The error says `maximum number of series (500) reached for a single query`. Two habits avoid it. Aggregate with `sum by (...)` and name only the labels you need. Or remove labels earlier, with `keep`, `drop`, or a parser that extracts only some fields.

## unwrap: numbers from inside the line

To sum or average a value from the line, parse it and then `unwrap` it: `| json | unwrap duration`. The value must be a number. `unwrap duration_seconds(took)` reads a Go duration such as `1.5s`, and `unwrap bytes(size)` reads a size such as `3 MiB`. A line whose value cannot be converted gets `__error__`; drop those with `| __error__=""`.

The functions over unwrapped values include `sum_over_time`, `avg_over_time`, `max_over_time`, `min_over_time` and `quantile_over_time(0.95, ...)`. Most of them accept `by (...)` directly, for example `quantile_over_time(0.95, ... [5m]) by (_authority)`. `sum_over_time`, `rate`, `rate_counter` and `absent_over_time` over unwrapped values do not; wrap them in `sum by (...)` instead.

<InLab>
The beacon writes 171 lines a minute, one per slot of the course, so a 10-minute window holds 1,710 of them. Each line carries a unique `observed_timestamp` as structured metadata, which is why a bare `count_over_time` on the beacon returns one series per line.
</InLab>

<Trap>
A metric query on OTLP logs returns structured metadata as labels too. `count_over_time({service_name="beacon"}[10m])` fails with the 500-series error, although it selects one stream: wrap it in `sum()`.
</Trap>

<Remember>
Count with count_over_time and rate, measure with unwrap, and always decide which labels the result keeps: sum by, keep or drop.
</Remember>

<Question id="q-m12-s07" answer="d">
You run `rate({app="api"} | json [5m])` on a JSON access log and Loki answers `maximum number of series (500) reached for a single query`. The selector matches one stream. What is the best fix?

- Shorten the window from `[5m]` to `[1m]`, so each series holds fewer lines.

  The number of series depends on the distinct label sets, not on the window. A shorter window can still hold hundreds of distinct requests.

- Replace `rate` with `count_over_time`, which returns fewer series.

  Both functions return one series per distinct label set. The count is the same.

- Move `| json` after `[5m]`, so the parser runs only once per window.

  The window may follow the pipeline, but the parser still runs on every line and extracts the same fields.

- Aggregate, such as `sum by (status) (rate({app="api"} | json [5m]))`.

  `| json` made each request's fields labels, so every line became a series. The aggregation keeps only `status`.
</Question>
