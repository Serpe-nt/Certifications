<Problem>
Loki's query-frontend writes a line for every query it serves, and you want the ones that searched text in the last quarter of an hour. Typing `query-frontend` into a search box finds nothing, because Loki does not search the text until you have told it which streams to read.
</Problem>

Every LogQL query is built in the same order: first the streams, then what to keep from their lines.

<Idea>
A query starts with a stream selector in braces, which picks streams by their labels. Line filters come next. Each one searches the text of every line from those streams and keeps or drops it. Filters chain from left to right, and the cheap ones go first.
</Idea>

## The selector picks streams

A selector is one or more label matchers in braces, separated by commas. A stream must match all of them. There are four operators, the same as in PromQL:

- `=` equal, `!=` not equal;
- `=~` matches a regular expression, `!~` does not match it.

The regular expressions in a selector are anchored: they must match the whole label value. `{container=~"query"}` does not match `query-frontend`; `{container=~"query.*"}` does. Loki also refuses a selector that could match every stream, such as `{namespace=~".*"}`. At least one matcher must need a value that cannot be empty, so `{namespace=~".+"}` is accepted.

The more specific the selector, the less Loki reads. Loki's query guide advises starting from the most specific label you have.

## Line filters search the text

After the selector come line filters. They work like grep on each line:

| Filter | Keeps lines that |
|---|---|
| `\|= "text"` | contain the text |
| `!= "text"` | do not contain it |
| `\|~ "regex"` | contain a match of the regular expression |
| `!~ "regex"` | contain no match of it |

Matching is case-sensitive. A regular expression in a line filter is not anchored, and `(?i)` at its start makes it case-insensitive. Filters chain: `|= "error" != "timeout"` keeps lines that contain the first word and not the second.

Inside double quotes, a backslash must be doubled. A string in backticks takes it as written, which makes regular expressions easier to read: `` |~ `status=\d+` ``.

## Order for speed

Loki runs the pipeline on every line the selector lets through, from left to right, and stops on a line as soon as a stage drops it. So the order matters. Line filters are the fastest way to drop a line. Plain contains-filters are faster than regular expressions. Put them before any parser, so that the parser only sees the lines that are left.

<Flow caption="The order of a fast query">
  <Stage title="Selector" kicker="Fewest streams">The most specific labels you know.</Stage>
  <Stage title="|= and !=" kicker="Cheapest">Plain text filters first.</Stage>
  <Stage title="|~ and !~" kicker="Costlier">Regular expressions only when needed.</Stage>
  <Stage title="Parser" kicker="Most work">Runs on the lines that are left.</Stage>
</Flow>

<Question id="q-m12-s04" answer="a">
You want the lines of the `checkout` container that contain `timeout` but not `retrying`. Which query is right and cheapest?

- `{container="checkout"} |= "timeout" != "retrying"`

  The selector picks the stream by label, and two plain filters, the cheapest stage, keep and drop lines by text.

- `{container="checkout"} |~ ".*timeout.*" !~ ".*retrying.*"`

  The result is the same, but regular expressions cost more than plain filters, and line filter regexes need no `.*` because they are not anchored.

- `{container=~"checkout"} != "retrying" |= "Timeout"`

  Line filters are case-sensitive. `Timeout` misses lines that say `timeout`.

- `{container="checkout", line=~".*timeout.*"}`

  `line` is not a label. Text is searched with line filters after the braces, not with a label matcher.
</Question>
