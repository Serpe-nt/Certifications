<Problem>
You parsed Envoy's JSON access log and now want the requests that took 5 milliseconds or more, shown as one short line each: status, method, host and time. Each line has 20 keys, and in Explore the long JSON hides the four values you care about.
</Problem>

Parsing gives you fields. Two more kinds of stage let you choose lines by those fields and show them the way you want.

<Idea>
A label filter compares a label or a parsed field with a typed value: a string, a number, a duration or a size. Format stages then rewrite the result. `line_format` builds a new line from a template, and `label_format`, `keep` and `drop` shape the labels. None of them change what Loki stores.
</Idea>

## Label filters compare typed values

A label filter can sit anywhere in the pipeline, usually right after a parser. Loki infers the type from the value you write:

- a string in quotes, compared with `=`, `!=`, `=~` and `!~`, like a selector;
- a number, such as `response_code >= 500`;
- a duration, such as `duration > 250ms` (units ns, us, ms, s, m, h);
- a size in bytes, such as `total_bytes > 1MB` (units B, kB, KB, KiB, MB, MiB and up).

Numbers, durations and sizes support `==`, `!=`, `>`, `>=`, `<` and `<=`. Predicates chain with `and` and `or`, and a comma, a space or another pipe also means `and`. `and` binds tighter than `or`, as in most languages: `a or b and c` means `a or (b and c)`. The log queries page says the predicates are read from left to right, but Loki 3.7.9 does not do that, as action 4 shows. Write brackets whenever you mix the two. A filter on structured metadata, such as `| slot="log-m12-4"`, is the same kind of stage.

## When the type does not fit

Loki converts the field's value to the type you wrote before it compares. If the conversion fails, the line is not dropped. It is kept, and it gets the label `__error__`. Envoy writes `"duration":5`, a plain number of milliseconds. `| duration > 5s` cannot read `5` as a duration, so every line passes with an error label. The right filter for this field is a number: `| duration >= 5`. Loki's query-frontend writes `duration=4.7ms`, which is a duration, so there `| duration > 5ms` works.

</Compare>

## Formatting changes the result, not the data

`line_format` replaces the text of each line with a Go template. Every label is available by name: `| line_format "{{.response_code}} {{.method}}"`. Templates can use functions such as `printf`, `upper`, `div` and `default`, and `{{ __line__ }}` gives the original line. `label_format` renames a label with `new=old`, or sets one from a template with `new="{{...}}"`. `keep` leaves only the labels you list, and `drop` removes some. Both matter for metric queries in step 7, where each distinct label set becomes its own series.

Line filters after a `line_format` search the new text, not the old one, so put them before it.

<Question id="q-m12-s06" answer="b">
After `| logfmt`, a line has `took=850`, a number of milliseconds. A teammate's query ends with `| logfmt | took > 1s` and still returns this line. Why?

- Loki compares 850 with 1, sees that 850 is larger, and keeps the line.

  Loki does not drop the unit. It tries to read the value as a duration, and that is what fails.

- `850` has no unit, so it cannot be read as a duration; the line is kept with an `__error__` label.

  A failed conversion does not drop a line. Writing `took > 1000`, a number, compares the value correctly.

- Label filters only work on stream labels, and `took` is a parsed field, so the filter is skipped.

  Label filters work on parsed fields and structured metadata as well as on stream labels.

- `1s` is read as the string "1s", and every number is greater than a string in LogQL.

  A value such as `1s` is read as a duration, not a string. Strings are written in quotes.
</Question>
