<Problem>
Step 4's filter `|= "level=error"` kept a line from Loki's ruler that only quoted those words inside a query. You wanted lines whose level is error, not lines that mention it. A text filter cannot tell a field from a quote of it.
</Problem>

To test a field, Loki first has to know where the field is in the line.

<Idea>
A parser reads fields out of each line and adds them as labels for the rest of the pipeline. LogQL has one for each common format: `json`, `logfmt`, `pattern` for a fixed layout, and `regexp` for anything else. After the parser, you filter on a field instead of on text.
</Idea>

## json and logfmt read structured lines

When lines are JSON, `| json` extracts every property. Nested keys are joined with an underscore: `payload.token` becomes `payload_token`. Arrays are skipped. When lines are logfmt, `| logfmt` extracts every `key=value` pair. Both parsers take parameters to extract only some fields, and to rename them: `| json code="response_code", method` or `| logfmt duration, kind="query_type"`. Extracting only what you need is less work for Loki and leaves fewer labels in the result.

Names are cleaned to fit label rules, so characters other than letters, digits and underscores become underscores. Envoy's JSON key `:authority` becomes `_authority`.

## pattern and regexp read everything else

Many lines have a fixed shape without keys, such as an access log. The pattern parser takes a template of the line. Named captures are written in angle brackets, like `<status>`, and `<_>` skips a part. The text between them must match the line exactly. A pattern is anchored at the start of the line, so begin it with `<_>` if the line may start with something else.

The regexp parser takes a Go regular expression with named groups, written `(?P<name>...)`, and extracts each group. It can match anything, but it is harder to write and slower. Loki's docs advise `json` and `logfmt` first, then `pattern`, and `regexp` as the last resort.

<Compare caption="Which parser for which line">
  <Col title="json, logfmt" hot>Lines that carry their own keys. Shortest to write, and they find every field.</Col>
  <Col title="pattern">Lines with a fixed layout and no keys, such as access logs. Faster than regexp.</Col>
  <Col title="regexp">Anything else. Most flexible, slowest, hardest to read.</Col>
</Compare>

## What a parser adds, and what it costs

A parser does not drop lines. A line it cannot parse is kept and gets the label `__error__`, for example `JSONParserErr` for a line that is not JSON. A field whose name is already a label is added with the suffix `_extracted`. And a parser runs on every line that reaches it, so it belongs after the line filters. `{...} |= "metrics.go" | logfmt` parses only the lines that passed the filter; `{...} | logfmt |= "metrics.go"` parses them all first.

<InLab>

</InLab>

<Trap>
A parser does not remove lines it cannot read. If a stream mixes JSON lines and plain lines, `| json` keeps both, and the plain ones carry `__error__`. Add `| __error__=""` after the parser to keep only the lines it could read.
</Trap>

<Remember>
Filter on text first, then parse, then filter on fields. Prefer json and logfmt, use pattern for a fixed layout, and regexp only when nothing else fits.
</Remember>

<Question id="q-m12-s05" answer="c">
A service writes lines such as `level=warn msg="slow call" took=1.2s user=42`. You want only the warnings, and you know the word `warn` also appears in some messages. Which query is right and cheap?

- `{app="api"} |= "warn"`

  This also keeps every line whose message contains the word, which is the problem you want to avoid.

- `{app="api"} | regexp "level=(?P<level>\\w+)" | level="warn"`

  It gives the right answer, but regexp is the slowest parser, and the line is logfmt, which `logfmt` reads directly.

- `{app="api"} |= "level=warn" | logfmt | level="warn"`

  The text filter cheaply drops most lines first, and the parser and the field test then remove the lines that only mention the words.

- `{app="api"} | json | level="warn"`

  The lines are not JSON. Every line gets `__error__`, and none of them gets a `level` field to match.
</Question>
