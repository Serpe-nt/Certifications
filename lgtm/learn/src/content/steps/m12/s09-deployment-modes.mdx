<Problem>
A blog post from 2024 tells you to install Loki with the read, write and backend groups, because that is the easy way to scale. You follow it, and the Loki 4.0 release notes then say that this mode is gone. The install you just finished has to be migrated before its first upgrade.
</Problem>

The components of step 8 can be run in different groupings. Which grouping you choose depends on your log volume, and one of them has no future.

<Idea>
Loki is one binary, and the flag `-target` chooses which components a process runs. Monolithic mode runs them all in one process and suits small volumes. Microservices mode runs each component on its own and suits large ones. Simple scalable mode, the middle ground, is deprecated and is removed in Loki 4.0.
</Idea>

## One binary, many targets

Every Loki component is compiled into the same program. Started with `-target=all`, a process runs every component. Started with `-target=ingester`, it runs only an ingester. Since the data lives in the object store and not in the processes, Loki's docs say you can move an install to another mode with few or no changes to its configuration.

## Monolithic: all in one process

Monolithic mode runs everything in one process. Loki's docs place it at small volumes, up to about 20 GB of logs a day. It can run as several copies that share an object store and a ring, with a replication factor of 3, for high availability. Loki's overview calls this HA monolithic mode and names it the recommended replacement for most simple scalable installs. Its query parallelism is limited by the number of copies.

## Microservices: one component per process

Microservices mode runs each component as its own processes, so each can be scaled alone: more queriers for heavy queries, more ingesters for more streams. It is the most flexible mode and also the most complex to run, and it is built for Kubernetes. Loki's docs recommend it for very large clusters, or when you need precise control over scaling. The Helm chart calls it `Distributed`, and puts it at volumes typically over 1 TB a day.

## What happened to simple scalable

Simple scalable mode grouped the components into three targets: `write` (distributor and ingester), `read` (query frontend and querier) and `backend` (compactor, index gateway, scheduler, ruler). It needed a proxy in front to route each request. Its section in Loki 3.7's docs says it is being deprecated and will be removed with Loki 4.0, and that you cannot run 4.0 in this mode. Installs that use it should move to microservices or to HA monolithic. The chart's values file marks it as deprecated and removed in Loki 4, and its default is now `Monolithic`.

<Remember>
One binary, chosen by -target. Small: monolithic, with copies for high availability. Large: microservices. Simple scalable is on its way out; do not start a new install with it.
</Remember>

<Question id="q-m12-s09" answer="a">
A team ingests about 5 GB of logs a day and wants Loki to survive the loss of one node. They plan a new install today and want it to keep working after Loki 4.0. Which mode fits best?

- Several monolithic copies sharing an object store, replication factor 3.

  At this volume one process can do all the work, and several copies with a replication factor of 3 survive the loss of a node.

- Simple scalable mode with read, write and backend groups.

  It would work today, but it is deprecated and Loki 4.0 removes it, so the install would have to be migrated.

- Microservices mode with every component scaled on its own.

  It would work, but it is the most complex mode to run, and the docs keep it for very large clusters.

- A single monolithic process with a large local disk.

  One process cannot survive the loss of its node, which is what the team asked for.
</Question>
