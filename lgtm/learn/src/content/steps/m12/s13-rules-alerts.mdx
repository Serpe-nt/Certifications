<Problem>
A third-party load balancer exposes no metrics, but it logs every failed health check. You want a page when it logs more than five of them in five minutes. Opening Explore every morning to count them is not monitoring.
</Problem>

Step 7 turned lines into numbers. A rule does the same on a schedule and acts on the result.

<Idea>
Loki's ruler evaluates LogQL metric queries on a schedule, in the same rule format as Prometheus. An alerting rule fires when its expression returns a result, and a recording rule writes its result to a metrics store. Rules are stored per tenant and loaded through the ruler's API.
</Idea>

## Alerting rules in LogQL

A Loki rule file looks like a Prometheus one: groups with a `name` and an `interval`, each holding rules. An alerting rule has an `alert` name, an `expr`, an optional `for`, and `labels` and `annotations`. The only difference is the expression, which is a LogQL metric query, for example `sum(count_over_time({app="lb"} |= "health check failed" [5m])) > 5`. An expression that returns at least one series puts the alert in pending; after `for`, it fires.

Logs suit two kinds of alerts in particular. Event alerts, where one occurrence matters, such as a leaked credential in a line. And alerts on sources too varied to be metrics, such as per-customer errors, because the labels are extracted at query time and never stored as series.

## Recording rules

A recording rule has `record` instead of `alert`: the name of the series to create. The ruler runs the query at each interval and sends the result by remote write to a Prometheus-compatible store such as Mimir, with the rule's tenant in `X-Scope-OrgID`. Loki's query guide suggests recording rules for queries too heavy to run on every dashboard refresh.

## Where rules live and how they are loaded

The ruler keeps rule groups in object storage, per tenant, and checks for changes every minute. You load a group with `POST /loki/api/v1/rules/NAMESPACE`, with the group as YAML; the namespace stands in for a file name. `GET /loki/api/v1/rules` lists the tenant's groups, and `/prometheus/api/v1/rules` and `/prometheus/api/v1/alerts` show their state in the Prometheus format. `DELETE` on the namespace or on a group removes it. The tool `lokitool rules` does the same from a folder of files, and can diff and sync them in a pipeline.

The ruler sends firing alerts to the Alertmanager at `alertmanager_url`. That can be a Prometheus Alertmanager or Grafana's. Grafana calls these rules data-source-managed, as opposed to its own Grafana-managed rules.

<Trap>
A rule whose expression is a log query, such as `{app="lb"} |= "failed"`, is accepted when you load it. It only fails when the ruler runs it: the rule shows `health` `err` with `rule result is not a vector or scalar`, and never fires. Wrap the query in `count_over_time` or `rate` and compare.
</Trap>

<Question id="q-m12-s13" answer="b">
You want a dashboard panel with the rate of 5xx responses from a busy nginx log, and its query takes 20 seconds over 24 hours. What does Loki offer for this?

- An alerting rule with that query, because the ruler caches the result for dashboards.

  An alerting rule only produces alert states, not series a panel can read, and the ruler does not cache results for dashboards.

- A recording rule that writes the result to Mimir every minute for the panel to read.

  The ruler computes the expensive query once per interval and stores the result as a metric, so the panel reads a cheap series.

- A larger `split_queries_by_interval`, so the query frontend runs fewer pieces.

  Fewer, larger pieces run with less parallelism. It does not make an expensive query cheap.

- A label `status` on the nginx stream, so the query reads the index instead of the lines.

  Labels only pick streams. The query would still read and count the lines, and the new label adds streams.
</Question>
