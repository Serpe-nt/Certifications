<Problem>
Your team decides to run Alloy everywhere. The first thing to move is a small Collector pipeline from module m09: a memory limiter, a filter, an attribute that marks the environment, a deleted IP address and a batch. Rewriting it by hand is slow and easy to get wrong, so you reach for the converter. It stops at the third processor.
</Problem>

A converter can only map what exists on both sides. Reading what it says, and checking what it writes, is part of the job.

<Idea>
`alloy convert --source-format=otelcol` reads a Collector file and writes the same pipeline as `otelcol.*` components, joined by `output` blocks. It is a public preview feature and works on a best-effort basis: a Collector component without an Alloy wrapper stops it, and its output can still fail `alloy validate`. Convert, read the report, validate, and fix by hand.
</Idea>

## What converts and what does not

The converter supports the Collector components that Alloy wraps as `otelcol.*`. The `resource` processor is not among them in Alloy 1.21, and a file that uses it fails with a critical error that `--bypass-errors` cannot skip: the file cannot even be read as a Collector configuration Alloy knows. The way out is a component Alloy does have. The `transform` processor can set a resource attribute too, so you swap `resource/env` for `transform/env` before converting.

## How names and defaults come out

Each Collector ID becomes a component label. In this file every label starts with `default`, followed by the part of the ID after the slash, with dashes turned into underscores: `filter/drop-child` becomes `otelcol.processor.filter.default_drop_child`, and `batch` becomes `otelcol.processor.batch.default`. The report lists every one of these mappings. Settings that equal Alloy's defaults are left out, and defaults that differ between the two products are written in. So `error_mode: ignore` disappears, and the batch processor gains `send_batch_size = 8192` and `send_batch_max_size = 0`.

<Flow caption="From Collector file to a running Alloy">
  <Stage title="Convert" kicker="alloy convert">Stops on components Alloy does not have.</Stage>
  <Stage title="Report" kicker="--report">Lists each mapping and each warning.</Stage>
  <Stage title="Validate" kicker="alloy validate">Finds many faults, such as unknown values and stability levels.</Stage>
  <Stage title="Fix by hand" kicker="Then run">Edit, validate again, deploy.</Stage>
</Flow>

## Two faults that validation finds

The converted file still has two faults. `alloy validate` checks syntax, components, names and arguments without running anything, so it catches both, though it cannot catch every fault that would only show at run time. The transform statement was written in the Collector's short form, without a context, and the converter wrote `context = ""`, which Alloy rejects as an unknown context. Give it `context = "resource"` and drop the `resource.` prefix from the path. The `debug` exporter becomes `otelcol.exporter.debug`, which is experimental in Alloy. Alloy runs only generally available components unless `--stability.level` allows lower ones, so `alloy validate` and `alloy run` both refuse it with the default flag.

<InLab>
The lab's Alloys run with `--stability.level=generally-available`, set by the k8s-monitoring chart. An experimental component in their configuration would stop them from loading it.
</InLab>

<Trap>
"A configuration file was generated successfully" means the converter finished, not that Alloy will run the file. Always run `alloy validate` with the same `--stability.level` you will run with.
</Trap>

<Done>
The converter stopped on a processor Alloy does not have, converted the file once you replaced it, and `alloy validate` found the two faults the conversion left. After the fix the file validates.
</Done>

<Trap practice>
Keep the `-` at the end of the convert command and the `<` before the file name. Without them the command waits for input from your terminal.
</Trap>

<Remember>
Convert, read the report, validate with your real stability level, then fix by hand. A Collector component with no `otelcol.*` wrapper has to be replaced before conversion.
</Remember>

<Question id="q-m10-s08" answer="d">
`alloy convert` prints "A configuration file was generated successfully" for a Collector file whose only exporter is `debug`. You start Alloy with its default flags and it refuses the file. Why?

- The converter forgot to add a `service` block with the pipelines

  Alloy has no service block; the converter wires components with output blocks.

- Converted files must be signed before Alloy loads them

  Alloy has no signing step for configuration files.

- The `debug` exporter cannot be converted, so the file is empty

  The converter maps it to `otelcol.exporter.debug`; the file is not empty.

- `otelcol.exporter.debug` is experimental, and Alloy runs only generally available components by default

  The default `--stability.level` is generally-available, so experimental components are refused.
</Question>
