<Problem>
A service is instrumented with an OpenTelemetry SDK and sends OTLP. In module m09 you would put a Collector in front of it. The team you work with runs only Alloy and does not want a second kind of collector in the cluster for traces.
</Problem>

Alloy contains the Collector's own components for OTLP. You connect them the Alloy way, by references, instead of with a `service` section.

<Idea>
Each `otelcol.*` component wraps one Collector component: `otelcol.receiver.otlp` is the OTLP receiver, `otelcol.processor.batch` the batch processor, `otelcol.exporter.otlp` the OTLP exporter over gRPC. Each one sends its data on through an `output` block that lists the `input` export of the next component, one list per signal.
</Idea>

## The same components, wired differently

In the Collector, components are declared in one place and wired in `service.pipelines`, a separate list per signal. In Alloy, the wiring is inside each component. The receiver's `output` block says `traces = [otelcol.processor.batch.default.input]`; the processor's `output` names the exporter's `input`. A receiver that should also pass on metrics adds `metrics = [...]` to the same block. The behaviour of each piece and the meaning of its settings come from the Collector code it wraps, but a few defaults differ. Alloy's `otelcol.processor.batch` sends a batch at 2000 items and caps it at 3000, where the Collector's batch processor uses 8192 and no cap; step 8 meets this again. Alloy 1.21 bundles Collector v0.162.0.

<Compare caption="One traces pipeline, two ways to write it">
  <Col title="Collector (m09)">receivers, processors, exporters declared by ID; wired in service.pipelines.traces.</Col>
  <Col title="Alloy" hot>Each component names the next one's input in its own output block.</Col>
</Compare>

## Three components, three Collector names

`otelcol.receiver.otlp` wraps the Collector's `otlp` receiver. Here it listens for gRPC on `0.0.0.0:4317`, which is also Alloy's default for it. `otelcol.processor.batch` wraps the `batch` processor and groups spans before export. `otelcol.exporter.otlp` wraps the Collector's OTLP exporter for gRPC. Its `client` block holds the endpoint, the headers and the TLS settings.

## Tenant and TLS on the exporter

Tempo reads the tenant from the same `X-Scope-OrgID` header as Loki and Mimir, so the exporter sets it in `headers`. The lab's Tempo distributor listens in plain text, and the exporter's documentation says a server without TLS needs `insecure = true` in the `tls` block. Against a real backend on the internet, you would leave TLS on.

<InLab>
The lab's collector gateway from module m09 does the same job for the shop, with the exporter `otlp_grpc/tempo` and tenant `lab`. Your Alloy sends to the same Tempo distributor, `tempo-distributor.tempo.svc:4317`, as tenant `learn-m10`.
</InLab>

<Trap>
An `output` block with no list for a signal drops that signal: by default the lists are empty and the data is discarded. A receiver whose `output` names only `traces` throws away any metrics or logs it receives.
</Trap>

<Trap practice>
If telemetrygen fails with a connection error, the Service has no ready endpoint: check that the Alloy pod is Running and that the receiver's endpoint is `0.0.0.0:4317`, not `localhost:4317`, which other pods cannot reach.
</Trap>

<Remember>
`otelcol.*` components are Collector components with Alloy wiring: each `output` block names the next `input`, one list per signal, and an empty list drops that signal.
</Remember>

<Question id="q-m10-s07" answer="c">
In an Alloy file, `otelcol.receiver.otlp "in"` has `output { traces = [otelcol.exporter.otlp.tempo.input] }`. An SDK sends it traces and metrics. What happens to the metrics?

- They go to the same exporter, which sends every signal it receives

  Only the traces list names the exporter. The metrics have no list of their own.

- Alloy refuses to load the file until metrics are routed too

  All lists of the output block are optional, so the file loads.

- The receiver drops them, because its metrics list is empty

  Signals with no consumers in the output block are discarded.

- They are kept in memory until a metrics list is added

  Nothing buffers them; data with nowhere to go is dropped.
</Question>
