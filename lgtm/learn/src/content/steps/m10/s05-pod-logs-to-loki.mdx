<Problem>
A team wants the logs of its new service in Loki, but the platform team will not give them a DaemonSet with access to the nodes' `/var/log`. They have one namespace, the right to create pods in it, and the address of Loki. That has to be enough.
</Problem>

It is enough, because Kubernetes already serves every container's log through its API. A small Alloy in the team's namespace can read it from there.

<Idea>
`discovery.kubernetes` finds the pods of a namespace, `discovery.relabel` keeps the containers you want and gives them labels, `loki.source.kubernetes` follows their logs through the Kubernetes API, and `loki.write` pushes the lines to Loki under a tenant. Four components, joined by references, and one Deployment to run them.
</Idea>

## Logs from the API instead of from files

The lab's own collector reads log files on each node, which needs a DaemonSet and a host mount. `loki.source.kubernetes` asks the API server for the log stream of each target, as `kubectl logs -f` does. It needs no privileged container, no root user and no access to the node's file system, and one Alloy can follow pods on any node. The price is more network traffic and more work for the kubelets, so it suits a namespace or a small cluster better than thousands of pods.

The permissions follow from that: the Alloy's service account needs `get`, `list` and `watch` on `pods` to discover them, and `get` on `pods/log` to read them. A Role in your namespace grants exactly that, and nothing outside it.

## Choosing what to follow, and how to label it

`discovery.kubernetes` with `role = "pod"` makes one target per declared container port, and one target for a container without ports. The `namespaces` block limits it to `learn-m10`, which also keeps the Role enough. `discovery.relabel` then keeps only the `podinfo` container and copies three of the `__meta_kubernetes_*` labels to the names `namespace`, `pod` and `container`. Labels that start with two underscores are dropped before the lines are sent.

<Flow caption="Your practice log pipeline">
  <Stage title="discovery.kubernetes" kicker="Finds">Pods in learn-m10.</Stage>
  <Stage title="discovery.relabel" kicker="Keeps, labels">Only the podinfo container; namespace, pod, container.</Stage>
  <Stage title="loki.source.kubernetes" kicker="Tails">Each container's log through the API.</Stage>
  <Stage title="loki.write" kicker="Pushes">To Loki as tenant learn-m10.</Stage>
</Flow>

## A tenant of your own

The lab's Loki is multi-tenant: the header `X-Scope-OrgID` decides whose data a line is, and `loki.write` sets it from `tenant_id`. The lab's Alloy writes as `lab`, the tenant the shop and the cluster logs share. Practice data goes into a tenant of its own, `learn-m10`: it cannot mix with the lab's data, and deleting your work later touches nothing else. A tenant exists as soon as the first line arrives with its name. The price is that Grafana's `loki` data source reads only `lab`, so you query your tenant through Loki's API with the header.

`external_labels` adds `cluster="lgtm-lab"` to every line, as the lab's own writer does.

<InLab>
The practice app is podinfo 6.17.0, the small Go web app of module m01, started with `--level=debug` so that it writes one JSON line per request. A second container calls it every five seconds. The practice Alloy runs the image the lab pins, `grafana/alloy:v1.21.3`.
</InLab>

<Trap>
`loki.write` with no `tenant_id` sends no `X-Scope-OrgID` header at all, because it assumes a single-tenant Loki. The lab's multi-tenant Loki refuses such pushes; set the tenant every time.
</Trap>

3. Save the Alloy's configuration as `m10-config.yaml`. Steps 6, 7 and 9 replace this file with a longer one:

   ```yaml
   apiVersion: v1
   kind: ConfigMap
   metadata:
     name: m10-alloy
     namespace: learn-m10
   data:
     config.alloy: |
       livedebugging {
         enabled = true
       }

       discovery.kubernetes "pods" {
         role = "pod"
         namespaces {
           names = ["learn-m10"]
         }
       }

       discovery.relabel "app_logs" {
         targets = discovery.kubernetes.pods.targets

         rule {
           source_labels = ["__meta_kubernetes_pod_container_name"]
           regex         = "podinfo"
           action        = "keep"
         }
         rule {
           source_labels = ["__meta_kubernetes_namespace"]
           target_label  = "namespace"
         }
         rule {
           source_labels = ["__meta_kubernetes_pod_name"]
           target_label  = "pod"
         }
         rule {
           source_labels = ["__meta_kubernetes_pod_container_name"]
           target_label  = "container"
         }
       }

       loki.source.kubernetes "app" {
         targets    = discovery.relabel.app_logs.output
         forward_to = [loki.write.practice.receiver]
       }

       loki.write "practice" {
         endpoint {
           url       = "http://loki-gateway.loki.svc/loki/api/v1/push"
           tenant_id = "learn-m10"
         }
         external_labels = {
           cluster = "lgtm-lab",
         }
       }
   ```

<Remember>
Discovery finds targets, relabeling chooses and names them, a source reads them, a writer sends them. The tenant is part of the writer.
</Remember>

<Question id="q-m10-s05" answer="b">
A team may not run DaemonSets or mount host paths. Which component lets their Alloy, a single Deployment, collect their pods' logs?

- `loki.source.file`

  It reads files on the node where Alloy runs, which needs a host mount and one Alloy per node.

- `loki.source.kubernetes`

  It follows container logs through the Kubernetes API, with no host access, from any node.

- `local.file_match`

  It only turns path globs into file targets. It reads no log lines.

- `loki.source.kubernetes_events`

  It collects Kubernetes events from the API server, not the logs of containers.
</Question>
