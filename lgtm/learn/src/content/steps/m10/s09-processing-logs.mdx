<Problem>
Your podinfo logs reach Loki, but every line is one JSON string. To see only errors you would have to parse each line at query time. A third of the lines are readiness probes nobody reads. And the pod name, which changes with every rollout, sits in the stream's labels.
</Problem>

All three are fixed before the line leaves Alloy, in one component placed between the source and the writer.

<Idea>
`loki.process` runs stages on each line, in the order you write them. Parsing stages copy fields of the line into an extracted map; later stages read that map to set labels, attach structured metadata or drop the line. You watch the effect line by line with live debugging.
</Idea>

## Stages and the extracted map

Each stage sees the line, its labels, its timestamp and a shared map of extracted values. `stage.json` parses the line as JSON and copies the fields you name into the map: `level = ""` means "take the field `level`", because an empty expression reuses the key's name. The line itself is not changed. Other parsers fill the same map: `stage.logfmt` for `key=value` lines, `stage.regex` for anything else, `stage.cri` for the container runtime's own format, which the lab's file collector uses.

## Label or structured metadata

`stage.labels` turns values of the map into labels of the stream. `stage.structured_metadata` attaches them to each line instead, as structured metadata, which Loki stores with the line without indexing it. If the key you list is already a label, the stage moves it: it leaves the label set and becomes structured metadata. That is how the lab's collector keeps `pod` out of its stream labels.

<Compare caption="Where the practice pipeline puts each field">
  <Col title="Label">level: a few fixed values, used to choose streams.</Col>
  <Col title="Structured metadata" hot>uri and pod: many values, kept with each line.</Col>
  <Col title="Dropped">Lines whose uri is /healthz or /readyz.</Col>
</Compare>

Module m12 explains why a label with many values is expensive in Loki. Here the point is the mechanics: a value with a small, fixed set of values can be a label, and anything that changes per request or per pod belongs in structured metadata.

## Dropping lines before they cost anything

`stage.drop` discards a line when its conditions match. With `source = "uri"` and an `expression`, it tests the extracted value, not the whole line. Several conditions in one `stage.drop` must all match; for "this or that", write several `stage.drop` blocks. Each dropped line raises the counter `loki_process_dropped_lines_total`, labelled with the `drop_counter_reason` you choose. Your Alloy scrapes its own metrics since step 6, so that counter is already in your Mimir tenant.

<InLab>
The lab's `loki.process "pod_logs"` runs `stage.cri` inside a `stage.match`, makes `flags` and `stream` labels, drops the label `filename` with `stage.label_drop`, and lists `k8s_pod_name`, `pod` and `service_instance_id` in `stage.structured_metadata`, so `pod` and `service_instance_id` leave the label set.
</InLab>

<Trap>
Order matters. A `stage.labels` or `stage.drop` that reads `level` must come after the `stage.json` that extracts it. Placed before, it finds nothing in the map and quietly does nothing.
</Trap>

<Question id="q-m10-s09" answer="b">
A `loki.process` has `stage.labels { values = { level = "" } }` first and `stage.json { expressions = { level = "" } }` after it. Lines arrive in Loki without a `level` label. Why?

- `stage.labels` can only read structured metadata, not JSON

  It reads the extracted map by default; it simply runs before anything was extracted.

- Stages run in order, so the labels stage ran before `level` was extracted

  When `stage.labels` runs, the map has no `level` yet, so it sets nothing.

- An empty string in `expressions` means "extract nothing"

  An empty expression reuses the key as the field name, so `level` is extracted.

- Loki removes any label named `level` and keeps it as detected_level

  Loki accepts a `level` label; the problem is in the order of the stages.
</Question>
