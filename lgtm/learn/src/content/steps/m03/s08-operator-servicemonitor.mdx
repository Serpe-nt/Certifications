<Problem>
Your team deploys a new service with Helm. In the old setup, someone then opened a ticket so that the monitoring team would add a scrape job and its relabel rules to `prometheus.yml`. With twenty teams, that file became a queue. You want the scrape setup to ship with the service, in the same chart.
</Problem>

<Idea>
The Prometheus Operator runs Prometheus in Kubernetes and writes its configuration for you. You describe what to scrape with Kubernetes objects, such as a ServiceMonitor that selects Services by label, and the operator turns them into scrape jobs with the discovery and relabeling of steps 6 and 7.
</Idea>

## Two kinds of custom resources

The operator adds custom resources to the Kubernetes API. Some describe a running component: a `Prometheus` resource becomes a StatefulSet that runs Prometheus, an `Alertmanager` resource one that runs Alertmanager, and a `PrometheusAgent` resource runs Prometheus in agent mode (step 13). Others describe configuration:

- `ServiceMonitor`: scrape the pods behind Services that match a label selector.
- `PodMonitor`: scrape pods that match a label selector directly, without a Service.
- `Probe`: probe ingresses or static targets through a prober, usually the blackbox exporter.
- `ScrapeConfig`: anything the three above cannot express, such as targets outside the cluster.
- `PrometheusRule`: recording and alerting rules. The operator loads them without restarting Prometheus.

## How a ServiceMonitor finds pods

A ServiceMonitor does not point at pods. It selects Services by their labels, and it names a port of that Service by its name. Kubernetes already keeps the list of pod addresses behind each Service, and Prometheus discovers those addresses. So one ServiceMonitor follows a Service through every scale-up and rollout.

The `Prometheus` resource decides which ServiceMonitors it uses, with two fields: `serviceMonitorSelector` for their labels and `serviceMonitorNamespaceSelector` for their namespaces. An empty selector, `{}`, matches every object. A selector that is left out matches none, and a namespace selector that is left out means the Prometheus resource's own namespace only.

<Flow caption="From a ServiceMonitor to a target">
  <Stage title="ServiceMonitor" kicker="You write">Select Services by label, name a port.</Stage>
  <Stage title="Operator" kicker="Generates">A scrape job with discovery and relabel rules.</Stage>
  <Stage title="Prometheus" kicker="Reloads">Discovers the endpoints behind the Service.</Stage>
  <Stage title="Target" kicker="Scraped">One per pod address, with namespace, pod and job labels.</Stage>
</Flow>

## What the operator writes

For each endpoint of each ServiceMonitor, the operator adds one scrape job named `serviceMonitor/<namespace>/<name>/<index>`. The job keeps only the Services that match the selector and the port with the given name, and it copies the namespace, the Service, the pod and the container into labels. Unless the ServiceMonitor sets `jobLabel`, the `job` label gets the Service's name. The whole configuration lives in a Secret named after the Prometheus resource with the prefix `prometheus-`, and Prometheus loads each new version without a restart.

A PodMonitor works the same way with the pod's labels and the pod's port names. Use it when there is no Service to select.

<InLab>

</InLab>

</Trap>

<Trap practice>
The ServiceMonitor names the Service port by its name, `web`. Writing `port: "8080"` does not match it. If the target does not appear after two minutes, check that the Service has the label `app: example-app` and a port named `web`: <Cmd>kubectl -n learn-m03 get service example-app --show-labels</Cmd>

<Remember>
A ServiceMonitor selects Services by label and a port by name; the operator turns it into a scrape job named `serviceMonitor/<namespace>/<name>/<index>`. Whether Prometheus uses it depends on the selectors of the Prometheus resource.
</Remember>

<Question id="q-m03-s08" answer="d">
A batch of worker pods serves `/metrics` on a named port, but no Service selects them because nothing calls them. How do you have the Prometheus Operator scrape them?

- Create a Service only so that a ServiceMonitor can select it

  That works, but it adds an object nobody needs. The operator has a resource made for pods without a Service.

- Add the pods' addresses to a Probe

  A Probe sends targets to a prober, such as the blackbox exporter. It does not scrape the pods' own metrics.

- Add a recording rule in a PrometheusRule

  A PrometheusRule holds rules that run on stored data. It does not create scrape targets.

- Write a PodMonitor that selects the pods by label

  A PodMonitor selects pods directly and needs no Service in front of them.
</Question>
