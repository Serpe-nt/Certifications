<Problem>
The team wants a year of metrics from five clusters in one place, with a copy that survives the loss of a node. Each cluster's Prometheus keeps a day on one disk. Making that disk bigger does not give you a second copy, and it does not put five clusters into one query.
</Problem>

<Idea>
Remote write lets Prometheus send every sample it ingests to another system over HTTP. The local server keeps scraping and alerting as before, and a store built for scale and long retention, such as Mimir, holds the long history. The sender reads from the WAL, so a short outage of the receiver loses nothing.
</Idea>

## Four ways to work with remote storage

Prometheus can write the samples it ingests to a remote URL, and it can receive such writes from others when the flag `--web.enable-remote-write-receiver` is set. It can also read raw samples back from a remote system, and serve its own data to remote readers. Remote read is limited: Prometheus fetches the raw series and still runs every PromQL query itself.

The write protocol sends protocol buffers compressed with snappy over HTTP. Version 1.0 of its specification is stable and version 2.0 is experimental; Prometheus supports both, and the setting `protobuf_message` chooses between them.

## A remote_write section

A remote write destination is a list entry in the configuration:

```yaml
remote_write:
  - name: mimir
    url: http://mimir-gateway.mimir.svc/api/v1/push
    headers:
      X-Scope-OrgID: prom
    send_exemplars: true
    send_native_histograms: true
    write_relabel_configs:
      - source_labels: [__name__]
        regex: go_.*
        action: drop
```

`url` is where samples go, and `headers` adds HTTP headers, here the tenant that Mimir expects (module m11). `write_relabel_configs` are relabel rules of step 7 applied just before sending; the example drops every metric that starts with `go_` from what is sent, while the local copy keeps them. External labels from `global` are added before these rules run.

## How samples travel, and what an outage costs

Each destination gets its own queue. It reads samples from the WAL, spreads them over shards, and each shard sends batches to the endpoint. Prometheus adjusts the number of shards to keep up with the incoming rate, between `min_shards` and `max_shards`.

When the endpoint fails, Prometheus retries without losing data, as long as the outage is shorter than about two hours. After that the WAL is compacted and samples that were not sent are lost. Remote write also costs memory: most users see about 25% more. The metric `prometheus_remote_storage_samples_pending` shows how many samples wait to be sent.

<Flow caption="From the WAL to a remote store">
  <Stage title="WAL" kicker="Source">Every ingested sample is written here first.</Stage>
  <Stage title="Queue" kicker="Per destination">Samples are spread over shards.</Stage>
  <Stage title="Shards" kicker="Send">Batches go out over HTTP and are retried on failure.</Stage>
  <Stage title="Remote store" kicker="Mimir">Keeps the long history for many servers.</Stage>
</Flow>

## Agent mode: only scrape and send

When a server should only forward data, run it with `--agent`. Agent mode keeps scraping, service discovery and remote write, and replaces the database with a WAL that is emptied after each successful send. It uses far fewer resources, but you cannot query it, it evaluates no recording rules, and it sends no alerts: all of that happens in the remote system. Its screen still shows the configuration, the targets and service discovery.

<Compare caption="Full server or agent">
  <Col title="Server with remote write">Scrapes, stores locally, queries, rules and alerts, and also sends everything to the remote store.</Col>
  <Col title="Agent mode">Scrapes and sends only. No local queries, rules or alerts; a small WAL buffer in place of the database.</Col>
</Compare>

<Trap>
Remote write does not make the local server smaller. Prometheus still stores, queries and alerts on its own data; remote write adds memory and network on top. Only agent mode drops the local database.
</Trap>

<Remember>
Remote write streams every sample from the WAL to a remote store, retrying through outages of up to about two hours. Write relabeling chooses what is sent, and agent mode keeps only scraping and sending.
</Remember>
