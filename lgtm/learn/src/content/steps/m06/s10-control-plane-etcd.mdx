<Problem>
A colleague opens "Kubernetes / Scheduler" in a fresh kube-prometheus-stack setup on a kubeadm cluster and finds every panel empty. On another cluster, alerts say `KubeSchedulerDown` and `KubeControllerManagerDown` from the first minute, while `kubectl get pods -n kube-system` shows both running. Nothing is wrong with the scheduler. Something is wrong with how it is reached.
</Problem>

Every control plane component serves `/metrics`. Whether Prometheus can reach it is a choice made when the cluster was built.

<Idea>
kubeadm runs the API server, the scheduler, the controller manager and etcd as static pods on the control plane nodes. The API server listens on the node's address, so Prometheus scrapes it. The scheduler, the controller manager and kube-proxy serve their metrics only on loopback, and etcd serves them on loopback without a certificate or on its client port with one. A Prometheus pod cannot reach them as they are. You either open them in the cluster's configuration or leave them out on purpose, as this lab does.
</Idea>

## Who listens where

<Compare caption="Control plane metrics on this kubeadm cluster">
  <Col title="Reachable" hot>kube-apiserver: port 6443 on each master's address, scraped as job apiserver.</Col>
  <Col title="Loopback only">kube-scheduler (port 10259) and kube-controller-manager (10257) with --bind-address=127.0.0.1; etcd metrics on http://127.0.0.1:2381 (or on port 2379 with a client certificate); kube-proxy on 127.0.0.1:10249 by default.</Col>
</Compare>

The kube-prometheus-stack chart has a ServiceMonitor ready for each of these four components. With their `enabled` switch on and the components on loopback, the targets show down, and the stack's alerts such as `KubeSchedulerDown` fire. With the switches off, as in this lab, the jobs and their alert rules do not exist at all, so nothing tells you the scheduler is unwatched.

## Seeing the control plane through the API server

You still see a great deal through the API server, because every other component talks to it. `apiserver_request_total` counts its requests by verb, resource and response code, so a rise in `5xx` codes shows trouble for every client at once. `etcd_request_duration_seconds` is the API server's own measure of how long etcd takes to answer, per operation. It does not replace etcd's metrics: etcd's `etcd_server_has_leader` and `etcd_disk_wal_fsync_duration_seconds` say whether the store has a leader and whether its disk is fast enough, and only etcd knows them.

## What would open them

On a kubeadm cluster, the flags of the control plane components come from the `ClusterConfiguration`. Its `extraArgs` for `scheduler` and `controllerManager` can set `bind-address` to the node's address or `0.0.0.0`, and the `etcd` section can set `listen-metrics-urls` to a reachable address. kube-proxy's `metricsBindAddress` in its own configuration does the same for kube-proxy. After that change, turn on `kubeScheduler`, `kubeControllerManager`, `kubeEtcd` and `kubeProxy` in the chart's values. An open metrics port can be reached by more than Prometheus, so decide who else may connect to the masters before you open it.

<InLab>
The lab's values file leaves the four switches off and says why: kubeadm binds them to localhost. Prometheus scrapes three API server targets, one per master, and nothing from the scheduler, the controller manager, etcd or kube-proxy. A later module opens them.
</InLab>

<Trap>
`KubeSchedulerDown` on a kubeadm cluster with the switch on usually means "Prometheus cannot reach it", not "the scheduler is down". Check `--bind-address` before you restart anything.
</Trap>

<Done>
You found the loopback flags of three control plane components, and the API server metrics that still tell you how the control plane is doing.
</Done>

<Trap practice>
`grep -- --bind-address` needs the `--` before the pattern; without it, grep reads `--bind-address` as one of its own options and stops with an error about an unknown option.
</Trap>

<Remember>
On kubeadm only the API server is reachable by default. The scheduler, the controller manager, kube-proxy and etcd's plain metrics port listen on loopback until the cluster's configuration opens them.
</Remember>

<Question id="q-m06-s10" answer="c">
On a kubeadm cluster, `up{job="kube-scheduler"}` is 0 on all three masters, while the scheduler pods are Running and new pods get scheduled. What is the most likely cause?

- The scheduler has crashed and its static pods only look Running

  New pods still get scheduled, so the scheduler works.

- Prometheus lacks the RBAC permission to read the scheduler's metrics

  A missing permission gives an HTTP 403 from a reachable port; the cause comes first here.

- The scheduler listens on 127.0.0.1, out of Prometheus's reach

  kubeadm sets --bind-address=127.0.0.1, so a scrape from another pod cannot connect.

- The scheduler serves no metrics on kubeadm clusters

  Every control plane component serves /metrics; the question is only where it listens.
</Question>
