<Problem>
A team installs kube-prometheus-stack on a fresh kubeadm cluster with every switch on. Ten minutes later `TargetDown` fires for the jobs `kube-scheduler` and `kube-controller-manager`, and the scheduler's dashboard is empty. Yet `kubectl get pods -n kube-system` shows both running, and new pods get scheduled. Nothing is wrong with the scheduler; something is wrong with how it is reached.
</Problem>

Every control plane component serves `/metrics`. Whether Prometheus can reach it is a choice made when the cluster was built.

<Idea>
kubeadm runs the API server, the scheduler, the controller manager and etcd as static pods on the control plane nodes. The API server listens on the node's address, so Prometheus scrapes it. The scheduler, the controller manager and kube-proxy serve their metrics only on loopback, and so does etcd's plain metrics port. etcd's client port listens on the node's address too, but only for callers with a client certificate signed by etcd's CA. So, as kubeadm leaves them, a Prometheus pod can scrape only the API server. You either open them in the cluster's configuration or leave them out on purpose, as this lab does.
</Idea>

## Who listens where

<Compare caption="Control plane metrics on this kubeadm cluster">
  <Col title="Reachable" hot>kube-apiserver: port 6443 on each master's address, scraped as job apiserver.</Col>
  <Col title="Loopback only">kube-scheduler (port 10259) and kube-controller-manager (10257) with --bind-address=127.0.0.1; etcd's plain metrics port, http://127.0.0.1:2381; kube-proxy on 127.0.0.1:10249 by default.</Col>
  <Col title="Certificate needed">etcd's client port 2379 on each master's address, which also serves /metrics, to a caller with a client certificate signed by etcd's CA.</Col>
</Compare>

## Down or missing: two different alerts

The kube-prometheus-stack chart has a ServiceMonitor ready for each of these four components. With their `enabled` switch on, Prometheus discovers the targets on the masters' addresses but cannot connect, so their `up` is 0. Two kinds of alert react to that: `TargetDown`, when more than 10% of a job's targets are down for 10 minutes, and `KubeSchedulerInstanceUnreachable` (and its controller manager twin), when `up` is 0 for 15 minutes.

`KubeSchedulerDown` does not fire then. Its expression is `absent(up{job="kube-scheduler"})`: it fires when Prometheus has found no scheduler target at all for 15 minutes, for example because the Service that the ServiceMonitor selects matches no pod. A target that exists and fails has `up` at 0, and 0 is not absent. So `...Down` means "nothing to scrape", while `TargetDown` and `...InstanceUnreachable` mean "something to scrape that does not answer".

With the switches off, as in this lab, the jobs and their alert rules do not exist at all, so nothing tells you the scheduler is unwatched.

## Seeing the control plane through the API server

You still see a great deal through the API server, because every other component talks to it. `apiserver_request_total` counts its requests by verb, resource and response code, so a rise in `5xx` codes shows trouble for every client at once. `etcd_request_duration_seconds` is the API server's own measure of how long etcd takes to answer, per operation. It does not replace etcd's metrics: etcd's `etcd_server_has_leader` and `etcd_disk_wal_fsync_duration_seconds` say whether the store has a leader and whether its disk is fast enough, and only etcd knows them.

## What would open them

On a kubeadm cluster, the flags of the control plane components come from the `ClusterConfiguration`. Its `extraArgs` for `scheduler` and `controllerManager` can set `bind-address` to the node's address or `0.0.0.0`, and the `etcd` section can set `listen-metrics-urls` to a reachable address; for etcd the other way is to give Prometheus a client certificate signed by etcd's CA and scrape port 2379. kube-proxy's `metricsBindAddress` in its own configuration does the same for kube-proxy. After that change, turn on `kubeScheduler`, `kubeControllerManager`, `kubeEtcd` and `kubeProxy` in the chart's values. An open metrics port can be reached by more than Prometheus, so decide who else may connect to the masters before you open it.

</InLab>

<Trap>
Read an alert's expression before you act on its name. On a kubeadm cluster with the switch on, `TargetDown` and `KubeSchedulerInstanceUnreachable` mean "Prometheus cannot connect", not "the scheduler is down": check `--bind-address` before you restart anything. `KubeSchedulerDown` means something else: Prometheus found no target to try.
</Trap>

<Trap practice>
`grep -- --bind-address` needs the `--` before the pattern; without it, grep reads `--bind-address` as one of its own options and stops with an error about an unknown option.

<Remember>
On kubeadm only the API server is reachable without changes. The scheduler, the controller manager, kube-proxy and etcd's plain metrics port listen on loopback, and etcd's client port asks for a certificate. A target that does not answer has `up` 0; `absent(up)` means there is no target.
</Remember>

<Question id="q-m06-s10" answer="c">
On a kubeadm cluster, `up{job="kube-scheduler"}` is 0 on all three masters, while the scheduler pods are Running and new pods get scheduled. What is the most likely cause?

- The scheduler has crashed and its static pods only look Running

  New pods still get scheduled, so the scheduler works.

- Prometheus lacks the RBAC permission to read the scheduler's metrics

  A missing permission gives an HTTP 403 from a reachable port; the cause comes first here.

- The scheduler listens on 127.0.0.1, out of Prometheus's reach

  kubeadm sets --bind-address=127.0.0.1, so a scrape from another pod cannot connect.

- The scheduler serves no metrics on kubeadm clusters

  Every control plane component serves /metrics; the question is only where it listens.
</Question>
