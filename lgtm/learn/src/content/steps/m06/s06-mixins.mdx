<Problem>
At 02:00 the pager says `KubeCPUOvercommit`. Nobody on the team wrote that alert, and its expression is eight lines of PromQL around a series named `namespace_cpu:kube_pod_container_resource_requests:sum`. Before you can decide whether to wake someone, you need to know what it measures.
</Problem>

The stack came with more than a hundred alerts and two dozen dashboards. They were written once, upstream, for every cluster.

<Idea>
A mixin is a package of dashboards, recording rules and alerts for one system, kept in its own repository and written in jsonnet. kube-prometheus-stack ships the rules and dashboards of the Kubernetes and node mixins as PrometheusRule objects and ConfigMaps. Each alert reads recording rules, and each recording rule reads raw metrics, so you can always trace an alert back to the component that reported it.
</Idea>

## Where they come from

The kubernetes-mixin is a set of Grafana dashboards and Prometheus alerts for Kubernetes; the node mixin does the same for node exporter. Both are written in jsonnet and installed with jsonnet-bundler, so a team can change the job selectors or the dashboard names before it builds them. Building one gives you files of alerts and recording rules for Prometheus and a folder of dashboards for Grafana.

The kube-prometheus-stack README says that its dashboards and rules are copies: scripts in the chart's `hack/` folder fetch them from kube-prometheus and the mixins, and a change to them belongs in the original repository. For your own cluster, the chart's values give you a way around that: `defaultRules.disabled` switches off a single alert by name, and `additionalPrometheusRulesMap` adds rules of your own, such as your version of that alert. A hand edit to the copy in the cluster is in no values file, so the next install of the chart does not have it.

## From alert to raw metric

Recording rules follow a naming scheme, `level:metric:operations`. The level says which labels are kept, the metric is the name it came from, and the operations say what was done to it, newest first. So `namespace_cpu:kube_pod_container_resource_requests:sum` is the sum of `kube_pod_container_resource_requests` for CPU, kept per namespace.

<Flow caption="Tracing KubeCPUOvercommit back to its source">
  <Stage title="Alert" kicker="kubernetes-resources">KubeCPUOvercommit: CPU requests above what the cluster can lose a node and still give.</Stage>
  <Stage title="Recording rule" kicker="k8s.rules.container_resource">namespace_cpu:kube_pod_container_resource_requests:sum, every 30 seconds.</Stage>
  <Stage title="Raw metrics" kicker="kube-state-metrics">kube_pod_container_resource_requests and kube_pod_status_phase.</Stage>
</Flow>

The alert compares the summed requests with `kube_node_status_allocatable` minus the largest node. It fires when the pods could not all be placed again if one node were lost. Every stack alert carries a `runbook_url` that explains this and what to check first. The dashboards use the same recording rules: the "Kubernetes / Compute Resources" dashboards read `node_namespace_pod_container:container_cpu_usage_seconds_total:sum_rate5m`, a recording rule over the cAdvisor CPU counter.

<InLab>
The lab's release brought 30 PrometheusRule objects with 134 alerting and 86 recording rules, and 25 dashboard ConfigMaps that the lab's Grafana shows in the folder Kubernetes, among them "Kubernetes / Compute Resources / Namespace (Pods)" and "Node Exporter / USE Method / Node".
</InLab>

<Trap>
An alert that reads a recording rule depends on the rule's group running. If you drop the recording rules to save series, the dashboards go blank and the alerts that read them never fire, without any error.
</Trap>

<Do>
1. Open <LabLink to="prometheus" path="/alerts">the Alerts page</LabLink> and type `KubeCPUOvercommit` in the search box. Open the rule. Read its expression, its `for: 10m`, its `severity="warning"` label and its `runbook_url`.
2. In the expression, find the series name with colons in it. That is a recording rule.
3. Open <LabLink to="prometheus" path="/rules">Rule health</LabLink> (under Status) and search for `namespace_cpu`. Open `namespace_cpu:kube_pod_container_resource_requests:sum` in the group `k8s.rules.container_resource`, and read which metrics its expression uses.
4. On <LabLink to="prometheus" path="/query">the query page</LabLink>, check that the rule gives the same number as the raw metric for one namespace: <Query lang="promql">{`namespace_cpu:kube_pod_container_resource_requests:sum{namespace="shop"}`}</Query> <Query lang="promql">{`sum(kube_pod_container_resource_requests{namespace="shop", resource="cpu"})`}</Query>
5. In <LabLink to="grafana" path="/dashboards">Grafana's dashboards</LabLink>, open the folder Kubernetes and the dashboard "Kubernetes / Compute Resources / Namespace (Pods)" for `shop`. Open the menu of the CPU usage panel, choose Edit, and find the recording rule in its query.

</Do>

<Done>
You followed one alert to a recording rule and that rule to the kube-state-metrics series it sums, and both queries in action 4 gave the same number.
</Done>

<Trap practice>
The two queries in action 4 can differ for a few seconds after a pod starts or stops, because the recording rule runs every 30 seconds. Run them again; they settle on the same value.
</Trap>

<Remember>
The stack's alerts and dashboards come from mixins. Follow the colons: alert to recording rule to raw metric, and you know which component to look at.
</Remember>

<Question id="q-m06-s06" answer="a">
Your team wants `KubePodNotReady` to wait 5 minutes instead of 15, in every cluster that installs kube-prometheus-stack from your values file. What do you change?

- Disable the alert in `defaultRules.disabled` and add your version in `additionalPrometheusRulesMap`

  Both are chart values, so every install from the file gets the change, and the chart's copy no longer fires.

- Run `kubectl edit` on the PrometheusRule `prom-kubernetes-apps` in each cluster

  The edit lives only in that cluster's object; nothing in the values file carries it to the next install.

- Edit the rule file that the operator writes into the Prometheus pod

  The operator generates that file from the PrometheusRule objects and writes it again from them.

- Add a route in Alertmanager that waits 10 minutes before it sends the alert

  Alertmanager can only delay a notification. It cannot make the rule fire before its 15 minutes.
</Question>
