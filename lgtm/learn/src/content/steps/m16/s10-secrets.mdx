<Problem>
A developer commits a Terraform file with a Grafana token pasted into the provider block, to "fix it later". The repository is mirrored to a second server, and every clone now holds an admin key to production Grafana. Deleting the line in the next commit does not help: Git keeps every earlier version.
</Problem>

<Idea>
Files in Git say what to build and where its secrets are; they never hold the secrets. A secret lives in a store made for it, such as a Kubernetes Secret, and the configuration refers to it by name. If a secret ever reaches Git, it is burnt: rotate it, because removing it from the history does not remove it from the clones.
</Idea>

## What counts as a secret here

In an observability repository the usual secrets are API tokens (Grafana service account tokens, cloud keys), passwords (Grafana's admin user, a database behind the shop), object store keys, the keys of TLS certificates, and webhook URLs that carry a token in their path. Terraform state counts too: it stores the values Terraform last saw, secrets included. Tenant IDs, data source UIDs and addresses are not secrets, and they belong in Git.

## Where they go instead

A Kubernetes Secret holds the value, and a pod reads it as a file or an environment variable. Charts accept a reference: Grafana's chart takes `admin.existingSecret` with the key names, and the release never sees the password in its values. Grafana's provisioning files can read environment variables, so a data source password can come from a Secret through the pod's environment. Terraform's Grafana provider reads `GRAFANA_AUTH` from the environment, which is how your pod `work` gets the token.

<Layers caption="One secret, from where it is made to where it is used">
  <Layer title="Generated">By a person or a playbook, shown once, never written to a file.</Layer>
  <Layer title="Stored">A Kubernetes Secret, or a vault outside the cluster.</Layer>
  <Layer title="Referenced" hot>Values and files name the Secret and the key, not the value.</Layer>
  <Layer title="Used">The pod reads it as an environment variable or a mounted file.</Layer>
</Layers>

A Kubernetes Secret is only base64-encoded by default, not encrypted, so who may read Secrets in a namespace is the real protection. Teams that want secrets in Git after all encrypt them first, or keep them in an external vault and sync them into the cluster; both keep the plain value out of the repository.

## Short lives and narrow rights

Grafana service account tokens have no expiry unless you set one, and Grafana's page advises a short one when in doubt. A token inherits the role of its service account, so a pipeline that only manages dashboards needs Editor, not Admin. Several tokens per account let you rotate one without stopping the others. The token of this module is Admin only because step 3 creates a Git Sync connection, which needs administration rights, and it expires after a day.

<Remember>
Git holds references; a Secret or a vault holds the value. A secret that reached Git is rotated, not just deleted.
</Remember>

<Question id="q-m16-s10" answer="d">
A Grafana token was committed by mistake and pushed. The next commit removes it. What must the team do?

- Nothing more, the latest commit no longer has the token

  Every earlier commit still holds it, and so does every clone made in between.

- Rewrite the history so that no commit has the token

  That helps the next clones, but copies made before the rewrite still hold a working token.

- Make the repository private

  Everyone who already cloned it keeps the token, and private repositories leak too.

- Revoke the token in Grafana and give the pipeline a new one from a Secret

  Only revoking makes the leaked copy worthless. The new token then lives where it belongs.
</Question>
