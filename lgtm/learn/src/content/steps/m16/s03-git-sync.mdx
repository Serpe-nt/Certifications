<Problem>
Step 2 left a gap. A provisioned dashboard cannot be saved from the screen, so a colleague who wants to move one panel copies the JSON, edits it in a text editor, commits it and waits for a deploy. Most people give up and build a private copy by hand, and the drift from step 1 starts again.
</Problem>

<Idea>
Git Sync links a Grafana folder to a path in a Git repository, in both directions. Grafana pulls the repository on an interval and creates the dashboards it finds; a save on the screen becomes a commit or a pull request. Generally available since Grafana 13.0, it is the method Grafana's documentation recommends for provisioning dashboards.
</Idea>

## How the two copies stay one

Each link is a Repository resource in Grafana's newer API, `provisioning.grafana.app`. (A separate Connection resource exists only for GitHub App and OAuth sign-in.) It names the Git URL, the branch, a path inside the repository, a title and a sync target. With the default target `folder`, Grafana makes a folder named after the Repository's `title` and puts every dashboard JSON file under the path into it, with subfolders for subdirectories. With `folderless`, the files land at the top of the Dashboards list.

From Git to Grafana, Grafana polls the branch, every 60 seconds by default on a self-hosted Grafana, or reacts at once to a webhook from the Git provider. From Grafana to Git, the save dialog of a synced dashboard asks for a branch, a file name and a comment. The workflow `write` lets it commit straight to the branch; `branch` makes it push a new branch and open a pull request instead. With no workflow the connection is read only.

<Flow caption="One dashboard, edited on either side">
  <Stage title="Screen" kicker="Save">A save becomes a commit or a pull request.</Stage>
  <Stage title="Repository" kicker="branch and path">Review and merge as for code.</Stage>
  <Stage title="Grafana" kicker="poll or webhook">Pulls the merge and updates the folder.</Stage>
</Flow>

## What it covers, and what it needs

Git Sync manages dashboards and folders. Alert rules, data sources and library panels are not supported yet; they stay with provisioning files or Terraform. Moving an existing dashboard into a synced folder means exporting it to the repository and deleting the original, so that the synced copy can take over its UID. Git Sync makes its own folders, so a folder that file provisioning or Terraform owns stays separate even if the names match.

A self-hosted Grafana 13 has the needed feature switch on by default. It can sync with GitHub through an app or a token, and with any other Git server through the type `git`, which speaks Git over HTTP with a token. Up to 10 connections are allowed by default, and Grafana advises staying under about 1,000 resources per connection.

## A Git server inside the lab, and Grafana's answer

No lesson pushes to GitHub, so this module runs its own Git server as a pod: Soft Serve, a small open-source server that speaks Git over HTTP. Your clone in WSL reaches it through a port-forward; pods reach it at `git.learn-m16.svc`.

Grafana, however, refuses Git URLs that resolve to a loopback, private, link-local or unspecified address, unless the host is listed in the setting `allowed_git_urls`. This protects a Grafana server from being used to reach machines behind it, the attack called SSRF. A second setting, `allow_insecure`, is needed before Grafana sends a token over plain `http://`. The lab's Grafana sets neither, and its release is not changed for one lesson. So you will send the connection and read the refusal, which is what a self-hosted Grafana says until an administrator lists the internal host.

<Compare caption="The same connection, two places">
  <Col title="This lab">Git server on a cluster address; refused until allowed_git_urls and allow_insecure are set.</Col>
  <Col title="Your own GitHub repository" hot>type github, a fine-grained token or a GitHub App, a public address; accepted.</Col>
</Compare>

With your own repository you would set `type` to `github`, give the `url` of the repository and a token with the repository permissions that Grafana's setup page lists (contents and pull requests read and write, among others), and the same folder would appear within a minute.

<Trap>
Allowing a whole private range such as `10.0.0.0/8` in `allowed_git_urls` removes the protection for every host in it, and the listed hosts receive the Git token on every sync. List the one Git host, not the network.
</Trap>

<Remember>
Git Sync is a two-way link between one Grafana folder and one path in Git, for dashboards and folders only. A self-hosted Grafana refuses a Git server on a private address until `allowed_git_urls` names it.
</Remember>

<Question id="q-m16-s03" answer="a">
A team connects its self-hosted Grafana 13 to its own Git server at `git.corp.internal`, which resolves to 10.20.0.15. The connection is refused before any sync. What fixes it with the least exposure?

- List `git.corp.internal` in `allowed_git_urls`

  Grafana rejects private addresses by default to prevent SSRF. Listing the one host allows it and nothing else.

- Add `10.0.0.0/8` to `allowed_git_urls`

  That works, but it reopens the whole private range to requests from Grafana, which the default exists to prevent.

- Switch the connection's workflow from `write` to `branch`

  The workflow decides how saves reach Git. It has nothing to do with which addresses Grafana may call.

- Turn on the `provisioning` feature toggle

  In Grafana 13 that toggle is already on by default for self-hosted instances.
</Question>
