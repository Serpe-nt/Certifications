<Problem>
You have a dashboard generated by code (step 5), a Terraform folder for Grafana (step 4) and a Git server (step 3). Each piece works on its own. The question a team asks is simpler: when a colleague proposes a new dashboard on a branch, how does it reach Grafana, and who sees what before it does?
</Problem>

<Idea>
A promotion is one loop: change on a branch, show the effect, review, merge, deliver from the main branch only, and check the result. The branch never touches the lab; the main branch is what runs. Every step leaves a record: the commit, the plan, the merge and the apply.
</Idea>

## The loop

The change starts on a branch, so the main branch stays what the lab runs. The author pushes the branch and asks for a review. The reviewer reads two things: the diff of the files, which says what the author meant, and a plan made from the branch, which says what will change in Grafana. In a hosted Git service a CI job posts that plan on the pull request; here you make it by hand in the pod. After the merge, the delivery runs from the main branch, and a last look at Grafana closes the loop.

<Timeline caption="One change, from branch to Grafana">
  <Event at="1" title="Branch">Add the generated dashboard and its resource.</Event>
  <Event at="2" title="Plan from the branch">1 to add; nothing else moves.</Event>
  <Event at="3" title="Merge">The main branch now holds the change.</Event>
  <Event at="4" title="Apply from main">Grafana gets the dashboard.</Event>
  <Event at="5" title="Check">The folder shows it with its three panels.</Event>
</Timeline>

## Who delivers

Here Terraform delivers, because the lab's Grafana does not sync from a Git server on a private address. With Git Sync connected to a public repository, the merge itself would be the delivery: Grafana would pull the main branch within its sync interval, and the same review would have happened in the pull request. Grafana's documentation describes the larger form of this loop: a development Grafana synced to one branch or path, a production Grafana to another, and promotion as a merge between them.

What must not happen is a second way in. If someone also edits the dashboard on the screen, the next plan shows the edit as drift and undoes it. The loop works because main is the only source.

<InLab>
The plan and the apply run in the pod `work` of `learn-m16`, from its clone of `http://git.learn-m16.svc:23232/m16.git`, with the token from the Secret `grafana-m16`.
</InLab>

<Trap>
Applying from the branch before the merge puts unreviewed work into the lab, and the next apply from main takes it out again. Plan from the branch; apply from main.
</Trap>

<Do>
1. Make sure the port-forward to the Git server runs (step 3, action 6). Bring back the resources of step 4 from the main branch: <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && git checkout -q main && git pull -q && terraform plan -no-color -out=m16.plan | tail -1 && terraform apply -no-color m16.plan | tail -1'`}</Cmd> Three resources are added: the folder **Learn m16**, its dashboard and the contact point.
2. In WSL, start a branch and put the dashboard you generated in step 5 into the repository: <Cmd>{`cd ~/m16 && git switch -c add-generated-dashboard && mkdir -p terraform/dashboards && cp ~/m16-generated.json terraform/dashboards/generated.json`}</Cmd>
3. Add this resource at the end of `~/m16/terraform/main.tf`. It reads the JSON from the file and puts the dashboard in the same folder.

   ```hcl
   resource "grafana_dashboard" "generated" {
     folder      = grafana_folder.m16.uid
     config_json = file("${path.module}/dashboards/generated.json")
   }
   ```
4. Commit, push the branch, and read the change as a reviewer would, first the files, then the plan made from the branch: <Cmd>{`git add terraform && git commit -q -m "Add the generated dashboard" && git push -q origin add-generated-dashboard && git diff --stat main...add-generated-dashboard`}</Cmd> <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && git fetch -q origin && git checkout -q origin/add-generated-dashboard && terraform plan -no-color | tail -1'`}</Cmd> The plan says `Plan: 1 to add, 0 to change, 0 to destroy.` Nothing in Grafana has changed yet.
5. Approve the change by merging it into main and pushing main: <Cmd>{`git switch main && git merge -q --no-ff add-generated-dashboard -m "Merge: add the generated dashboard" && git push -q origin main`}</Cmd>
6. Deliver from main only, and keep the last line of the apply: <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && git checkout -q main && git pull -q && terraform plan -no-color -out=m16.plan | tail -1 && terraform apply -no-color m16.plan | tail -1'`}</Cmd>
7. Open <LabLink to="grafana" path="/dashboards">Dashboards</LabLink> and the folder **Learn m16**. It holds **m16 generated: requests per service** with one panel each for checkout, payment and cart, next to the dashboard from step 4.
8. Clean up the whole module. Destroy everything Terraform made, then delete the namespace: <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && terraform destroy -no-color -auto-approve | tail -1'`}</Cmd> <Cmd>{`pkill -f "port-forward svc/git 18100"; kubectl delete namespace learn-m16`}</Cmd> In <LabLink to="grafana" path="/org/serviceaccounts">Service accounts</LabLink>, delete the service account `learn-m16`, which deletes its token. Your clone in `~/m16` can stay or go: <Cmd>{`rm -rf ~/m16 ~/m16-generated.json`}</Cmd>
</Do>

<Done>
A dashboard went from a branch, through a plan and a merge, into Grafana from the main branch only, and everything the module created is gone.
</Done>

<Trap practice>
If the plan of action 4 shows more than one change, main and the lab already differed before your branch: someone changed a resource on the screen, or step 4 was not destroyed. Apply main first, then plan the branch again.
</Trap>

<Remember>
Plan from the branch, review the plan with the diff, merge, and deliver from main only.
</Remember>

<Question id="q-m16-s11" answer="b">
A reviewer approves a pull request that adds one dashboard. After the merge, the apply from main reports "1 added, 1 changed". What does the extra change most likely mean?

- Terraform always changes the folder when a dashboard is added

  Adding a dashboard does not change its folder resource. A clean change shows only what the files changed.

- Grafana had drifted from main, and the apply undid it

  A change nobody proposed is drift: someone edited a managed resource outside Git, and main won.

- The branch was merged twice

  Merging the same commits again adds nothing new to plan.

- The plan of the branch was wrong and should be ignored

  The branch plan was right for its moment. The difference came from Grafana, not from the plan.
</Question>
