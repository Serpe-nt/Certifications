<Problem>
Your team runs its cloud accounts with Terraform: every bucket and every network goes through a plan that someone reads. Grafana is the one place where a folder, a dashboard or a contact point appears without a plan. When a contact point is wrong, nobody can say when it changed.
</Problem>

<Idea>
The Grafana provider lets Terraform manage Grafana resources the way it manages a cloud account. You describe folders, dashboards, contact points and alert rules in `.tf` files; `terraform plan` compares them with Grafana and lists every difference; `terraform apply` makes Grafana match. Grafana's documentation calls it the as-code tool that supports the most resources.
</Idea>

## Resources, a provider and its token

A `.tf` file declares resources. `grafana_folder` is a folder, `grafana_dashboard` takes a dashboard's JSON model in `config_json`, and `grafana_contact_point` describes where notifications go. A resource can refer to another one, as `grafana_folder.m16.uid`, so Terraform knows to create the folder before the dashboard in it.

The provider needs Grafana's address and a credential. It reads them from its block in the file, or from the environment variables `GRAFANA_URL` and `GRAFANA_AUTH`. The credential is a service account token: a key that belongs to a service account, not to a person, so it survives when people leave and can have exactly the role the pipeline needs. In this module the token lives in a Kubernetes Secret, and the pod that runs Terraform gets it as an environment variable. It never appears in a file. Step 10 comes back to this.

## Plan, apply, and the state

`terraform plan` is the review. It reads Grafana through the API and prints each resource with a sign: `+` for create, `~` for change in place, `-` for destroy, `-/+` for replace. The last line counts them. Saved with `-out`, the plan can be applied exactly as it was read, even if the files change in between.

To know which dashboard in Grafana belongs to which resource, Terraform keeps a state file. The state holds the real IDs and the last values it saw, which can include secrets such as a webhook password. It belongs in a protected backend, never in Git. Here it stays in the working folder of the pod, which is enough for one learner.

  <Stage title="Edit" kicker=".tf in Git">Change the files in the repository.</Stage>
  <Stage title="Plan" kicker="terraform plan">Compare files, state and Grafana; print the difference.</Stage>
  <Stage title="Review" kicker="a person">Read every + ~ and - line.</Stage>

## What Grafana does with Terraform's objects

Alerting resources created through the provisioning API, which the provider uses, are marked as provisioned. By default you cannot edit them in Grafana's screen, so the files stay the source of truth. Each alerting resource has an argument `disable_provenance` that allows editing on the screen; using it gives up that guarantee. A folder and a dashboard made by Terraform can still be changed on the screen, and the next plan shows the change as drift and undoes it.

<Do>
1. Have the port-forward to the Git server from step 3 running, then, in WSL, make the folder for Terraform in your clone: <Cmd>{`mkdir -p ~/m16/terraform`}</Cmd>
2. Save this as `~/m16/terraform/main.tf`. It declares the folder `Learn m16`, one dashboard with one panel on checkout's orders, and a contact point that nothing routes to.

   ```hcl
   terraform {
     required_providers {
       grafana = {
         source  = "grafana/grafana"
         version = "4.55.0"
       }
     }
   }

   # Address and token come from GRAFANA_URL and GRAFANA_AUTH.
   provider "grafana" {}

   resource "grafana_folder" "m16" {
     uid   = "learn-m16"
     title = "Learn m16"
   }

   resource "grafana_dashboard" "orders" {
     folder = grafana_folder.m16.uid
     config_json = jsonencode({
       uid   = "m16-orders"
       title = "m16 checkout orders"
       panels = [{
         type       = "timeseries"
         title      = "Orders per second"
         gridPos    = { x = 0, y = 0, w = 12, h = 8 }
         datasource = { type = "prometheus", uid = "mimir" }
         targets = [{
           refId = "A"
           expr  = "sum(rate(traces_spanmetrics_calls_total{service_name=\"checkout\", span_name=\"oteldemo.CheckoutService/PlaceOrder\"}[5m]))"
         }]
       }]
     })
   }

   resource "grafana_contact_point" "m16" {
     name = "m16 webhook"
     webhook {
       url = "http://webhook.learn-m16.svc:8080/m16"
     }
   }
   ```
3. Commit and push it: <Cmd>{`cd ~/m16 && git add terraform/main.tf && git commit -q -m "Grafana folder, dashboard and contact point for m16" && git push -q origin main`}</Cmd>
4. In the pod, pull the commit and initialise Terraform. It downloads the pinned provider: <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && git pull -q && terraform init -input=false -no-color | tail -3'`}</Cmd> The last lines say that Terraform has been successfully initialized.
5. The contact point **m16 webhook** is under <LabLink to="grafana" path="/alerting/notifications">Alerting > Contact points</LabLink>, marked as provisioned.

Change the panel's title in `main.tf` from `Orders per second` to `PlaceOrder calls per second`, commit, push and plan again: <Cmd>{`cd ~/m16 && sed -i 's/Orders per second/PlaceOrder calls per second/' terraform/main.tf && git commit -q -am "Clearer panel title" && git push -q origin main`}</Cmd> <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && git pull -q && terraform plan -no-color -out=m16.plan'`}</Cmd> The dashboard is changed in place (`~`), and the plan prints the old and new JSON. Copy the summary line for the check.
7. Apply the change, then destroy everything this step made, and read the summary: <Cmd>{`kubectl -n learn-m16 exec work -c terraform -- sh -c 'cd /work/m16/terraform && terraform apply -no-color m16.plan && terraform destroy -no-color -auto-approve | tail -1'`}</Cmd> It ends with `Destroy complete! Resources: 3 destroyed.` The folder and the contact point are gone from Grafana. Keep `main.tf` in the repository; step 11 uses it again.

<Question id="q-m16-s04" answer="c">
A plan for a Grafana dashboard prints `-/+ resource "grafana_dashboard" "orders"` with "forces replacement" next to `uid`. What will apply do?

- Change the dashboard's title in place and keep its history

  An in-place change is shown with `~`. `-/+` is a replacement.

- Nothing, because a plan only reports drift

  A plan reports what apply will do. Apply then does it.

- Delete the dashboard and create a new one with the new UID

  `-/+` means destroy, then create. Links and bookmarks to the old UID stop working.

- Create a second dashboard and keep the first

  Terraform keeps one object per resource. It would not leave the old one behind.
</Question>
