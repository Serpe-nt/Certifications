<Problem>
Ten percent of the workshop's checkouts fail with a 500. The trace from step 7 shows a server span marked as an error, three database spans and a call to the shop, and nothing about the card charge, because the charge is plain Python. You cannot see whether the time went into reserving stock, charging the card or storing the order.
</Problem>

<Idea>
With the API you create spans for your own work and enrich the spans that libraries started. In Python, `tracer.start_as_current_span()` in a `with` block starts a span, makes it current so that spans inside it become its children, and ends it when the block ends. An exception that leaves the block is recorded on the span and sets its status to Error.
</Idea>

## A tracer from the API

The code needs one import and one tracer, created once at module level:

```python
from opentelemetry import trace

tracer = trace.get_tracer("workshop")
```

That is all the code knows about OpenTelemetry. The agent from step 7 still builds the SDK, the exporter and the sampler behind the API, as step 2 described. The name `workshop` becomes the instrumentation scope of every span this tracer creates (step 4).

## A span around your own work

`start_as_current_span` used as a `with` block starts a span, makes it current, and ends it when the block ends. Spans that start inside the block, from your code or from an instrumentation library, take it as their parent. The charge becomes a span of its own:

```python
def charge(total):
    """Pretend to charge a card: a short wait, and sometimes a decline."""
    with tracer.start_as_current_span("checkout.charge") as span:
        span.set_attribute("workshop.order.total_usd", round(total, 2))
        time.sleep(random.uniform(0.01, 0.05))
        if random.random() < FAIL_RATE:
            raise PaymentError(f"card declined for {total:.2f} USD")
```

The checkout handler gets two more spans the same way, `checkout.reserve` around the stock update and `checkout.store` around the insert, and the computation gets a span `fibonacci`. The SQLite spans of step 7 now appear under `checkout.reserve` and `checkout.store`, because those spans were current when the queries ran.

## Attributes on your spans and on the server span

`span.set_attribute()` adds an attribute to a span you hold. For the span that a library started, `trace.get_current_span()` returns it: inside a Flask handler that is the server span. The checkout handler puts the request's details on it:

```python
    server_span = trace.get_current_span()
    server_span.set_attribute("workshop.sku", str(sku))
    server_span.set_attribute("workshop.quantity", quantity if isinstance(quantity, int) else -1)
```

and, once the order is stored, `server_span.set_attribute("workshop.order.id", order_id)`. An attribute value must be a string, a boolean, a number, or an array of these, which is why the code turns an unknown SKU into a string and an odd quantity into `-1`. The workshop's own attributes all start with `workshop.`, so they cannot be mistaken for the names of a semantic convention.

## Events, exceptions and status

`span.add_event()` records a moment with a time and attributes of its own. The reserve span gets an event `stock reserved` with the stock left after the update, or `out of stock` when there is not enough.

A declined charge raises `PaymentError` inside the `checkout.charge` block. By default, Python's `start_as_current_span` does two things when an exception leaves the block: it records an exception event, and it sets the span's status to Error with the exception as description. You can switch either off with `record_exception=False` or `set_status_on_exception=False`. The event is named `exception` and carries `exception.type`, `exception.message` and `exception.stacktrace`.

The handler catches the exception and answers 500, so the Flask server span ends with status Error as well: the HTTP conventions set Error on a server span for a 5xx response, and leave it Unset for a 4xx.

The semantic convention page for exceptions on spans is now marked Deprecated and points to exceptions in logs instead. Instrumentations keep the span event by default for now, and the Trace API still describes recording an exception as an event.

<Trap>
`start_span` without `as_current` starts a span but does not make it current: spans started afterwards do not become its children. Use `start_as_current_span` unless you manage the context yourself.
</Trap>

<Trap practice>
Python is strict about indentation: the new `with` lines keep the indentation of the lines they replace, and the code inside them moves one level in. If the service does not start, `run.py` prints the line that failed. A `with` that holds three things (`tracer...`, `db_lock`, `db() as cur`) is one line.
</Trap>

<Remember>
`tracer = trace.get_tracer(...)` once; `with tracer.start_as_current_span(...) as span:` around your own work; `trace.get_current_span()` to enrich the library's span. An exception that leaves the block becomes an event and sets Error.
</Remember>

<Question id="q-m07-s08" answer="c">
Python code raises an exception inside `with tracer.start_as_current_span("charge"):` and does not catch it inside the block. With default arguments, what happens to the span?

- It stays open, because the block did not finish normally

  Leaving the with block ends the span whether or not an exception was raised.

- It is ended with status Ok, because the SDK only records outcomes the code sets

  Nothing sets Ok by itself. The defaults record the exception and set Error.

- It records an exception event and gets status Error, then ends

  record_exception and set_status_on_exception both default to True for start_as_current_span.

- It is dropped, so failed operations do not reach the backend

  The span is exported like any other. The exception makes it more useful, not less.
</Question>
