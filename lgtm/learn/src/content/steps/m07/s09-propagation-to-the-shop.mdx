<Idea>
To propagate by hand you start a client span for the outgoing call, make it current, and call the propagator's inject on the carrier, here the request headers. The receiving service extracts the context and continues the trace. Through a message queue the producer injects its context into the message; the messaging conventions then relate the consumer's span to it with a link.
</Idea>

## Switch the library off, do its work yourself

The agent loads every instrumentation it finds. `OTEL_PYTHON_DISABLED_INSTRUMENTATIONS` takes a comma-separated list of entry point names that it must skip; with `requests` in it, calls to the shop are no longer traced or propagated. Two lines go into `workshop.env`. The second one writes out the default propagators, so you can see what inject will use:

```text
OTEL_PYTHON_DISABLED_INSTRUMENTATIONS=requests
OTEL_PROPAGATORS=tracecontext,baggage
```

Now the code has to make the client span and inject the context, which is what the instrumentation did before.

## A client span, then inject

Each call to the shop goes through one new function. It starts a span of kind client named after the HTTP method, as the HTTP conventions ask for a client span with no URL template. It sets the convention's attributes, injects the context into an empty dictionary of headers, and sends the request with them:

```python
def shop_get(path):
    """GET a path of the shop in a client span, with the context in the headers."""
    url = f"{SHOP_URL}{path}"
    # HTTP client span names are the method alone (semantic conventions).
    with tracer.start_as_current_span("GET", kind=SpanKind.CLIENT) as span:
        span.set_attribute("http.request.method", "GET")
        span.set_attribute("url.full", url)
        headers = {}
        # Adds traceparent (this span as the parent) and baggage.
        propagate.inject(headers)
        response = requests.get(url, headers=headers, timeout=5)
        span.set_attribute("http.response.status_code", response.status_code)
        if response.status_code >= 400:
            span.set_status(StatusCode.ERROR)
        response.raise_for_status()
        return response
```

`propagate.inject(headers)` reads the current context and lets the global propagator write into the dictionary. The client span is current at that moment, so `traceparent` carries its span ID as the parent ID, exactly as step 6 described. The order matters: start the client span first, then inject. A client span sets Error for a 4xx or 5xx answer, as the HTTP conventions ask.

## Baggage from the edge of the request

The checkout handler reads a header `X-Customer-Tier` and puts its value into baggage for the rest of the request:

```python
@app.post("/checkout")
def checkout():
    body = request.get_json(silent=True) or {}
    sku = body.get("sku")
    quantity = body.get("quantity", 1)
    # Baggage travels with the context to every service downstream.
    tier = request.headers.get("X-Customer-Tier", "standard")
    token = context.attach(baggage.set_baggage("workshop.customer.tier", tier))
    try:
        return place_order(sku, quantity)
    finally:
        context.detach(token)
```

`set_baggage` returns a new context with the entry, because a context never changes (step 6). `attach` makes it current and returns a token, and `detach` in `finally` restores the previous context even when the order fails. The rest of the old handler becomes `place_order(sku, quantity)`. Every inject inside it now also writes a `baggage` header. Nothing in the shop copies that entry into an attribute, so you will not find it in Tempo: baggage and attributes are separate (step 6).

## Through Kafka: a link, not a parent

In the shop, checkout does not call the fraud check directly. It writes the order to the Kafka topic `orders` in a producer span `publish orders`, and fraud-detection, a Java service with the Java agent, reads it later. The producer attaches its context to the message as the creation context, in the message's headers.

On the consumer side, the messaging conventions use links as the default way to relate a consumer to a producer. A span has one parent, a consumer may handle a batch of messages from many producers, and it may already run inside another span; a link works in all these cases. So fraud-detection starts a trace of its own: a root span `receive orders` of kind consumer, and a child `process orders` with a link to checkout's `publish orders` span in the other trace.

<Flow caption="One order through Kafka in the lab">
  <Stage title="checkout" kicker="Producer span">publish orders: the context is attached to the message.</Stage>
  <Stage title="Kafka topic orders" kicker="Carrier">The message headers hold the creation context.</Stage>
  <Stage title="fraud-detection" kicker="New trace">receive orders, then process orders with a link to publish orders.</Stage>
</Flow>

<Question id="q-m07-s09" answer="b">
In the lab, fraud-detection's `process orders` span carries a link to checkout's `publish orders` span instead of being its child. Why do the messaging conventions make links the default?

- Kafka messages cannot carry headers, so only a link can be stored

  Kafka messages do carry headers; the creation context travels in them.

- A span has one parent, but a consumer may handle messages from many producers

  Links are the one structure that works for batches and for consumers that already have an ambient context.

- A producer span has ended by the time the consumer runs, and an ended span cannot be a parent

  The Trace API allows an ended span to be used as a parent. The reason is the single parent, not the timing.

- Links cost less to store in a backend than parent span IDs

  Storage cost is not the reason the conventions give.
</Question>
