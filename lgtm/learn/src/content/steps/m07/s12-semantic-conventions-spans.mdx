<Problem>
Your workshop's database spans arrived in Tempo named `sqlite`, though the instrumentation called them `SELECT` and `UPDATE`. The front proxy's server spans arrived as `GET` with an attribute saying they were once `ingress`, and checkout's Kafka span as `publish orders`, once `orders publish`. Someone renamed them on the way, and there is a rule behind each new name.
</Problem>

Module m02 introduced the semantic conventions as a shared dictionary. Now that you have made HTTP, database and messaging spans yourself, here are the rules for exactly those three kinds.

<Idea>
For HTTP, database and messaging operations, the semantic conventions fix the span's name, its kind, when its status is Error, and which attributes it carries at which requirement level. Names are built from attributes and should stay low cardinality. The conventions for HTTP and databases are Stable; those for messaging are in Development.
</Idea>

## HTTP spans

An HTTP span is named `{method} {target}` when a low-cardinality target exists, and `{method}` alone when not. For a server span the target is `http.route`, the route template; for a client span it is `url.template`, when the instrumentation has one. The URI path must not be used as a target by default, because `/orders/8812` would give every order a span name of its own.

A server span has kind server and must carry `http.request.method`, `url.path` and `url.scheme`, and, among the conditionally required ones, `http.route` and `http.response.status_code` when they exist. A client span has kind client and must carry `http.request.method`, `server.address`, `server.port` and `url.full`. Status follows the rules you met in steps 8 and 9: a 5xx answer sets Error on both sides; a 4xx sets Error on a client span and leaves a server span Unset.

## Database spans

A database span is named after the best thing available, in this order: `db.query.summary`; then `{db.operation.name} {target}`; then the target alone; and finally `db.system.name`. The target is the collection (`db.collection.name`), a stored procedure, the namespace (`db.namespace`), or the server's address. The kind should be client.

`db.system.name` is required, and `db.query.text` is recommended. `db.collection.name`, `db.namespace` and `db.operation.name` are among the conditionally required ones: required under a condition the page states for each, for `db.namespace` simply "if available".

## Messaging spans

The messaging conventions name a span `{messaging.operation.name} {destination}`, such as `publish shop.orders` or `process orders`. They define five operation types and the kind for each: create (producer), send (producer, or client when it does not carry the creation context), receive (client), process (consumer) and settle (client). The creation context and the links between consumer and producer are the ones from step 9. The page's status is Development, so names can still change.

## Who renamed your spans

Instrumentations change slowly: many still send the older, experimental names unless you opt in, as `OTEL_SEMCONV_STABILITY_OPT_IN=http,database` did for the workshop in step 7. The Python instrumentations support it for HTTP and databases. Values with `/dup` send the old and the new names at once while dashboards and queries move over.

The lab's gateway adds a second safety net. Its transform processor calls `set_semconv_span_name("1.43.0", "original_span_name")`, which rewrites the name of HTTP, RPC, messaging and database spans from their attributes by the conventions, and keeps the old name in `original_span_name` when it differs. Spans of other kinds, such as the workshop's `checkout.charge`, keep their names. The function exists to keep span names low cardinality, for span metrics above all.

<Trap practice>
The rule puts the operation first and the target second, separated by one space: no colon, no dot. The collection name keeps its schema prefix, as the instrumentation would report it.
</Trap>

<Remember>
HTTP: `{method} {target}`, never the raw path. Database: summary, then operation and target, then target, then the system. Messaging: operation and destination, still in Development.
</Remember>

<Question id="q-m07-s12" answer="c">
An HTTP server instrumentation handles `GET /orders/8812`. Its framework gives it no route template. What should the span be named?

- GET /orders/8812, because the full path is the most precise target

  Instrumentation must not use the URI path as a target by default; every order would get its own span name.

- `/orders/{id}`, made by replacing the number in the path

  A server span's target should be the route template, which is missing here. The instrumentation does not invent one.

- GET, the HTTP method alone, with no target

  With no low-cardinality target available, an HTTP span is named after the method alone.

- HTTP GET, with the protocol in front

  HTTP is used as the method only when the method is unknown (_OTHER). Here the method is known.
</Question>
