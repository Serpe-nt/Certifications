<Problem>
Checkout is slow, but only sometimes. It runs as three pods on two nodes. A span tells you which operation was slow, yet not which pod or node did the work, and copying the pod name into every span by hand would be tedious and easy to forget. You need the "who sent this" written once and attached to everything the service sends.
</Problem>

<Idea>
A resource is a set of attributes that describes the entity producing telemetry: the service, its instance, the pod, the node, the host. The SDK attaches it to the provider when the provider is created, and from then on every span, metric and log from that provider carries it. It cannot be changed afterwards.
</Idea>

## One description for everything a process sends

A process that runs in a container on Kubernetes has a process name, a pod name, a namespace and maybe a Deployment name. All of them can go into its resource. In a backend you then narrow a latency problem down to one container, pod or Deployment.

The resource lives on the provider. When the SDK creates its TracerProvider (or MeterProvider, or LoggerProvider), it gets a resource, and every span produced by any tracer of that provider must carry it. The specification calls a resource immutable, and the link between provider and resource cannot be changed later. To change a resource attribute you start the process again.

## What the SDK fills in by itself

Some attributes are always there. `service.name` is the logical name of the service; if nobody sets it, SDKs use `unknown_service`, so set it yourself, for example with `OTEL_SERVICE_NAME`. The SDK also describes itself with `telemetry.sdk.name`, `telemetry.sdk.language` and `telemetry.sdk.version`. The OpenTelemetry SDK must set `telemetry.sdk.name` to `opentelemetry`; any other SDK must use a name of its own, because that value is reserved.

Resource detectors add more. Most SDKs have detectors for the operating system, the host, the process and its runtime, the container, Kubernetes and cloud providers. The specification asks for detectors of generic platforms such as Docker and Kubernetes to ship as packages separate from the SDK. A detector that finds nothing is not an error.

## Your own attributes, and which value wins

You add your own attributes in code or with the environment variable `OTEL_RESOURCE_ATTRIBUTES`, a list such as `service.namespace=shop,deployment.environment.name=production`. Every value in it is a string, and a comma or an equals sign inside a key or value must be percent-encoded. If the variable cannot be decoded, the SDK should drop all of it and report an error.

When two sources give the same key, the SDK merges them and the updating resource wins. Two rules from the specification decide the usual cases. The SDK merges `OTEL_RESOURCE_ATTRIBUTES` as the secondary resource, so a resource you set in code wins over it. And `OTEL_SERVICE_NAME` wins over a `service.name` written in `OTEL_RESOURCE_ATTRIBUTES`.

<Flow caption="Where a span's resource comes from">
  <Stage title="SDK defaults" kicker="Always">service.name (unknown_service until set) and telemetry.sdk.*</Stage>
  <Stage title="Detectors and environment" kicker="At start-up">host, process, container; OTEL_RESOURCE_ATTRIBUTES, OTEL_SERVICE_NAME</Stage>
  <Stage title="Resource on the provider" kicker="Fixed">Attached to every span, metric and log the provider produces.</Stage>
</Flow>

## A collector can add attributes on the way

The resource is not only the SDK's business. A Collector between the service and the backend can add or overwrite resource attributes. The lab's gateway adds `cluster="lgtm-lab"` and `k8s.cluster.name` to everything, and its Kubernetes attributes processor adds the pod, the namespace, the node and the Deployment. That processor finds the pod by the IP address of the incoming connection unless it is told otherwise. Keep this in mind for step 7: your workshop service does not run in a pod, so the address the gateway sees belongs to something else.

<Remember>
The resource says who sent the data, it is fixed when the provider is created, and every span of that provider carries it. `OTEL_SERVICE_NAME` beats `service.name` in `OTEL_RESOURCE_ATTRIBUTES`, and code beats the environment.
</Remember>

<Question id="q-m07-s03" answer="b">
A service sets `OTEL_RESOURCE_ATTRIBUTES=deployment.environment.name=staging` in its Deployment, but its code also builds a resource with `deployment.environment.name` set to `production`. Which value do its spans carry?

- staging, because the environment always overrides code

  The specification merges the environment variable as the secondary resource. The value from code wins.

- production, because the resource given in code has priority over the environment variable

  The SDK merges OTEL_RESOURCE_ATTRIBUTES as the secondary resource, so the user-provided resource wins.

- Both values, as two separate resource attributes

  A resource holds one value per key. Merging keeps one.

- Neither, because a conflict makes the SDK discard the variable

  The variable is discarded only when it cannot be decoded, not when a key also comes from code.
</Question>
