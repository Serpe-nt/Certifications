<Problem>
Module m02 showed a span as a bar with a name, a duration and a parent. Now you are going to create spans yourself, and every choice is yours: what the span is called, what kind it is, when it counts as failed, whether a detail is an attribute or an event, and how it points to work in another trace. Wrong choices give traces that look fine and mislead.
</Problem>

<Idea>
A span is one operation. It has a name, a kind, a start and an end, attributes, events, links and a status, and it is identified by its span context. Only the span context travels to other services; everything else stays in the span and goes to the backend with it.
</Idea>

## The span context is the part that travels

Each span holds an immutable span context with four fields. The trace ID, 16 random bytes, groups all spans of one trace. The span ID, 8 random bytes, identifies this span and becomes the parent span ID of its children. The trace flags are one byte. Its lowest bit is the sampled flag, which says whether the caller sampled the trace; the Trace API now defines a second flag, Random, as well. The trace state is a list of key-value pairs that tracing vendors use for their own data. The span context is what goes into the headers of an outgoing call, and it is also what a link points to.

A span context made from a header that arrived from another process is marked as remote. Step 6 shows how the context is written into headers and read back.

## Name, kind and attributes

The name says what the work is, in the most general terms that still mean something. `get_account` is a good name; `get_account/42` is not, because a new user ID makes a new name. The ID belongs in an attribute.

The kind says how the span relates to other processes. It is set when the span starts and defaults to internal.

<Compare caption="Span kinds by direction and style of communication">
  <Col title="Client and server">Request and response. Client: an outgoing call that waits for the answer. Server: the handling of an incoming call while the caller waits.</Col>
  <Col title="Producer and consumer">Deferred work. Producer: creating a job for later. Consumer: processing it, perhaps long after the producer span ended.</Col>
  <Col title="Internal" hot>No remote parent or child: work inside one process. The default.</Col>
</Compare>

Attributes describe the operation. Give them when the span starts if you can: a sampler decides when the span is created and sees only what is there at that moment. The SDK limits a span to 128 attributes, 128 events and 128 links by default.

## Status follows strict rules

A span's status is Unset, Error or Ok. Unset is the default and means the operation finished without an error. Error means it failed. Ok means a developer or operator checked it and declared it a success.

The three are ordered: Ok is above Error, and Error is above Unset. Once a span is set to Ok, later attempts to change it should be ignored. An attempt to set Unset is ignored too. A description may go with Error only. Instrumentation libraries should leave the status Unset unless there is an error by the rules of the semantic conventions, and should not set Ok unless they are configured to. Analysis tools should treat Ok as a reason to suppress errors they would otherwise report, a 404 for example.

## Event or attribute, link or parent

An event is a named moment inside a span, with a timestamp and attributes of its own, like a structured log line attached to the span. Use an event when the time of the moment matters, and an attribute when it does not. An exception is often recorded as an event named `exception`, with the exception's type and message as attributes, and the lab's spans still carry such events. The semantic convention page for exceptions on spans is marked Deprecated today, in favour of recording exceptions as logs.

A link points from one span to the span context of another span that is causally related, in the same trace or in another one. A span has at most one parent, so links cover what a parent cannot: a batch job that processes items from many incoming requests, a new trace started at a trust boundary, or a consumer that handles a message long after the producer's trace has ended. Links given when the span starts can be used by a sampler; links added later may not be.

<Remember>
Only the span context travels. Status: Unset is success, Ok is final, Error follows the conventions. An event is a timed moment, an attribute is a fact, and a link joins spans that a parent cannot.

<Question id="q-m07-s05" answer="d">
Service A starts a client span, sets five attributes and an event on it, and calls service B. What does service B receive from that span with the call?

- Its five attributes, so B can copy them to its own span

  Attributes stay in the span and go to the backend with it. They are not sent to the next service.

- Its event, so B knows when A sent the request

  Events are part of the span's data for the backend. They are not propagated.

- Its status, so B can tell whether A saw an error

  The status is part of the span's data, not of the span context, so it is not propagated.

- Its span context: trace ID, span ID, trace flags and trace state

  The span context is the part of a span that is serialized and propagated to child spans across process boundaries.
</Question>
