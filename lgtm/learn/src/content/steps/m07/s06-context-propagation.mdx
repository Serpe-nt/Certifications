<Problem>
Checkout calls payment over gRPC, and payment runs in another process, in another language, on another node. For payment's span to join checkout's trace, something must carry the trace ID and the caller's span ID across the network. And the customer's loyalty tier, known only where the request came in, is needed three services further down.
</Problem>

<Idea>
Inside a process, OpenTelemetry keeps the current span and the baggage in a context object. Between processes, propagators inject that context into the carrier of an outgoing call, such as its headers, and extract it on the other side. By default they use the W3C `traceparent` header for the span context and the W3C `baggage` header for baggage.
</Idea>

## The context inside one process

A context is a small immutable object. Writing a value into it returns a new context that holds the old values and the new one; the old context does not change. A language keeps one context as the current one. When Python code runs `with tracer.start_as_current_span(...)`, the new span becomes current inside the block, so spans started there take it as their parent and the previous context comes back after the block. Code can also attach a context by hand and detach it later with the token that attach returned.

Traces, baggage and the other signals all read the same context. That is why one mechanism carries both the span context and the baggage.

## Inject on the way out, extract on the way in

A propagator works on a carrier. On an outgoing call it reads the span context and the baggage from the current context and injects them into the carrier, for example as HTTP headers. On an incoming call it extracts them from the carrier and returns a new context that holds them. The new server span takes the extracted span context as its remote parent. If a header cannot be parsed, extract must not throw an exception and must not store a value, so a valid context that was already there is kept.

Instrumentation libraries usually do this for you; the Propagators API is there for the cases they do not cover. Which propagators run is set with `OTEL_PROPAGATORS`. Its default is `tracecontext,baggage`. Other known values include `b3`, `b3multi`, `xray` and `none`. A note on the API: unless something configures propagators, the API uses no-op ones, which is why an SDK or an agent must set them up.

<Flow caption="One call, one header, one parent">
  <Stage title="Checkout" kicker="Client span">The client span for the call is current; its span context is injected.</Stage>
  <Stage title="traceparent" kicker="Carrier">00-trace ID-client span ID-01 travels in the gRPC metadata.</Stage>
  <Stage title="Payment" kicker="Server span">Extracts the header; its server span has the same trace ID and checkout's client span as parent.</Stage>
</Flow>

## Reading a traceparent header

The W3C Trace Context Recommendation defines the header as four fields joined by hyphens: version, trace ID, parent ID and trace flags, all in lower-case hexadecimal. For example:

`traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01`

Version `00` is the current format. The trace ID has 32 characters (16 bytes). The parent ID has 16 characters (8 bytes): it is the span ID of the caller's span, the client span that made the call. The flags `01` mean sampled. A trace ID or a parent ID of all zeros is invalid, and a receiver must then ignore the header. A second header, `tracestate`, carries up to 32 vendor entries.

## Baggage rides along with the context

Baggage is a key-value store that lives next to the context and travels with it, in the W3C `baggage` header. It is meant for values known at the start of a request that services further down need: an account ID, a product ID, a customer tier. Instrumentations propagate it automatically.

Baggage is not the same as attributes. A baggage entry appears on no span, metric or log until code reads it and adds it, although several languages offer a baggage span processor that does this for every span. And baggage travels in plain headers, often to services you do not own, and nothing checks that an entry is genuine. Keep credentials, API keys and personal data out of it.

</Remember>

<Question id="q-m07-s06" answer="b">
Checkout calls payment. In the trace, payment's server span has a parent span. Which span is it?

- Checkout's server span, the operation that decided to call payment

  The caller injects the context while its client span for the call is current, so that client span is the parent.

- Checkout's client span for that call, whose span ID travelled as the parent ID in traceparent

  The parent ID in traceparent is the span ID of the caller's client span, and the receiver takes it as its remote parent.

- The root span of the trace, because all remote spans hang under the root

  Only the trace ID is shared with the root. The parent is the span that made the call.

- None, because a span from another process starts a new root with the same trace ID

  Extracting the context gives the server span a remote parent; a trace has one root.
</Question>
