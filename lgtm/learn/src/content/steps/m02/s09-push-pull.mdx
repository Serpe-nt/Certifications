<Problem>
Telemetry has to travel from hundreds of pods to a store. Either the store goes and fetches it, or each pod sends it. The choice decides who must know about whom, how you notice a dead target, and what happens to a job that runs for ten seconds and exits.
</Problem>

Both answers are in use, often in the same cluster. This lab uses both.

<Idea>
In pull, the collector asks each target for its data on a schedule: Prometheus scrapes an HTTP page. In push, the source sends its data to a receiver: OpenTelemetry's OTLP works this way. Both are fine; each has cases where it fits better.
</Idea>

## Pull: Prometheus goes and asks

Prometheus collects metrics by pulling them over HTTP from each target at a fixed interval. Each target only has to serve a page of its current values; it does not need to know where Prometheus is.

The work moves to the other side: a puller must know its targets. Prometheus finds them through service discovery or from a static list. Kubernetes service discovery reads targets from the Kubernetes API and stays in step as pods come and go. Module m03 shows how.

In return, pull gives you some things for free. For every scrape Prometheus records `up`: 1 if the scrape worked, 0 if it failed, so a dead target is easy to see. You can also open a target's page in a browser, or start a second Prometheus on your laptop that scrapes the same targets.

## Push: the source sends

With OTLP, the client sends export requests to a server, such as a collector or a backend. The source must know where to send, and the receiver does not need a list of targets. Loki also receives its logs by push. Prometheus can accept OTLP pushes too, but that receiver is off by default.

<Compare caption="Who has to know whom">
  <Col title="Pull">Prometheus knows every target, through service discovery or a list. A dead target shows as `up` = 0.</Col>
  <Col title="Push">Every source knows the receiver's address. The receiver needs no list of targets.</Col>
</Compare>

## A short job and the Pushgateway

One weak spot of pull is a short job: it may end before any scrape finds it. For that case Prometheus has the Pushgateway. The job pushes its last results there, and Prometheus scrapes them from it.

Use it only for service-level batch jobs, jobs that do not belong to one machine or instance. It costs you three things: it can become a single point of failure, you lose `up` for the job, and it keeps every pushed series until you delete it.

<InLab>
The shop pushes OTLP to the collector gateway `otel-gateway`. Prometheus pulls metrics from exporters, then pushes them on to Mimir with remote write.
</InLab>

<Trap>
Do not pick a monitoring system only for push or pull. The Prometheus team says pull is slightly better, but not a major point. And do not push every service's metrics through the Pushgateway: stale series will stay there forever.
</Trap>

<Remember>
Pull means the store knows its targets and sees a dead one at the next scrape. Push means the source knows the store. The Pushgateway is only for short, service-level batch jobs.
</Remember>

<Question id="q-m02-s09" answer="d">
A nightly job deletes old users and exits after 20 seconds. The team wants its result in Prometheus. What is the recommended way?

- Lower the scrape interval to 1 second so Prometheus catches the job

  A short-lived job may still end between scrapes, and a 1-second interval adds load everywhere.

- Run a second Prometheus server only for the job

  A second server does not solve the problem: there is still nothing to scrape after the job exits.

- Send the job's log lines to Prometheus

  Prometheus does not take logs. It stores metrics.

- Push the job's result to a Pushgateway, without an instance label

  A service-level batch job is the case the Pushgateway is meant for.
</Question>
