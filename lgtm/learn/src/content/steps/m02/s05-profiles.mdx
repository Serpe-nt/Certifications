<Problem>
The ad service uses all its CPU. The metric shows the CPU line at the top. The trace shows that one span is slow. Neither tells you which function in the code is burning the CPU, so the developer still has to guess what to fix.
</Problem>

The three signals so far stop at the edge of the code. A fourth one looks inside it.

<Idea>
A profile records where a program spends its resources, down to the function. It takes many samples of the call stack and counts which code was running. Profiles are the newest signal, next to metrics, logs and traces.
</Idea>

## The question only a profile answers

Each signal answers its own question. A profile is the one that points at a line of code.

<Layers caption="Each signal and its question">
  <Layer title="Logs">What happened?</Layer>
  <Layer title="Metrics">How much, and how often?</Layer>
  <Layer title="Traces">Where did the request go, and where did it spend its time?</Layer>
  <Layer title="Profiles" hot>Which code uses the CPU or the memory?</Layer>
</Layers>

A profiler looks at the call stack again and again, for example on a timer, and counts which functions it finds. A function that shows up in many samples is where the time goes. There are several kinds of profile. On-CPU shows which functions use processor time. Off-CPU shows where threads wait, for example on locks or disk. Heap shows which functions hold memory. Allocations shows which code allocates the most memory.

## Watching from the kernel with eBPF

eBPF runs small, safe programs inside the Linux kernel. A profiler can use it to sample the stacks of any process, with no change to the code. It works on Linux only and needs root access on the host.

eBPF does more than profiles. OBI, OpenTelemetry eBPF Instrumentation, uses it to create traces and rate, error and duration metrics without code changes. Grafana Beyla is Grafana's distribution of OBI.

## Where profiles are stored, and how ready they are

Grafana Pyroscope is a profile database built like Loki, Mimir and Tempo. Alloy can collect CPU profiles with eBPF and send them to it.

In OpenTelemetry, profiles are still young. OpenTelemetry marks the profiles signal as Alpha. Traces, metrics and logs are further along: their protocol, OTLP, is stable.

<Remember>
When you know which service is slow but not which code, you need a profile. eBPF can collect one with no code change, on Linux.
</Remember>

<Question id="q-m02-s05" answer="b">
A service's CPU use is at 95%. The team knows which pod it is, but not which part of the code is responsible. Which signal answers that best?

- A metric of CPU use per pod

  The metric already showed the high CPU. It cannot point inside the code.

- An on-CPU profile

  An on-CPU profile shows which functions were running on the CPU.

- A trace of one slow request

  A trace shows which service and operation were slow, not which function used the CPU.

- Kubernetes events for the pod

  Events report things like scheduling and restarts, not code-level resource use.
</Question>
