<Problem>
The Java service calls the HTTP method `method`, the Go service calls it `http_verb`, and the Python service `request.type`. One dashboard for all three needs three queries, and a tool cannot know that the three names mean the same thing. Every team has invented its own words.
</Problem>

The fix is to agree on the words before any data is sent.

<Idea>
Semantic conventions are OpenTelemetry's shared dictionary. They fix the names, types and meaning of common attributes, and the names of common spans and metrics. When every service and library uses them, one query, one dashboard and one tool work for all.
</Idea>

## A shared dictionary for telemetry

The conventions define attribute names, their types, their meaning and their allowed values. They also define span names and kinds, and metric instruments with their units. They cover HTTP, databases, messaging, RPC, cloud providers, exceptions and more. There are conventions for each signal, and for resources: the attributes that describe what produces the telemetry.

<Compare caption="The HTTP method, before and after the agreement">
  <Col title="Each team's own name">`method` in Java, `http_verb` in Go, `request.type` in Python: three queries.</Col>
  <Col title="Semantic conventions" hot>`http.request.method` in every service: one query.</Col>
</Compare>

## An HTTP span, by the book

An HTTP server span carries `http.request.method`, `http.route` and `http.response.status_code`. Its name is the method and a low-cardinality target, such as `GET /webshop/articles/:article_id`, never the full path with an ID in it. A name with an ID would make a new span name for every article, the cardinality problem of step 10.

## service.name comes first

Of all the attributes, `service.name` matters most. It is a resource attribute, so every span, metric and log the SDK sends carries it. It is the logical name of a service, the same for every replica. If you do not set it, SDKs use `unknown_service`, so set it, for example with the `OTEL_SERVICE_NAME` variable.

## Conventions have versions

The conventions change over time, and some names have changed. Many older HTTP instrumentations still send the old names by default. `OTEL_SEMCONV_STABILITY_OPT_IN=http` switches them to the stable names, and `http/dup` sends both while you migrate.

<InLab>
Mimir and Loki turn `service.name` into the label `service_name`. That is the label you saw in the "Related logs" query of step 6.
</InLab>

<Trap>
Semantic conventions are not only for traces. Metrics, logs, profiles and resources have them too. And a name that looks right is not enough: the type and the meaning of the value must match as well.
</Trap>

<Remember>
Use the convention's name, type and meaning for every common attribute, and always set `service.name`. Then one query works for every service.
</Remember>

<Question id="q-m02-s11" answer="a">
A service sends spans with `service.name` set to `unknown_service:java`. What does this tell you?

- Nobody set the service name, so the SDK used its fallback value

  SDKs fall back to `unknown_service` plus the process name when `service.name` is not set.

- The service runs an old Java version that OpenTelemetry does not support

  The fallback says nothing about the Java version.

- The collector failed to reach the backend

  Export problems do not change resource attributes.

- Java services must always use this name by convention

  The convention is the opposite: every service should set its own logical name.
</Question>
