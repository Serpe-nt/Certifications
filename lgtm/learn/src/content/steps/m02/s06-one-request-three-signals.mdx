<Why>
You now know three signals, but only as ideas. In a real incident you jump between them fast: a graph shows a slow minute, you need one slow request from that minute, then the log lines it wrote. If you have never made those jumps, the first time should not be at 3 a.m.
</Why>

<Idea>
The lab links the three signals by one value: the trace ID. A latency graph carries example trace IDs, called exemplars. A trace links to the logs that carry its trace ID, and each of those log lines links back to the trace.
</Idea>

<Points>
  <Point label="Metric to trace: exemplars">An exemplar is one real trace kept next to a metric value. In this lab, Grafana draws exemplars as small green diamonds on the latency graph. Hover over one to see its trace ID.</Point>
  <Point label="The trace view">The trace view shows the root span's name and the trace ID at the top. Below it, each row is a span with its service, its operation and a bar for its duration. A search box in the header highlights the spans that match a word.</Point>
  <Point label="Trace to logs">The span details offer a **Related logs** link. It searches Loki for lines of the same service that carry the trace's ID, a few minutes either side of the span.</Point>
  <Point label="Log back to trace">Each shop log line in Loki carries the trace ID as a field. In the log details, a Links section shows `trace_id` with an **Open trace** link back to Tempo.</Point>
</Points>

<Do>
1. Open the dashboard <LabLink to="grafana" path="/d/shop-red-checkout">Shop / checkout (RED)</LabLink> in Grafana and set the time range to the last 15 minutes. The load generator places orders all the time, so the panels have data.
2. Read the four panels. Rate is requests per second, Errors is the share of failed spans, Duration is latency at p50, p95 and p99: these three come from Mimir. The fourth, "Logs of checkout", comes from Loki.
3. In the Duration panel, hover over one of the green diamonds. The tooltip shows a `traceID`. Click **Query with Tempo** next to it.
4. The trace opens in Explore. Copy the trace ID from the header. The trace can hold more than a hundred spans, and services show as `opentelemetry-demo/<name>`. Type `checkout` in the search box of the trace view to highlight the checkout spans.
5. Click a span of the checkout service. In its details, look at the resource attributes and find `service.name`.
6. In the same span details, click **Related logs**. Loki opens beside the trace with the query `{service_name="checkout"} | trace_id="..."`.
7. Expand one log line. Check that its `trace_id` is the ID you copied. Under Links, `trace_id` has an **Open trace** link that opens the same trace again.
8. Paste the trace ID in the lab check below.
</Do>

<Done>
You opened one trace from a diamond on the Duration panel. The log lines Loki showed all carry the same trace ID as the trace header.
</Done>

<Trap>
Copy the trace ID from the trace header. An ID read from an exemplar tooltip or a search result can lose a leading zero and have only 31 characters, which the check refuses. If **Related logs** shows no lines, the service may have written none in this request: try a span of payment.
</Trap>

<Question id="q-m02-s06" answer="a">
A latency graph has a spike at 14:02. What does an exemplar on that spike give you?

- The trace ID of one request from that interval

  An exemplar links a metric value to one example trace.

- The average latency of all requests in that minute

  The graph line already shows the latency. The exemplar points to one request.

- Every log line written during the spike

  Logs are reached from the trace by its ID. The exemplar itself holds a trace ID.

- A list of all traces slower than the p99

  An exemplar is one example, not a list of all slow traces.
</Question>
