<Problem>
Module m11 step 9 asked which metric costs tenant `lab` the most series in Mimir. The answer was not a metric any service of the shop exports: it was `traces_spanmetrics_latency_bucket`, written by Tempo. Nobody configured a histogram, and yet it is there, larger than anything else.
</Problem>

<Idea>
The metrics-generator reads every span from Kafka and keeps request, error and duration metrics for each combination of service, span name, span kind and status code, plus the dimensions the lab adds. It also matches client and server spans into service graph metrics. It writes both to Mimir with remote write, under the tenant the spans came from.
</Idea>

## What span metrics count

For every span it receives, the span metrics processor adds one to `traces_spanmetrics_calls_total`, adds the duration to the histogram `traces_spanmetrics_latency`, and adds the span's size to `traces_spanmetrics_size_total`. The labels are the span's `service`, `span_name`, `span_kind` and `status_code`, and any extra dimensions. Because the counter has a `status_code` label, an error rate is a ratio of two rates: the RED method from traces, with no line of metrics code in the services.

This lab adds three things in `lgtm/lab/helm/tempo/values.yaml`. `service.namespace` is an extra dimension. A mapping copies `service.name` into a label `service_name`, so span metrics use the same label as every other signal of the lab. And external labels `cluster="lgtm-lab"` and `source="tempo"` mark where the series came from.

## Why the histogram is the largest metric

A histogram is one series per bucket for each label combination, plus `_sum` and `_count`. On the lab on 2026-11-14, `traces_spanmetrics_calls_total` had 126 series, one per combination of the labels. The running configuration has 12 bucket bounds, from 0.002 to 4.1 seconds, and Prometheus adds `+Inf`, so the histogram had 126 × 13 = 1,638 bucket series. Tempo's configuration page lists two more bounds, up to 16.384 seconds, as the default; the running Tempo 3.1.1 uses the shorter list.

Every dimension multiplies this. Add an attribute with 50 values as a dimension, and the 126 combinations can become thousands, each times 13. The span name is usually the largest driver: a name that contains an ID creates a new series for every request. That is why the metrics-generator has limits on active series and on values per label, and folds the excess into an overflow series instead of dropping data.

## Service graphs

The service graphs processor waits up to 10 seconds for both halves of a call: a client span and the server span whose parent it is. Each matched pair counts in `traces_service_graph_request_total` with the labels `client` and `server`, and in the histograms `traces_service_graph_request_client_seconds` and `traces_service_graph_request_server_seconds`. Calls to a database or a service that sends no spans are matched by attributes such as `db.system.name`, so they still appear as a node. Grafana's service graph and node graph views draw these metrics.

<Question id="q-m13-s08" answer="b">
A team adds the span attribute `customer.id`, with about 20,000 values, as a span metrics dimension. What happens to `traces_spanmetrics_latency_bucket`?

- Nothing, because the metrics-generator only uses resource attributes as dimensions

  Dimensions are searched in span and resource attributes, so a span attribute is used.

- Its series multiply by up to 20,000, times every bucket, until the generator's limits fold the excess into overflow series

  Each value of a dimension is a new label combination, and each combination has one series per bucket.

- It gains one label but keeps the same number of series

  A label with many values creates a series for each value; the number of series grows with it.

- Tempo refuses spans that carry the attribute until the dimension is removed

  The generator never refuses spans for this. It writes more series, up to its active series limit.
</Question>
