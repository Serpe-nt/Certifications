<Problem>
Checkout's p95 jumps from about 15 ms to many seconds, and some users get errors after exactly 15 seconds. CPU and memory of every pod look normal, nothing restarts, and no service logs an error about it. Five services sit between the button and the database, and each one is slower by the same amount.
</Problem>

<Idea>
Follow the time, not the errors. Find slow traces, follow each one down to the span whose time is its own, then ask TraceQL what that span was doing and what else ran on the same table. Here the span that waits is a database query, and the reason is a lock that another transaction holds.
</Idea>

## From a percentile to slow traces

Start with a number that shows the problem, then turn it into traces. A TraceQL metrics query gives the percentile per service; a selector with `span:duration` gives the slow spans themselves. Choose the deepest service that is slow: when product-catalog's server spans take seconds, checkout's do too, because checkout waits for them. On the lab, product-catalog's 95th percentile went from 7 to 11 ms to between 15 and 28 seconds within a minute of the flag.

## Down the tree to the span that waits

A slow span with a slow child is waiting for that child. The child operator finds the slow children of the slow spans in one query: `{ resource.service.name = "product-catalog" && span:kind = server && span:duration > 1s } > { span:duration > 1s }`. On the lab it returned `astronomy-db` spans of 12 to 28 seconds, each an ordinary `SELECT` on `catalog.products`. A `SELECT` by primary key that takes seconds is not slow work; it is waiting.

The rest of the trace tells the same story from above. In one checkout on the lab, product-catalog's `GetProduct` took 27.2 seconds and the frontend waited all of it. The shop's Envoy proxy, `frontend-proxy`, gave up after 15.0 seconds and marked its span as an error. That is where the users' errors come from: a timeout that turns slowness into failure two services above the cause.

## What held the table

A query waits on a lock when another transaction holds it, so look for statements on the same table: `{ span.db.query.text =~ "LOCK.*" }`. On the lab it found `LOCK TABLE catalog.products IN ACCESS EXCLUSIVE MODE`, as a trace of its own, started by product-catalog with no request above it. Its span lasted half a millisecond: taking a lock is quick. The transaction that took it kept it for 30 seconds, and that time belongs to no span, so a search on `span:duration` would never find the culprit. The SQL text does. While the lock is held, PostgreSQL lets no other transaction even read the table.

<Timeline caption="One cycle of the fault, as the lab showed it">
  <Event at="0 s" title="Lock taken">A background transaction runs LOCK TABLE catalog.products IN ACCESS EXCLUSIVE MODE.</Event>
  <Event at="0 to 30 s" title="Reads wait">Every SELECT on the table waits; product-catalog, checkout and the frontend slow down.</Event>
  <Event at="15 s" title="Proxy gives up">Envoy ends waiting requests with an error; the services below keep waiting.</Event>
  <Event at="40 s" title="Again">A ticker checks the flag every 10 seconds and takes the lock again; the log line repeated every 40 seconds.</Event>
</Timeline>

## Confirm the size, then stop

Go back to aggregates. `quantile_over_time(span:duration, .95)` for product-catalog's server spans shows the waits as values of many seconds per minute, and turning the flag off brings it back to milliseconds within a minute. A trace explained one request; the metric shows that the pattern covered all of them.

<InLab>
The flag is `productCatalogLockContention` on the flag screen. Product-catalog checks it every 10 seconds and logs `lock contention scenario active` each time it takes the lock. Its database spans are named `astronomy-db`, after the database service, with the SQL in `db.query.text`.
</InLab>

<Trap>
The deepest slow span is not always the culprit. A database span that waits shows where the time went, not why; look for what held the resource it waited for, even if that took no time at all.
</Trap>

<Do>
1. Open the <LabLink to="flags" path="/feature">flag screen</LabLink> and check that every flag is off. Set `productCatalogLockContention` to `on` and save. Note the time.
2. Wait two minutes. In <LabLink to="grafana" path="/explore">Explore</LabLink>, data source `tempo`, query type **TraceQL**, time range **Last 5 minutes**, run: <Query lang="traceql">{`{ resource.service.name = "product-catalog" && span:kind = server } | quantile_over_time(span:duration, .95)`}</Query> The 95th percentile is now seconds instead of milliseconds.
3. Find slow product-catalog server spans: <Query lang="traceql">{`{ resource.service.name = "product-catalog" && span:kind = server && span:duration > 1s }`}</Query> Open one trace and follow it up: the frontend waits as long, and `frontend-proxy` may stop at 15 seconds with an error.
4. Find the slow children of those spans and what they ran: <Query lang="traceql">{`{ resource.service.name = "product-catalog" && span:kind = server && span:duration > 1s } > { span:duration > 1s } | select(span.db.query.text)`}</Query> The slow child is `astronomy-db`, a `SELECT` on `catalog.products`.
5. Look for a lock statement in the same minutes: <Query lang="traceql">{`{ span.db.query.text =~ "LOCK.*" } | select(span.db.query.text, span:duration)`}</Query> Each result is a short trace of product-catalog with one span.
6. Read the `db.query.text` of that span. Paste the two words of the lock mode, before `MODE`, in the check below.
7. Go back to the flag screen, set `productCatalogLockContention` to `off` and save. Wait two minutes and run the query of action 2 again with the time range **Last 2 minutes**: the percentile is back to milliseconds.
</Do>

<Done>
You went from a percentile to the slow spans, down to the database query that waited, found the lock statement that held the table, and switched the flag off.
</Done>

<Trap practice>
Switch the flag off when you are done, and check on the flag screen that it shows `off`. Other people practise in the same lab, and a flag left on spoils every number they read. If nothing gets slow within two minutes of switching it on, product-catalog may not have picked up the flag: tell whoever runs the lab rather than leaving it on.
</Trap>

<Question id="q-m13-s12" answer="b">
A product-catalog server span took 12 s. Its only child, a database span running `SELECT ... WHERE p.id = $1`, took 11.9 s. What does that tell you?

- Product-catalog itself spent 11.9 s of CPU on the request

  The child holds almost all the time, so product-catalog's own work was 0.1 s.

- The database query waited, and something made it wait

  A lookup by primary key normally takes milliseconds. Seconds point to waiting, such as for a lock.

- The query plan is wrong and needs an index on p.id

  A missing index would slow every lookup a little, not make some of them take seconds.

- The trace is broken, because a child cannot be almost as long as its parent

  A parent that only waits for one child is almost exactly as long as that child.
</Question>
