<Problem>
The namespace `tempo` has twelve pods. Most of their names end in a component you have not met in Tempo before: block-builder, live-store, backend-scheduler. Tutorials from before 2026 talk about ingesters and a compactor, and neither is here. Before you can debug a missing trace, you must know which pod handled it.
</Problem>

<Idea>
Tempo 3 splits writing and reading. Distributors write spans to Kafka; block-builders turn them into blocks in object storage, while live-stores keep the last minutes queryable. Queries go through the query frontend to queriers, which read both the live-stores and the blocks.
</Idea>

## The write path

A span enters at a distributor, over OTLP. The distributor checks the ingestion rate limit of the tenant, hashes the trace ID to pick a partition, and writes the spans to Kafka. It answers the sender only when Kafka has acknowledged the write, so a `200` means the spans are safe in Kafka. All spans of one trace go to the same partition.

Three consumer groups read the topic, each at its own pace. The block-builders read in cycles: each cycle they collect what arrived, write it as Parquet blocks to object storage, and commit their Kafka offset. A trace whose spans arrive across two cycles ends up in two blocks; queries put it back together. The metrics-generator reads the same spans to make metrics, as step 8 shows.

Kafka plays the same role here as for Mimir in module m11 step 2: a durable log between the component that receives data and the components that store it. Because Kafka keeps the data safe, Tempo writes each span once, with no copies across pods.

<Flow caption="Write path in this lab">
  <Stage title="Distributor" kicker="2 pods">OTLP in, ingestion limits, hash by trace ID.</Stage>
  <Stage title="Kafka" kicker="topic tempo-traces">Two partitions, three consumer groups.</Stage>
  <Stage title="Block-builder" kicker="2 pods">One partition each, Parquet blocks every cycle.</Stage>
  <Stage title="Object store" kicker="bucket tempo-traces">Blocks for 48 hours.</Stage>
</Flow>

## The read path

Between the moment Kafka has a span and the moment a block-builder has flushed it, only the live-stores can answer for it. A live-store reads its partition from Kafka, assembles traces in memory, and after a few idle seconds writes them to a local write-ahead log in Parquet, where they become searchable. It keeps them as local blocks for some minutes after that.

A query reaches the query frontend first. The frontend cuts it into jobs by time and by data size, puts the jobs in a queue per tenant, and merges what comes back. Queriers do the jobs: for recent data they ask the live-store that owns each partition, and for older data they read blocks from object storage; when they look up a trace ID, bloom filters let them skip blocks that cannot hold it. In this lab the query frontend's setting `query_backend_after` is 15 minutes: a search over the last 15 minutes reads the live-stores, and older parts of the time range read the blocks.

<Flow caption="Read path in this lab">
  <Stage title="Query frontend" kicker="1 pod">Cuts a query into jobs per tenant.</Stage>
  <Stage title="Querier" kicker="1 pod">Runs jobs on recent and stored data.</Stage>
  <Stage title="Live-store and blocks" kicker="2 pods + bucket">Recent traces from memory, older ones from Parquet blocks.</Stage>
</Flow>

## The maintenance pair

Block-builders write many small blocks. The backend scheduler, a single pod, creates jobs: compaction jobs that merge small blocks into larger ones, and retention jobs that delete blocks older than the retention period. Backend workers ask the scheduler for jobs and run them. Together they replace the compactor of Tempo 2, and step 10 looks at them closely. The last pod, `tempo-memcached`, is a cache that the queriers and the frontend use for bloom filters, Parquet footers and search results.

All Tempo pods run the same image, `grafana/tempo:3.1.1`. The flag `-target` decides which component a process is, and each component serves its own metrics on `/metrics` at port 3200. Most names start with `tempo_` or `tempodb_`.

</InLab>

<Question id="q-m13-s02" answer="a">
A block-builder pod is stopped for ten minutes. What happens to a trace sent during those ten minutes?

- Search still finds it through a live-store, and its block is written once the block-builder catches up

  Live-stores read Kafka on their own, so recent data stays queryable. The block-builder resumes from its last committed offset.

- The distributor refuses the spans until the block-builder is back

  The distributor writes to Kafka and answers when Kafka has the data. It does not wait for any consumer.

- The trace is lost, because no component wrote it to object storage

  Kafka keeps the spans. The block-builder reads them from its committed offset when it starts again.

- The live-store writes the block to object storage in place of the block-builder

  In microservices mode only block-builders write the blocks that are kept. Live-stores only serve recent data.
</Question>
