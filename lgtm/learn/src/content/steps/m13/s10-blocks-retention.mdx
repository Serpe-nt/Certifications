<Problem>
The lab promises 48 hours of traces. A block-builder writes a few new blocks every five minutes, so after two days a tenant would have hundreds of small blocks, and a search over the whole range would open every one. Something must merge them, and something must delete them on time.
</Problem>

<Idea>
A Tempo block is a Parquet file of whole traces plus the metadata that makes it findable. The backend scheduler hands out compaction jobs that merge small blocks of the same hour and retention jobs that delete blocks past the retention period; backend workers run them. A block is visible to queries only once its `meta.json` exists.
</Idea>

## What a block-builder writes

Each cycle, a block-builder writes one or more blocks per tenant and partition. A block is a folder `TENANT/BLOCKID/` in the bucket. `data.parquet` holds the spans, and `meta.json` holds the block's time range, tenant and number of traces. Bloom filters and an index let a querier find a trace ID without reading the data. The block-builder writes `meta.json` last: until it exists, no querier sees the block, so a crash in the middle leaves nothing half visible. The IDs of its blocks are derived from the partition, tenant and Kafka offsets, so a retry after a crash writes the same block again instead of a second copy.

## Why Parquet

Parquet stores data by column. A TraceQL condition such as `span.http.response.status_code = 500` reads the column of that attribute, not whole traces. Each row of a Tempo block is one trace; its spans are nested inside it, under their resource and scope. A few fields, such as `service.name`, the span name, kind, status and duration, have columns of their own. Other attributes sit in a generic attribute map that is slower to scan, unless an operator promotes them to dedicated columns. Tempo 3.1 writes the format vParquet5 by default; vParquet4 can still be chosen, and vParquet3 can no longer be written.

## Compaction and retention

The backend scheduler is a single pod. Every cycle it looks at each tenant's blocklist and creates compaction jobs: groups of two to four blocks of the same one-hour window and level, smallest first. A backend worker merges each group into one block and marks the inputs compacted by renaming their `meta.json` to `meta.compacted.json`. The old blocks stay readable for one more hour, because other components only learn about the new block when they next poll the bucket, every five minutes.

Retention is a job of its own, created once an hour: it deletes blocks whose data is older than the retention period. The period is `block_retention`, 48 hours in this lab. A trace is therefore kept between 48 and about 49 hours.

<Timeline caption="Life of a block in this lab">
  <Event at="0 to 5 min" title="Built">A block-builder flushes the cycle's spans as a level-0 block.</Event>
  <Event at="minutes later" title="Compacted">A backend worker merges it with others of the same hour.</Event>
  <Event at="+1 h" title="Old copy deleted">The compacted inputs are removed after one hour.</Event>
  <Event at="48 h" title="Deleted">The next hourly retention job removes the block.</Event>
</Timeline>

<Question id="q-m13-s10" answer="c">
A query in Tempo that filters on `span.customer.tier` is slow, while a query on the span name over the same range is fast. What change helps the first one most?

- Lower the block retention so that fewer blocks exist

  Retention removes old data. It does not change how an attribute is stored in the blocks that remain.

- Run more backend workers so compaction finishes sooner

  Fewer blocks help every query a little. The attribute is still read from the generic map in each block.

- Add `customer.tier` as a dedicated column of scope span

  A dedicated column stores the attribute in its own Parquet column, so the query stops scanning the generic attribute map.

- Switch the block format back to vParquet3

  Tempo 3.1 refuses to write vParquet3, and the older format has fewer dedicated columns, not more.
</Question>
