<Problem>
Product-catalog serves the shop's pages and the checkout. Its server spans are fast on average, but you want to know how it behaves only when checkout calls it. A selector on product-catalog alone mixes both callers. You need to ask for product-catalog spans that sit below a checkout span in the same trace.
</Problem>

<Idea>
Structural operators relate two span sets of the same trace: one side must be an ancestor, a parent, a child, a descendant or a sibling of the other. They return the spans of the right side, unless the operator starts with an ampersand. Aggregates after a pipe then keep or drop a whole trace by a number over its spans.
</Idea>

## Descendant, child, sibling

`{A} >> {B}` returns spans matching B that have an ancestor matching A anywhere above them. `{A} > {B}` is stricter: A must be B's direct parent. `{A} << {B}` and `{A} < {B}` turn this around and return the ancestors or parents. `{A} ~ {B}` returns spans matching B that have a sibling matching A, a span with the same parent.

The difference between `>>` and `>` matters in the shop. Checkout's server span `PlaceOrder` calls payment and empties the cart directly, but it reaches cart and product-catalog through an internal span, `prepareOrderItemsAndShippingQuoteFromCart`. So `{ resource.service.name = "checkout" && span:kind = server } > { span:kind = client }` returns only the `Charge` and `EmptyCart` calls. On the lab, `{ resource.service.name = "frontend" && span:kind = server } > { resource.service.name = "checkout" }` returned no trace at all, while the same query with `>>` found checkout below the frontend in every checkout trace.

<Compare caption="One relation, three operators, on a checkout trace">
  <Col title="A >> B" hot>B anywhere below A. Finds product-catalog below checkout.</Col>
  <Col title="A > B">B directly below A. Misses calls made from an internal span in between.</Col>
  <Col title="A &>> B">Like >>, but returns the spans of A and of B.</Col>
</Compare>

## Both sides, and the experimental negations

A structural operator returns the right side. When you want both, the checkout span and the product-catalog spans below it, use the union form: `&>>`, `&>`, `&<<`, `&<` and `&~`. The negated forms `!>>`, `!>`, `!<<`, `!<` and `!~` find spans that do not have the relation. Tempo marks them experimental, because they can return false positives. One is still useful: `{ status = error } !< { status = error }` returns error spans that have no direct child in error, the place where a chain of errors starts.

## Aggregates and groups

After a pipe, `count()`, `avg()`, `min()`, `max()` and `sum()` work on the span set of each trace and keep the trace when the comparison is true. `{ trace:rootName = "user_checkout_multi" } | count() > 100` keeps multi-item checkouts with more than 100 spans; on the lab one had 104. `{ resource.service.name = "product-catalog" && span:kind = server } | avg(span:duration) > 1ms` keeps traces whose catalog calls average over a millisecond, and the result shows the average.

`by()` splits a trace's span set into groups first. `{ resource.service.name = "cart" } | by(span:name) | count() > 4` returns, per trace, the groups of cart spans with the same name that appear more than four times; in checkout traces that is the Valkey calls. Remember that all of this is per trace. Counting across all traces over time is the job of TraceQL metrics, step 7.

<Trap practice>
A structural query on a broad left side, such as `{ } >> { status = error }`, makes Tempo read the structure of every trace in the range. Keep the time range short, and put the most selective conditions in the selectors.
</Trap>

<Question id="q-m13-s06" answer="a">
Which query returns the database spans of product-catalog, but only in traces where checkout called product-catalog?

- `{ resource.service.name = "checkout" } >> { resource.service.name = "product-catalog" && span:name = "astronomy-db" }`

  The database spans are on the right side, and >> requires a checkout span anywhere above them.

- `{ resource.service.name = "checkout" } > { resource.service.name = "product-catalog" && span:name = "astronomy-db" }`

  The child operator needs a checkout span as the direct parent. The parent of a database span is product-catalog's own server span.

- `{ resource.service.name = "checkout" } && { span:name = "astronomy-db" }`

  This only asks that both exist in the trace, including database calls made for another caller in the same trace.

- `{ resource.service.name = "product-catalog" && span:name = "astronomy-db" } >> { resource.service.name = "checkout" }`

  The sides are reversed: this asks for checkout spans below a database span, which never happens.
</Question>
