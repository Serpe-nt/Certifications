<Problem>
Nine more charts, each with hundreds of values: three storage backends in microservices mode, two collectors, Prometheus, Grafana, the lab's own glue chart and a 13-service shop. Installed in the wrong order, the shop's first telemetry has nowhere to go; installed without reading, you will not know why Loki deletes logs after two days.
</Problem>

<Idea>
`make lab` installs the nine releases in a fixed order and prints the addresses and the lab seed at the end. Read a few values of each first, so you know what you are getting. Afterwards `make lab TAGS=<release>` installs or upgrades one of them alone.
</Idea>

## Values worth reading before you install

- Loki (`helm/loki/values.yaml`): `deploymentMode: Distributed` runs Loki in microservices mode, `auth_enabled: true` turns on tenants, and `retention_period: 48h` is why logs older than two days disappear.
- Mimir (`helm/mimir/values.yaml`): `ingest_storage.enabled: true` sends every write through Kafka, and `compactor_blocks_retention_period: 7d` keeps metrics for a week.
- Prometheus (`helm/kube-prometheus-stack/values.yaml`): `retention: 1d` keeps only a day on Prometheus itself, and its `remoteWrite` sends everything to Mimir with the header `X-Scope-OrgID: prom`.
- The Collector (`helm/otel-gateway/values.yaml`): `mode: deployment` and `replicaCount: 2` run it as a gateway of two pods, not as an agent on every node.
- Grafana (`helm/grafana/values.yaml`): `admin.existingSecret: grafana-admin` reads the admin password from a Secret the playbook makes, so no password is in the values.

## make lab, then one release at a time

`make lab` runs the roles in the order of step 15 and waits for each release. On the first run it also creates the Grafana admin password and the lab seed, and it ends by printing the addresses, the seed and where the password is. On the owner's cluster the first run took about nine minutes. A second run reports `changed=0`.

To change one release later, edit its values file and run `make lab TAGS=loki`, or another tag: `prometheus`, `mimir`, `tempo`, `otel-gateway`, `alloy`, `grafana`, `glue` or `shop`.

## Reading the result with Helm

`helm list -A` now shows 17 releases: the 6 of the platform, the 9 of `make lab`, and two more in `alloy`, `k8s-monitoring-alloy-logs` and `k8s-monitoring-alloy-singleton`. Those two come from the Alloy Operator, which the `k8s-monitoring` chart installs: it runs each Alloy instance from the Alloy Helm chart, so each instance is a release too. `helm get metadata loki -n loki` shows the chart, its version and `APPLY_METHOD: server-side apply`.

<Question id="q-m01-s17" answer="a">
You changed one value in `lgtm/lab/helm/grafana/values.yaml`. Which command applies it and leaves every other release alone?

- `make lab TAGS=grafana`

  The tag runs only the Grafana role, which upgrades that one release.

- `make lab`

  It works, but it walks through every release; the others report no change.

- `make reset`, then `make lab`

  A reset uninstalls every release and deletes their data, far more than one value needs.

- `helm upgrade grafana grafana-community/grafana -n grafana`

  It bypasses the lab's files: without --version it takes the newest chart, and the next make lab puts back what the files say.
</Question>
