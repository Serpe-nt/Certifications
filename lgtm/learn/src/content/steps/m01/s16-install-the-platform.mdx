<Problem>
The stack needs volumes, an S3 store, a way in for the browser, Kafka and certificates, and none of that exists on the empty cluster. Six charts will change your cluster deeply. Installing them without reading their values is how a lab ends up with three default StorageClasses or a disk that fills in a week.
</Problem>

<Idea>
`make platform` installs six Helm releases in order: metrics-server, cert-manager, Envoy Gateway, Longhorn, the RustFS S3 store and the Strimzi Kafka operator with its Kafka cluster. Before you run it, read two or three values of each; after it, check each release with `helm list`, `helm get values` and kubectl.
</Idea>

## Values worth reading before you install

Each values file explains its choices in comments. Three releases set things you will meet again:

- Longhorn (`helm/platform/longhorn/values.yaml`): `persistence.defaultClass: true` makes `longhorn` the default StorageClass; `defaultReplicaCount: 2` keeps two copies of every volume on two workers; `storageOverProvisioningPercentage: 200` lets thin volumes add up to twice the disk, because Longhorn keeps 30% of each disk in reserve and the lab's volumes would not fit otherwise.
- RustFS (`helm/platform/rustfs/values.yaml`): `dataStorageSize: 25Gi` sizes the one volume that holds every metric block, log chunk and trace block of the lab.
- metrics-server (`helm/platform/metrics-server/values.yaml`): `--kubelet-insecure-tls`, because the kubelets of a kubeadm cluster serve self-signed certificates. A lab simplification, not a production setting.

## One command, in order

`make platform` runs `ansible/playbooks/platform.yml`. It first moves CoreDNS and the Calico controllers off the control-plane node, then installs the add-ons in order. It downloads the pinned Helm, kubectl and two other tools into `lgtm/lab/.bin` as well. The first run on the owner's cluster took about 13 minutes; a second run changes nothing.

## Checking with Helm

`helm list -A` now shows the six releases, each `deployed` at revision 1 or higher, with the chart versions of `versions.yml`. `helm get values <release> -n <namespace>` prints the values Ansible passed, so you can compare them with the files you read. `make platform-check` then proves the add-ons work: a volume keeps its data, the S3 store answers, the gateway routes through `lb`, and a message goes through Kafka.

<Question id="q-m01-s16" answer="b">
A colleague asks why the lab's Longhorn allows volumes to add up to twice the disk size. What is the reason given in its values file?

- Each volume is written twice, so the disk must count double

  Two copies need space on two workers, but that is not what the over-provisioning setting is for.

- Volumes are thin, so they use only what is written, and the 30% reserve would not leave room otherwise

  The values file sets 200% because thin volumes rarely fill and the reserve shrinks the usable space.

- Kafka needs twice its volume size for its logs

  Kafka's volumes are sized on their own; the setting applies to every Longhorn disk.

- Longhorn needs the setting to make it the default StorageClass

  The default class comes from persistence.defaultClass, a separate value.
</Question>
