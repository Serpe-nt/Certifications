<Problem>
The lab has three writers into Mimir: Prometheus, the collector gateway and Tempo. Each one speaks a different protocol or sends as a different tenant, and you have never seen what their samples look like on arrival. Before you change one of them, you want to send a sample of your own and watch what Mimir makes of it.
</Problem>

<Idea>
Mimir's distributor takes Prometheus remote write on `/api/v1/push` and OTLP on `/otlp/v1/metrics`, and every request names its tenant in the header `X-Scope-OrgID`. Remote write arrives as Prometheus series already. OTLP is translated: dots become underscores, `service.name` becomes the label `job`, and the other resource attributes go to `target_info` unless you promote them.
</Idea>

## Two protocols, one front door

A distributor accepts Prometheus remote write, in version 1 and in version 2, which Mimir 3.0 lists as experimental. It also accepts OTLP over HTTP and the Influx line protocol. Remote write is protocol buffers compressed with snappy, as module m03 showed. OTLP over HTTP is protocol buffers too, and the OTLP specification also defines a JSON form of the same messages.

The tenant goes in a header on every request. Prometheus sets it with `headers` in its `remote_write` entry. An OpenTelemetry Collector sets it with `headers` on its `otlp_http` exporter, whose endpoint is Mimir's `/otlp`: the exporter adds `/v1/metrics` itself. For a Collector, Mimir's documentation recommends OTLP over remote write.

## What OTLP turns into

An OTLP metric is not a Prometheus series yet. Mimir follows the OpenTelemetry rules for the translation. Dots in metric and attribute names become underscores, so `http.status_code` becomes `http_status_code`. The resource gives two labels to every series: `job` from `service.namespace` and `service.name` joined by a slash, or from `service.name` alone, and `instance` from `service.instance.id`. All other resource attributes go to one extra series, `target_info`, which you join in a query when you need them.

A tenant can also promote chosen resource attributes, so they become labels on every series. Mimir's documentation marks that option experimental.

<Flow caption="One OTLP data point on its way to a series">
  <Stage title="Resource" kicker="service.name=writer">Becomes job="writer"; other attributes go to target_info.</Stage>
  <Stage title="Data point" kicker="attribute n=3">Becomes the label n="3".</Stage>
  <Stage title="Series" kicker="In tenant learn-m11" hot>learn_m11_heartbeat with job, n and any promoted labels.</Stage>
</Flow>

<InLab>
Prometheus remote-writes to `http://mimir-gateway.mimir.svc/api/v1/push` as tenant `prom`, with exemplars and native histograms switched on. The collector gateway's exporter `otlp_http/mimir` sends to `/otlp` as tenant `lab`, and Mimir promotes `cluster`, `service.name` and a few Kubernetes attributes for that traffic. Tempo's metrics-generator remote-writes its span metrics as tenant `lab` too.
</InLab>

<Trap>
Do not look for `service_name` to find an OTLP sender in a plain Mimir. The standard label is `job`, built from the service's namespace and name. This lab has `service_name` as well only because it promotes `service.name`.
</Trap>

<Trap practice>
If the query returns an empty result, check the header first: without `X-Scope-OrgID: learn-m11` you are asking another tenant. If the log shows `status 404`, the path is wrong: the pod posts to `/otlp/v1/metrics`, while a Collector's exporter is configured with `/otlp` only.
</Trap>

<Remember>
Remote write goes to `/api/v1/push`, OTLP to `/otlp/v1/metrics`, both with `X-Scope-OrgID`. OTLP gets translated: underscores for dots, `job` and `instance` from the resource, the rest in `target_info`.
</Remember>

<Question id="q-m11-s06" answer="a">
An OTLP sender sets the resource attributes `service.namespace=shop` and `service.name=cart`. Nothing is promoted. Which label does Mimir give every metric of this sender?

- `job="shop/cart"`

  The OTLP translation joins the service namespace and name with a slash and stores them as `job`.

- `service_name="cart"`

  That label exists only when `service.name` is promoted. The standard label is `job`.

- `job="cart"`

  `service.name` alone becomes `job` only when the service namespace is empty.

- `namespace="shop"`

  Resource attributes that are not promoted go to `target_info`, not onto every series.
</Question>
