<Problem>
Steps 2 to 4 drew Mimir as boxes and arrows. On the cluster you see fourteen pods with names such as `mimir-query-scheduler-86b8988957-lpmc9`. Before you can debug Mimir, you must know which box each pod is and where it tells you what it is doing.
</Problem>

<Idea>
Every Mimir pod except the gateway runs the same image, and its `-target` flag says which component it is. Each component serves its own metrics on `/metrics`, and most of their names start with `cortex_`. One metric per component is enough to see it working.
</Idea>

## One image, many roles

The pods of the namespace `mimir` come from the chart's Deployments and StatefulSets. The stateless components, the distributors, queriers, query-frontend, query-scheduler and ruler, are Deployments, so their pods carry a random suffix. The stateful ones keep data on a volume and are StatefulSets with numbered pods: the ingesters keep their WAL and local blocks, the store-gateway its index-headers, the Alertmanager its alert state, and the compactor uses its volume as working space.

The gateway is the odd one out. It is an nginx server that the chart puts in front of everything: it routes `/api/v1/push` and `/otlp/v1/metrics` to the distributors, `/prometheus` to the query-frontend, and the rule and alert paths to the ruler and the Alertmanager.

## Why the ingester's name matters

With ingest storage, an ingester finds its Kafka partition in its own name. Mimir takes the number after the last hyphen of the instance ID, which is the pod's hostname: `mimir-ingester-0` reads partition 0. A StatefulSet keeps the name across restarts, so an ingester always comes back to the same partition and the same consumer group.

## Each component reports on itself

Every component serves `/metrics` on its HTTP port, 8080 in this chart. Mimir's own metrics start with `cortex_`, not with `mimir_`, so search for that prefix. The ones below answer the first question you would ask each component.

<Compare caption="One metric per component, and what it answers">

  <Col title="Read side">query-frontend: `cortex_query_frontend_queries_total`. query-scheduler: `cortex_query_scheduler_connected_querier_clients`. store-gateway: `cortex_bucket_store_blocks_loaded`.</Col>
  <Col title="Background" hot>compactor: `cortex_compactor_runs_completed_total`. ruler: `cortex_ruler_managers_total`, tenants with rules. Alertmanager: `cortex_alertmanager_tenants_owned`.</Col>
</Compare>

<Trap practice>
If `kubectl get --raw` answers "You must be logged in to the server", Mimir itself returned 401, and kubectl reads that as a sign-in problem. Paths that serve tenant data, such as `/prometheus/...`, need the header `X-Scope-OrgID`; `/metrics` does not, so check the path for a typing error.
</Trap>

<Remember>
One binary, one `-target` per pod. Stateful components are StatefulSets, and an ingester's partition is the number at the end of its name.
</Remember>

<Question id="q-m11-s05" answer="b">
A cluster runs ingest storage. The ingester StatefulSet is scaled from 3 to 4 replicas. Which partition does the new pod `mimir-ingester-3` read?

- None, because partitions are shared out by the distributors

  Distributors choose a partition for each series. Ingesters find their own partition from their name.

- Partition 3, taken from the number at the end of its instance ID

  Mimir reads the partition number from the instance ID with the pattern of a hyphen and digits at the end.

- Partition 0, because new ingesters start from the first partition

  Each ingester reads the partition that its own number names. Partition 0 belongs to `mimir-ingester-0`.

- All partitions, until the ring is balanced

  An ingester owns exactly one partition. It never reads all of them.
</Question>
