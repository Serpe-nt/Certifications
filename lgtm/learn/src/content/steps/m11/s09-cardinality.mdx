<Problem>
Tenant `lab` uses 5,900 of its 500,000 series today. A colleague wants to add a new label to the span metrics, and you must say what it will cost. First you need to know which metrics hold the series now, and which of their labels multiply them.
</Problem>

<Idea>
Mimir's cardinality API answers both questions: it counts the values of every label name and the series behind each value of a label, and it lists the active series a selector matches. It is off by default and switched on per tenant; this lab has it on for tenant `lab`. PromQL gives the same answers with a count per metric name, and it works where the API is off.
</Idea>

## The cardinality API

Mimir's query-frontend offers three endpoints for this work. `/prometheus/api/v1/cardinality/label_names` counts the values of every label name. `/prometheus/api/v1/cardinality/label_values?label_names[]=NAME` counts the series per value of the named labels, and a `selector` narrows it to one metric. `/prometheus/api/v1/cardinality/active_series?selector=...` lists the active series that match. They read the ingesters only, so they describe recent data, and they can count all series in memory or only the active ones, those with a sample in the last 20 minutes.

The label `__name__` holds the metric name, so `label_values` for `__name__` lists the metrics by series count. That is where the question "what is expensive" starts: in Mimir the series count is also the number the tenant's limit is checked against.

All three endpoints are off by default. The switch is the limit `cardinality_analysis_enabled`, which you can set for all tenants or for one tenant in the runtime overrides.

## Find the label that multiplies

Module m02 showed that every label multiplies the series of a metric. The top metric is usually a histogram, because every bucket is its own series. Count the distinct values of each of its labels. The product of the counts is the most the metric can reach; the real number is lower, because not every combination occurs. The label with the most values, or the one that is still growing, is where a new label or a change of instrumentation pays off first.

## Without the API: PromQL

Where the API is off, one PromQL query finds the big metrics by counting the series per metric name:

<Query lang="promql">{`topk(10, count by (__name__) ({__name__=~".+"}))`}</Query>

The selector matches every series of the tenant at the query's time, so run it on one tenant at a time and not on a huge one at peak hours. `count(count by (LABEL) (METRIC))` then counts the values of one label. For a whole tenant, the distributors' page `/distributor/all_user_stats` from step 7 already gives the total.

<InLab>
Since 2026-11-14, tenant `lab` has `cardinality_analysis_enabled: true` in the runtime overrides of the Mimir release, and Mimir picked it up without a restart. Tenant `prom` and the practice tenants keep the default, so the API answers them `cardinality analysis is disabled for the tenant`.
</InLab>

With `count_method=inmemory`, two calls of the cardinality API a minute apart can differ a lot, because an ingester may have cut a block between them. Compare numbers with `count_method=active`, which counts only series with a recent sample.
</Trap>

</Done>

<Trap practice>
Keep the query of action 6 in double quotes, as written, so that the shell fills in `$l`. In single quotes, Mimir receives the text `$l` itself and answers with a parse error. The API calls work only as tenant `lab`: as `prom`, Mimir answers that cardinality analysis is disabled.
</Trap>

<Remember>
The cardinality API counts series per label and per value where `cardinality_analysis_enabled` is on, as for tenant `lab` here. Without it, `topk(10, count by (__name__) (...))` finds the big metrics and `count(count by (LABEL) (...))` finds the label that multiplies them.
</Remember>

<Question id="q-m11-s09" answer="b">
You call `/prometheus/api/v1/cardinality/label_names` on a Mimir tenant and get `cardinality analysis is disabled for the tenant`. What turns the endpoint on for this tenant only?

- Restarting the query-frontend with a much higher query limit

  The endpoint is switched by a limit, not by query size or a restart.

- A runtime override with `cardinality_analysis_enabled: true`

  It is a per-tenant limit, so an override for that tenant switches it on, and the runtime configuration is reloaded without a restart.

- Sending the header `X-Scope-OrgID` with two tenants

  Several tenants in one header need tenant federation, and the API stays off.

- Querying `/distributor/all_user_stats` first

  That page shows totals per tenant. It does not change any setting.
</Question>
