<Problem>
Tenant `lab` uses 5,700 of its 500,000 series today. A colleague wants to add a new label to the span metrics, and you must say what it will cost. First you need to know which metrics hold the series now, and which of their labels multiply them.
</Problem>

<Idea>
Find the big metrics with one PromQL query: count the series per metric name and keep the top ones. Then count the values of each label of the biggest metric to see which label multiplies it. Mimir also has a cardinality API that does this per label, but it is off by default and needs a per-tenant switch.
</Idea>

## Count series per metric name

Module m02 showed that every label multiplies the series of a metric. In Mimir the series count is also the number the tenant's limit is checked against. The question "what is expensive" therefore starts with a count per metric name:

<Query lang="promql">{`topk(10, count by (__name__) ({__name__=~".+"}))`}</Query>

The selector matches every series of the tenant at the query's time, so run it on one tenant at a time and not on a huge one at peak hours. For a whole tenant, the distributors' page `/distributor/all_user_stats` from step 7 already gives the total.

## Find the label that multiplies

The top metric is usually a histogram, because every bucket is its own series. Count the distinct values of each of its labels with `count(count by (LABEL) (METRIC))`. The product of the counts is the most the metric can reach; the real number is lower, because not every combination occurs. The label with the most values, or the one that is still growing, is where a new label or a change of instrumentation pays off first.

## The cardinality API

Mimir's query-frontend offers three endpoints for this work. `/prometheus/api/v1/cardinality/label_names` counts the values of every label name. `/prometheus/api/v1/cardinality/label_values?label_names[]=NAME` counts the series per value of the named labels. `/prometheus/api/v1/cardinality/active_series?selector=...` lists the active series that match. They read the ingesters only, so they describe recent data, and they can count all series in memory or only the active ones, those with a sample in the last 20 minutes.

All three are off by default. The switch is the limit `cardinality_analysis_enabled`, which you can set for all tenants or for one tenant in the runtime overrides.

<InLab>
The lab leaves `cardinality_analysis_enabled` off, so the API answers `cardinality analysis is disabled for the tenant`. Turning it on for `lab` would be one line under `overrides.lab` in the Mimir values; that is a change to a lab release, so this step uses PromQL.
</InLab>

<Trap>
With `count_method=inmemory`, two calls of the cardinality API a minute apart can differ a lot, because an ingester may have cut a block between them. Compare numbers with `count_method=active`, which counts only series with a recent sample.
</Trap>

<Done>
You found the tenant's biggest metric and the label that multiplies it most, without the cardinality API.
</Done>

<Trap practice>
Keep the query of action 4 in double quotes, as written, so that the shell fills in `$l`. In single quotes, Mimir receives the text `$l` itself and answers with a parse error.
</Trap>

<Remember>
`topk(10, count by (__name__) (...))` finds the big metrics; `count(count by (LABEL) (...))` finds the label that multiplies them. The cardinality API does the same per label, once `cardinality_analysis_enabled` is on.
</Remember>

<Question id="q-m11-s09" answer="b">
You call `/prometheus/api/v1/cardinality/label_names` on a Mimir tenant and get `cardinality analysis is disabled for the tenant`. What turns the endpoint on for this tenant only?

- Restarting the query-frontend with a higher query limit

  The endpoint is switched by a limit, not by query size or a restart.

- Setting `cardinality_analysis_enabled: true` in the tenant's runtime override

  It is a per-tenant limit, so an override for that tenant switches it on, and the runtime configuration is reloaded without a restart.

- Sending the header `X-Scope-OrgID` with two tenants

  Several tenants in one header need tenant federation, and the API stays off.

- Querying `/distributor/all_user_stats` first

  That page shows totals per tenant. It does not change any setting.
</Question>
