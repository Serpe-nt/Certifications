<Problem>
In module m02 you clicked a green diamond on a latency graph and landed in a trace. That diamond came from somewhere. When a team asks why their graphs have no diamonds, you need to know where Mimir keeps exemplars, which senders deliver them, and how to check with one request.
</Problem>

<Idea>
Mimir keeps exemplars per tenant in a fixed-size buffer in the ingesters' memory, when the tenant's limit `max_global_exemplars_per_user` is above 0. The API `query_exemplars` returns them, and each carries a trace ID that Tempo can open. Native histograms are a separate switch: Mimir accepts them, but a sender must send them.
</Idea>

## Where exemplars live

Exemplar storage in Mimir works like Prometheus's: a circular buffer of fixed size, in memory, for all series of a tenant, and new exemplars push out the oldest. The ingesters also write them to the WAL, so a restart keeps them. The size is the tenant limit `max_global_exemplars_per_user`, which is 0 by default, so exemplars are off until you set it. The documentation suggests starting at 100,000 and gives about 100 bytes per exemplar that holds only a trace ID.

Senders must deliver them too. Prometheus needs `send_exemplars: true` in `remote_write`, and it only has exemplars to send when it runs with `--enable-feature=exemplar-storage`. Over OTLP, exemplars travel inside the data points.

## Reading them back

The query-frontend answers `/prometheus/api/v1/query_exemplars` with a selector, a start and an end, like Prometheus's API of the same name. Each answer lists series with their exemplars: the labels of the exemplar, such as a trace ID, plus its value and its time. Grafana uses the same API when you switch Exemplars on in a panel, and the data source maps a label name to a Tempo link.

## Native histograms in Mimir

A classic histogram arrives as one series per bucket plus `_sum` and `_count`, as module m04 showed. A native histogram arrives as one series whose samples hold all of that. Mimir accepts native histograms when `native_histograms_ingestion_enabled` is true, which is the default in this version, and it can cap the buckets per sample with `max_native_histogram_buckets`; the documentation recommends 160. Mimir converts OpenTelemetry exponential histograms into native ones, and it can also store a classic histogram in the native form with custom buckets, which needs no change in the code that measures.

<Question id="q-m11-s12" answer="a">
A team's Grafana panel on Mimir shows no exemplars, although their application exports them and their Prometheus has `send_exemplars: true`. Mimir's limits are at their defaults. What is the first thing to fix?

- Set `max_global_exemplars_per_user` above 0 for the tenant

  Its default is 0, which keeps no exemplars at all. The documentation suggests starting at 100,000.

- Switch on native histogram ingestion

  Native histograms and exemplars are separate features. One does not enable the other.

- Raise the tenant's series limit

  Exemplars have their own limit. More series would not keep any exemplar.

- Turn on the cardinality API

  That API counts series per label. It plays no part in storing exemplars.
</Question>
