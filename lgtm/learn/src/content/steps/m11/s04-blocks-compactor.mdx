<Problem>
Three ingesters each upload a block every two hours for every tenant. After a week, one tenant has hundreds of small blocks in the bucket, and a 7-day query has to open every one of them. Nobody has told Mimir yet when old data may go.
</Problem>

<Idea>
Ingesters cut their in-memory data into two-hour blocks and upload them to the object store. The compactor then merges the blocks of each tenant into fewer, larger ones, keeps a list of them in the bucket index, and deletes blocks that are older than the retention period.
</Idea>

## From memory to a block

A block holds the samples of one tenant for a time range: a `chunks` folder with the samples, usually about 120 per chunk, an `index` of metric names and labels, and a `meta.json` file. It is the same format as a Prometheus block from module m03.

An ingester keeps the newest samples in memory and in its WAL. Every two hours by default it cuts them into a block on its disk and uploads that block to the object store. It keeps its local copy for `-blocks-storage.tsdb.retention-period`, 13 hours by default, so that queriers can still ask it while the store-gateways discover the new block. Then the local copy is removed and the block exists only in the bucket.

## The compactor merges

Each ingester uploads its own block, so one two-hour window of one tenant arrives as one block per ingester. The compactor merges them per tenant in two ways. Vertical compaction joins the blocks of the same time range into one and removes duplicate samples. Horizontal compaction then joins adjacent ranges into larger blocks, by default of 12 hours and then 24 hours. Fewer blocks mean fewer index lookups per query, and a smaller index for the store-gateways to keep.

The compactor also keeps each tenant's bucket index up to date: the list of blocks and deletion marks that queriers and store-gateways read instead of listing the bucket.

## Retention and deletion

Mimir never deletes data by default: `compactor_blocks_retention_period` is 0. When you set it, the compactor removes the blocks that are older than the period, and the setting can differ per tenant. There is no deletion of single series and no Prometheus delete-series API.

Deleting a block takes two steps. The compactor first writes a `deletion-mark.json` into the block, which is a soft delete. After `-compactor.deletion-delay`, 12 hours by default, it removes the block for good. The delay gives queriers and store-gateways time to stop using the block.

<InLab>
The lab keeps metrics for 7 days (`compactor_blocks_retention_period: 7d`) in the bucket `mimir-blocks` of the RustFS store, and shortens the deletion delay to 2 hours. On 2026-11-14 tenant `lab` had one compacted block of level 3, made from 15 ingester blocks: five two-hour windows from each of the three ingesters.
</InLab>

<Trap>
Retention is enforced by the compactor alone. If the compactor is down for days, old blocks stay in the bucket and the bill grows, although every other component is healthy.
</Trap>

<Remember>
Ingesters upload two-hour blocks and keep them locally for a while. The compactor merges them, keeps the bucket index, and deletes what is older than retention, after a deletion mark and a delay.
</Remember>

<Question id="q-m11-s04" answer="a">
A team sets `compactor_blocks_retention_period: 30d` for its tenant. Six weeks later the bucket still holds the tenant's blocks from two months ago. Which component should you check first?

- The compactor, which applies retention and deletes old blocks

  Only the compactor marks and deletes blocks past retention. If it is not running for this tenant, nothing else removes them.

- The ingesters, which upload the blocks

  Ingesters upload blocks and drop their local copies. They never delete blocks from the bucket.

- The store-gateway, which reads the blocks

  The store-gateway reads blocks for queries. It does not decide when a block is deleted.

- The query-frontend, which caches results

  The frontend serves queries. Retention in the bucket is not its job.
</Question>
