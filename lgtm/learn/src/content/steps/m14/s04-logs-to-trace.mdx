<Problem>
A log search for "error" finds one line from checkout at 14:02. It tells you what failed, but not which services the request passed through or where it spent its time. You want the request's trace, and you would rather not copy a trace ID from the line into a TraceQL query by hand.
</Problem>

<Idea>
A derived field in the Loki data source reads a value from each log line and makes a link out of it. The lab has one, named `trace_id`: it takes the line's `trace_id` field and opens that trace in Tempo. A line without a trace ID gets no link, and that tells you something about the code that wrote it.
</Idea>

## How the derived field works

A derived field has a name, a type, a matcher and a target. With the type **Label**, the matcher is a regular expression that Grafana applies to the names of the line's labels, including structured metadata. With the type **Regex in log line**, it applies to the text of the line, and the first capture group becomes the value. The lab's field uses the type Label with the matcher `trace_id`, an internal link to the data source `tempo`, and the query `${__value.raw}`, which is the value itself. The link appears under **Links** in the log details, labelled **Open trace**.

## What breaks it

The derived field only builds a link from the value. Grafana's documentation points out that the trace must already be in Tempo, or the link opens Tempo and finds nothing. If a service wrote the trace ID under another name, such as `traceId`, a matcher of `trace_id` would not see it. And if the trace ID is only inside the text of the line, a field of type Label finds nothing: that case needs the type Regex in log line.

## Why some lines have no trace ID

The OpenTelemetry Logs SDK fills a record's trace ID and span ID from the context it is given when the line is written. Checkout is written in Go and logs through the `otelslog` bridge. Where its code passes the request's context, as for "payment went through", the line carries `trace_id`. Where it calls the logger without that context, as for "sending to postProcessor", the line has no trace ID, even though it was written during the same order. Loki's field list shows this as a share: `trace_id` on some lines of a service, not on all.

  <Col title="sending to postProcessor">Written without it. No trace_id, no link.</Col>

<InLab>
The derived field is provisioned in `lab/helm/grafana/values.yaml` with `matcherType: label` and `matcherRegex: trace_id`. Every shop service sends its logs to Loki over OTLP, so the trace ID is structured metadata, not part of the line's text.
</InLab>

<Trap>
A missing link does not mean the request had no trace. The line may have been written without the trace context, or under another field name. Look at the line's fields before you look for a fault in Tempo.
</Trap>

<Remember>
The link from a log line to its trace is a derived field: a name to match, a target data source, and a value that must be in the line. No trace ID in the line, no link.
</Remember>

<Question id="q-m14-s04" answer="d">
A service writes plain text logs to stdout, such as `charge failed trace=4bf92f3577b34da6a3ce929d0e0e4736`, and a collector ships them to Loki without parsing. The Loki data source has a derived field of type Label with the matcher `trace_id`. Why is there no link to the trace?

- Loki drops trace IDs from lines that do not come over OTLP

  Loki keeps the line's text as it is. The trace ID is still there, inside the text.

- The derived field needs the internal link switched off for text logs

  An internal link works for any value the field extracts. The field extracts nothing here.

- Tempo cannot open traces whose ID came from a log line

  The trace ID is the same value, wherever Grafana reads it from.

- The trace ID is only in the text, and a Label field reads label names

  A field of type Regex in log line, with a capture group for the ID, would find it.
</Question>
