<Problem>
Users say the Prometheus screen feels slow. The average request time is half a millisecond, which looks fine, but an average hides the slow tail. You want the 90th percentile: the time that nine requests out of ten stay under. Prometheus keeps no list of request times, only bucket counters.
</Problem>

<Idea>
A classic histogram counts observations into cumulative buckets, one counter series per upper bound, in the label `le`. You take the per-second rate of those buckets with `rate()`, and `histogram_quantile()` estimates from it where a quantile falls, by assuming that observations are spread evenly inside each bucket. The estimate is only as precise as the buckets are narrow.
</Idea>

## Buckets are counters, so start with rate()

Module m03 showed the three kinds of series a classic histogram writes: `_bucket` with an `le` label per bound, `_sum` and `_count`. Each bucket counts every observation at or below its bound since the process started, so the `+Inf` bucket always equals `_count`.

Totals since start-up say nothing about the last five minutes, so the first move is the one from step 3: take `rate()` of the buckets. That gives, per bucket, how many observations per second fell at or below each bound recently. The documentation's pattern for the 90th percentile over ten minutes is:

<Query lang="promql">{`histogram_quantile(0.9, rate(http_request_duration_seconds_bucket[10m]))`}</Query>

The first argument is the quantile as a number between 0 and 1. This gives one result per series apart from `le`: per handler, per instance, per pod.

## Aggregate with le kept

To get one percentile for a whole service, you add up the buckets of all its instances before the function, after the rate. The function needs the `le` label to know which bucket is which, so `le` must survive the aggregation:

<Query lang="promql">{`histogram_quantile(0.9, sum by (le) (rate(prometheus_http_request_duration_seconds_bucket[5m])))`}</Query>

Add any label you want to keep per result, as in `sum by (job, le)`. If you write `sum(...)` without `le`, all buckets collapse into one series. The function then finds no bucket bounds and returns nothing. The functions page only says that samples without `le` are silently ignored; the lab's Prometheus 3.13 also returns the warning `bucket label "le" is missing or has a malformed value of ""`, which the query page shows above the empty result.

<Compare caption="Two ways to aggregate the buckets">
  <Col title="sum(rate(..._bucket[5m]))">Buckets added into one series. le is gone, and histogram_quantile() returns nothing.</Col>
  <Col title="sum by (le) (rate(..._bucket[5m]))" hot>One series per bound, all instances added up. histogram_quantile() can read the buckets.</Col>
</Compare>

## How the estimate is made, and how far off it can be

The function finds the bucket where the quantile falls and assumes the observations inside it are spread evenly from its lower to its upper bound. The lowest bucket is assumed to start at 0 if its upper bound is greater than 0; otherwise the function returns that upper bound for any quantile that falls into it. The true value can lie anywhere in that bucket, so the error is limited by the bucket's width.

The lab shows how large that can be. Nearly all of Prometheus's HTTP requests take well under a millisecond, and its first bucket ends at 0.1 seconds. All of them land in that bucket, so the 90th percentile comes out at about 0.09 seconds: nine tenths of the way through a bucket from 0 to 0.1. With an average of half a millisecond, the real 90th percentile is almost certainly far lower. The answer is a fact about the buckets more than about the requests.

Two more rules are easy to miss. The highest bucket must be `+Inf`. If the quantile falls into it, the function returns the upper bound of the second highest bucket, because a bucket without an upper bound cannot be interpolated. A target with no observations in the window gives NaN.

## The average and a share under a threshold

The `_sum` and `_count` series answer two other questions. The average duration is the rate of the sum divided by the rate of the count, and that division can be aggregated in the same way:

<Query lang="promql">{`sum(rate(prometheus_http_request_duration_seconds_sum[5m])) / sum(rate(prometheus_http_request_duration_seconds_count[5m]))`}</Query>

The share of requests faster than a bound is one bucket divided by the count: `sum(rate(x_bucket{le="0.1"}[5m])) / sum(rate(x_count[5m]))`. This division needs a bucket with exactly that bound; if there is none, it returns nothing, with no estimate and no warning. For any other bound, `histogram_fraction(0, 0.3, sum by (le) (rate(x_bucket[5m])))` estimates the share with the same interpolation as `histogram_quantile()`, so the error is again up to a bucket's width. In the lab every request lands in the bucket from 0 to 0.1, so a bound of 0.05 gives 0.5: a guess from the interpolation, not a measurement. The functions page warns that a bound far from any bucket bound gives a large error, and says that with classic histograms, acting on the bucket series directly is often more robust. So use the bucket division when a bucket has your bound, and `histogram_fraction()` only when none does. Write the bound as Prometheus 3 stores it: `le` values are normalized at ingestion, so a bound of 1 is matched as `le="1.0"`, and `le="1"` finds nothing.

</InLab>

<Trap>
A quantile from a classic histogram is an estimate within one bucket, never a measured value. When most observations sit in one wide bucket, the estimate lands near that bucket's upper end, even if the real values are much smaller.
</Trap>

`histogram_quantile(φ, sum by (le) (rate(x_bucket[5m])))`: rate first, keep `le`, then estimate. The result is accurate only to the width of the bucket it falls in.

<Question id="q-m04-s07" answer="c">
A latency histogram has the buckets 0.05, 0.1, 0.5, 1 and +Inf seconds. Almost every request takes between 0.12 and 0.15 seconds. About what does histogram_quantile(0.5, ...) return?

- About 0.135 seconds, the middle of the real values

  The function does not know the real values. It only knows that the observations are in the bucket from 0.1 to 0.5.

- 0.5 seconds, the upper bound of the bucket

  The function interpolates inside the bucket. It returns a bucket bound as such only in special cases, such as a quantile in the +Inf bucket.

- About 0.3 seconds, the middle of the bucket from 0.1 to 0.5

  With almost all observations in that bucket, the median lands near its middle, because the function assumes an even spread.

- 0.1 seconds, the lower bound of the bucket

  0.1 would be returned only if the quantile fell at the very start of the bucket.
</Question>
