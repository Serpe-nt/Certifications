<Problem>
The Prometheus server answers 0.6 requests a second. Is that more than usual? You cannot tell from one number. You want the same rate as it was an hour ago, next to the current one. And for a node, you want to know how long ago it booted, but its exporter only gives a timestamp.
</Problem>

<Idea>
PromQL measures time in seconds since 1970, and lets you move a selector in time. `offset` shifts it back by a duration, `@` pins it to a fixed moment, and `time()` and `timestamp()` give the current evaluation time and the time of each sample. With them, "compared with an hour ago" and "how long since" become subtractions.
</Idea>

## offset: the same selector, earlier

`offset` follows a selector and shifts it back by a duration:

<Query lang="promql">{`sum(rate(prometheus_http_requests_total[5m] offset 1h))`}</Query>

This is the request rate as it was one hour ago. Subtract it from the current rate and you see the change. `offset` must come directly after the selector, inside the function, or after a subquery's closing bracket (step 11). `sum(x) offset 5m` is refused, because an offset applies to a selector or a subquery, not to the result of an expression. A negative offset looks forward in time, which is useful only when you evaluate a query in the past.

## @: a fixed moment

The `@` modifier evaluates one selector at a fixed Unix time instead of the query's own time. `up @ 1794480000` returns the value `up` had at that moment, however late you run the query. In a range query, `@ start()` and `@ end()` refer to the start and the end of the whole range, so every step of a graph can be compared with the same reference point. `@` and `offset` can be used together; the offset is then counted back from the `@` time.

Like `offset`, `@` follows the selector or the subquery directly. It is useful mainly in dashboards and in reports about a known incident.

## Timestamps are numbers too

Every timestamp in PromQL is a Unix time in seconds. `time()` returns the moment the query is evaluated. In a range query that is the time of each step, not the time you pressed the button. `timestamp(v)` returns, for each series, the time of the sample the query picked.

Many metrics hold a Unix time as their value: `node_boot_time_seconds` is when the node booted, `process_start_time_seconds` is when a process started, `kube_node_created` is when the Kubernetes node object was created. A subtraction turns such a value into an age:

<Query lang="promql">{`time() - node_boot_time_seconds`}</Query>

This is each node's uptime in seconds. Divide by 3600 for hours.

Functions such as `hour()`, `day_of_week()` and `day_of_month()` turn a Unix time into a part of a calendar date, in UTC. With no argument they use `time()`, so `hour()` is the current hour in UTC.

</Remember>

<Question id="q-m04-s09" answer="b">
`cert_expiry_timestamp_seconds` holds the Unix time when a certificate expires. Which expression gives the number of days left?

- `(cert_expiry_timestamp_seconds - time()) * 86400`

  Multiplying turns seconds into a much larger number. A day has 86,400 seconds, so you divide.

- `(cert_expiry_timestamp_seconds - time()) / 86400`

  The difference is the seconds left until expiry, and 86,400 seconds make one day.

- `(time() - cert_expiry_timestamp_seconds) / 86400`

  This is negative while the certificate is still valid. It counts the days since expiry.

- `timestamp(cert_expiry_timestamp_seconds) / 86400`

  timestamp() returns when the sample was scraped, not the expiry time stored as its value.
</Question>
