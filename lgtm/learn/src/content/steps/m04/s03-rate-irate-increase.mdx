<Problem>
A dashboard shows `prometheus_http_requests_total` as a line that climbs from 4,000 to 9,000 over the day, with a sudden drop to zero at noon. Nobody can tell from it whether the server is busy now. The total since the process started is the wrong question. You want to know how fast it grows.
</Problem>

<Idea>
A counter's value only matters through its change. `rate()` turns a window of counter samples into the average increase per second, `increase()` gives the same change as a total for the window, and `irate()` looks only at the last two samples. All three notice when a counter restarts at zero and correct for it.
</Idea>

## rate(): per second, averaged over a window

`rate()` takes a range vector of a counter and returns an instant vector: one number per series, the average increase per second over the window. To answer "how many rule evaluations per second does Prometheus run for the group node-exporter.rules", you write:

<Query lang="promql">{`rate(prometheus_rule_group_iterations_total{rule_group=~".*;node-exporter.rules"}[5m])`}</Query>

In the lab the answer is 0.0333. The group is evaluated every 30 seconds, so the counter grows by one every 30 seconds, which is one thirtieth per second.

The function does two things that a plain subtraction would not. When a value drops, it treats the drop as a counter reset, and it counts the value after the drop as new growth. And it extrapolates: samples rarely sit exactly at the edges of the window, so it stretches the change it saw to cover the whole window. That is also why a window must hold at least two samples. With a scrape interval of 30 seconds, `[30s]` usually holds only one, and the query returns nothing.

The documentation says `rate()` is best for alerts and for graphs of slow-moving counters.

## increase(): the same change, as a total

Often you want a count, not a speed: "how many requests in the last hour". `increase()` answers that. It is defined as `rate()` multiplied by the number of seconds in the window, so it handles resets and extrapolates in the same way. Because of the extrapolation, `increase()` can return 4.8 for a counter that only ever grows by whole numbers.

The documentation calls `increase()` syntactic sugar for readability, and asks you to use `rate()` in recording rules, so stored results are always per second.

## irate(): the last two samples only

`irate()` also takes a window, but it uses only the last two samples inside it. The window just sets how far back it may look for them. The result reacts at once to a short burst, which makes it fit for graphs of volatile, fast-moving counters. The documentation advises against it in alerts: a brief dip in the rate can reset the `for` clause of an alert, and a graph of nothing but short spikes is hard to read.

<Compare caption="Three functions on the same counter">
  <Col title="rate()" hot>Average per second over the whole window. For alerts and most graphs.</Col>
  <Col title="irate()">Per second between the last two samples. For graphs of fast, jumpy counters.</Col>
  <Col title="increase()">Total change over the window. For "how many in the last hour". It is rate() times the seconds of the window.</Col>
</Compare>

## Two mistakes that return a number anyway

The first is `rate()` of a gauge. A gauge goes up and down, and `rate()` reads every fall as a counter reset. `rate(node_load1[5m])` returns a value, and the value means nothing. For a gauge you want `deriv()` or `delta()`, which step 10 shows. A float sample does not store whether it is a counter or a gauge, so Prometheus can only guess from the name. The `_total` at the end of a name is the convention for counters. When the name does not end in `_total`, `_sum`, `_count` or `_bucket`, the query page shows an info note that the metric "might not be a counter", and still returns the number.

The second is to aggregate before the rate. A sum of counters from several pods is not a counter any more: when one pod restarts, the sum drops a little, and `rate()` cannot tell that drop from a real reset. The rule from the documentation is to take `rate()` first, then aggregate: `sum(rate(x[5m]))`, never a rate of a sum. Step 4 explains `sum`. If you write `rate(sum(x)[5m])`, Prometheus refuses it, because a plain range can only follow a selector. That refusal is no safety net: the subquery form `rate(sum(x)[5m:])` of step 11 is accepted and gives the wrong rate without a word.

<Trap>

</Trap>

<Remember>
Counters are read through `rate()` (per second), `increase()` (total for a window) or `irate()` (last two samples). Rate first, then aggregate, and only ever on counters.
</Remember>

<Question id="q-m04-s03" answer="a">
A graph of `irate(http_requests_total[10m])` shows one spike after another. A teammate says the 10-minute window should smooth it. Why does it not?

- irate() uses only the last two samples in the window

  The window only limits how far back irate() looks for its two samples. To average over ten minutes, use rate().

- irate() skips counter resets, so every restart becomes a spike

  irate() does adjust for counter resets, like rate().

- A 10-minute window holds too few samples for irate()

  Ten minutes holds many samples at a usual scrape interval. irate() ignores all but the last two.

- irate() returns the increase over the window, not a rate per second

  That describes increase(). irate() returns a per-second rate.
</Question>
