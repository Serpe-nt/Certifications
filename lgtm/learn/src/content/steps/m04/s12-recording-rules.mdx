<Problem>
The node overview dashboard has twelve panels, and each one computes CPU use from 176 raw series with nested `sum` and `rate`. Ten people keep it open, and it refreshes every 30 seconds. The server repeats the same work hundreds of times a minute, and the panels get slower as the cluster grows.
</Problem>

<Idea>
A recording rule computes an expression once per evaluation interval and stores the result as a new series with its own name. Dashboards and alerts then read the stored series, which is cheap. The name follows the pattern `level:metric:operations`, so a reader can tell what was computed and what labels are left.
</Idea>

## A rule is an expression with a name

Rules live in YAML files that the server loads through `rule_files`. Each file holds rule groups; each group has a name, an optional `interval`, and a list of rules. A recording rule has two required fields:

```yaml
groups:
  - name: node-exporter.rules
    rules:
      - record: instance:node_num_cpu:sum
        expr: count without (cpu, mode) (node_cpu_seconds_total{job="node-exporter",mode="idle"})
```

At every evaluation, Prometheus runs `expr` at the current time and stores the result under the name in `record`. An optional `labels` field adds or overwrites labels on the result. Rules inside a group run one after another, all with the same evaluation time, so a later rule in a group can read what an earlier one just stored. When no interval is given, the group uses the global `evaluation_interval`.

If a group takes longer to evaluate than its interval, the next evaluation is skipped, and the recorded series gets a gap. The counter `prometheus_rule_group_iterations_missed_total` records each skip.

## Reading the name

The best-practice name has three parts separated by colons:

- `level` says which labels are left after aggregation, such as `instance` or `cluster`.
- `metric` is the source metric's name, kept as it is, except that `_total` is dropped when a rate is taken.
- `operations` lists what was applied, the newest first, such as `rate5m` or `sum`.

So `instance:node_num_cpu:sum` is a sum (here a count) of a CPU metric, with one series per instance. The colons also tell you at a glance that a series is recorded, because colons are reserved for recording rules. The guidelines ask for `without` with the labels being removed, so `job` and other labels survive, and for `rate` rather than `increase` in rules, so stored values are always per second.

## Ratios are aggregated as two sums

A rule that stores a ratio per instance raises a trap when you want the ratio for a whole job. The average of the instance ratios is not statistically valid, because instances with little traffic weigh as much as busy ones. The guidelines say: aggregate the numerator and the denominator separately, then divide. The same holds for averages computed from a histogram's or a summary's `_sum` and `_count`.

## When a query should become a rule

The query basics give the signs. A query that must handle a large amount of data can time out in a graph. A query that a dashboard runs on every refresh, or that is too slow to graph ad hoc, should be recorded. Alerts that use an expensive expression benefit in the same way. The recorded series costs storage, so you record what is read often, not every query you ever write.

<Remember>
A recording rule stores `expr` under `record` at every evaluation, named `level:metric:operations`. Record what dashboards and alerts read often, and aggregate ratios as two sums before you divide.
</Remember>

<Question id="q-m04-s12" answer="a">
A rule records `rate(http_requests_total{job="api"}[5m])` with one series per instance and path. Which name follows the Prometheus guidelines?

- `instance_path:http_requests:rate5m`

  The level lists the labels left, the metric drops _total because a rate was taken, and the operation is rate5m.

- `http_requests_total:rate5m:instance_path`

  The order is level, then metric, then operations, and _total is dropped after a rate.

- `instance_path:http_requests_total:increase5m`

  The guidelines drop _total for a rate, and rules should record rate, not increase.

- `api:http_requests:rate5m`

  The level names the labels that are left, instance and path here, not the job's value.
</Question>
