<Problem>
The lab uses a large part of your PC's memory, and you will not study every evening. You need to switch it off and on again without a broken etcd, volumes stuck on a missing node, or an hour of repairs before you can study.
</Problem>

<Idea>
The script stops and starts the VMs in a fixed order. Stop shuts the guests down cleanly, workers first and `lb` last. Start runs the other way: `lb` first, then master1, then the workers. After a start the cluster heals itself; you wait and check.
</Idea>

## Why the order matters

Every node reaches the API and the lab's names through `lb`, so `lb` must come up first. master1 comes next, with etcd and the API server. With a single member, etcd's quorum is that member alone, so the API accepts changes as soon as master1 is up. The workers come last, when there is an API to register with. On stop, the order is reversed, so master1 keeps the API up while the workers shut down.

  <Event at="1" title="lb">HAProxy and the lab DNS answer again.</Event>
  <Event at="2" title="master1">etcd and the API server start.</Event>
  <Event at="3" title="worker1 to worker4">The kubelets register and pods start again.</Event>
  <Event at="+3 min" title="Check">make cluster-check passes.</Event>

## A clean shutdown, not a power cut

`stop` asks each guest to shut down, so Ubuntu stops its services before the VM turns off. The VMs are set to shut down the same way when Windows shuts down, and to stay off after Windows starts again until you run `start`. You never need to drain nodes for a planned stop of the whole lab.

## What a slow start looks like

For the first minutes after a start, some pods show `Unknown` or restart while their dependencies come back. On the earlier, larger version of the lab, with seven nodes and the whole stack installed, the record in `acceptance-lab.md` shows every pod Ready about eight minutes after a restart, with nothing done by hand. This lab has no such record yet. Wait before you act; look at a pod only if it is still down ten minutes after the nodes are `Ready`.

## After the PC has slept

When Windows sleeps, the VMs stop where they are and go on when the PC wakes, with their clocks set forward. Nothing restarts and running pods carry on. What can break is starting a new pod. Calico, the lab's pod network, wires up each new pod through a plugin that talks to the API server with a token, and calico-node writes that token on each node with a validity of 24 hours. The lab's Calico 3.31.7 renews it whenever kubelet renews calico-node's own token: about every 48 minutes while the VMs run, and again at kubelet's first pass after a wake. A night's sleep therefore does no harm.

After a sleep of more than about 23 hours, the token has run out when the PC wakes. A new pod then stays in `ContainerCreating`, and its events say `connection is unauthorized`. Run `make calico-renew` from `lgtm/lab` in WSL: it restarts calico-node one node at a time, each restart writes a new token, and it ends with one `PASS` line per node. `make lab-check` runs the same check first and names this command when a node's token has run out.

<Trap>
Do not restart the Windows host with the VMs still running and assume they come back. They shut down cleanly, but they stay off until you run `start` in an elevated PowerShell.
</Trap>

<Remember>
Stop: workers, master1, lb. Start: lb, master1, workers. Then wait a few minutes and check.
</Remember>

<Question id="q-m00-s07" answer="c">
Why does `start` bring up master1 before the four workers?

- The workers need more memory, so they start once master1 has finished

  Memory is reserved per VM when it starts. The order is about what each node needs to talk to.

- Workers cannot boot without master1 on the same Hyper-V switch

  A worker boots on its own. It needs the API only to register and run pods.

- master1 runs the API server, which the workers' kubelets must reach to register

  The kubelets register with the API server on master1; only the API server talks to etcd.

- master1 holds the Longhorn disks the workers mount

  The Longhorn disks are on the workers. master1 runs the control plane.
</Question>
