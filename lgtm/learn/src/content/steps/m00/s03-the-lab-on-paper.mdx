<Problem>
Later steps say things like "open Grafana", "query the tenant lab" or "the Collector in the namespace otel". Each of those lives on a VM, inside a cluster, inside a namespace. If you lose your place in those layers, a simple fault looks like a mystery.
</Problem>

<Idea>
The lab is four layers, each built by one command. Hyper-V on your PC runs six VMs, Ansible turns five of them into a Kubernetes cluster, Helm installs a platform on it, and Helm then installs the LGTM stack and a demo shop. Each product lives in a namespace of its own.
</Idea>

## Six machines on a private network

The VMs sit on a private Hyper-V network, 10.10.0.0/24, and reach the internet through your PC. One small VM called `lb` is not part of Kubernetes. It runs HAProxy, which sends API traffic to the control-plane node and web traffic to the workers, and dnsmasq, which answers names under `k8s.local`.

master1 runs etcd on itself, as a single member. Kubernetes calls etcd on the control-plane nodes stacked etcd. A highly available cluster runs at least three control-plane nodes with one etcd member each, so it keeps working when one of them is lost. This lab runs one and gives the memory to the workers; step 6 shows what that costs. All your workloads run on the four workers, and each worker has a second disk for volumes.

## Four layers, four commands

You build the lab from the bottom up, and each layer has its own command. You create the VMs from an elevated PowerShell. Everything after that runs from WSL, in the folder `lgtm/lab`.

## One namespace per product

The finished lab keeps every product apart. The platform uses `longhorn-system` for storage, `s3` for the object store, `gateway` for web traffic, `kafka` and `cert-manager`. The stack uses `mimir`, `loki`, `tempo`, `grafana`, `otel` for the Collector, `alloy`, `prom` for Prometheus, and `shop` for the demo shop. When something breaks, the namespace tells you where to look.

## How data moves through it

The shop's services send OTLP to the Collector `otel-gateway` in `otel`. The Collector sends metrics to Mimir, logs to Loki and traces to Tempo. Alloy adds pod logs and Kubernetes events. Prometheus scrapes the cluster and sends a copy to Mimir. Grafana reads from all of them. The browser reaches Grafana and the other screens through `lb` and the gateway, under names like `grafana.lab.k8s.local`.

Mimir, Loki and Tempo keep the data of different users apart as tenants. The shop's data goes to the tenant `lab`, and Prometheus writes to the tenant `prom`.

<Trap>
The `lb` VM is not a Kubernetes node, so `kubectl get nodes` lists five nodes, not six. It still matters: if `lb` is down, kubectl and the browser lose the cluster.
</Trap>

<Remember>
VMs, cluster, platform, stack: four layers, built in that order, one command each.
</Remember>

<Question id="q-m00-s03" answer="a">
The `lb` VM is stopped, and the five Kubernetes nodes still run. What stops working from your PC?

- kubectl and the browser, because both reach the cluster through lb

  HAProxy on lb carries the API on port 6443 and the web traffic on ports 80 and 443.

- Nothing, because lb is not a Kubernetes node

  It is not a node, but every way into the cluster from your PC goes through it.

- Only the shop, because lb runs the shop's database

  The shop runs on the workers. lb runs HAProxy and DNS only.

- etcd, because lb holds one etcd member

  etcd runs on the control-plane node, master1, not on lb.
</Question>
