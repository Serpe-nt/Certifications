<Problem>
`make cluster` ended without an error. Before you put a whole observability stack on top, you want proof: five nodes, an API server and an etcd member on master1, and kubectl talking to the cluster through the load balancer, not to master1 by chance.
</Problem>

<Idea>
A few read-only kubectl commands answer all of it. They show where kubectl connects, which versions run, which nodes are ready, and that the control-plane node runs its own API server and etcd member. Nothing here changes the cluster.
</Idea>

## Where kubectl connects

`kubectl cluster-info` prints the API address. In this lab it must be `https://cluster-endpoint.k8s.local:6443`, the name that points at `lb`. If it shows master1's own address, you are not testing the load balancer. `kubectl version` prints the client and the server version; both should be 1.35.

## Five nodes, two roles

`kubectl get nodes -o wide` lists master1 with the role `control-plane` and worker1 to worker4 with no role, all `Ready`, with the addresses 10.10.0.11 and 10.10.0.30 to 10.10.0.33 and containerd as runtime. master1 carries the taint `node-role.kubernetes.io/control-plane:NoSchedule`, so ordinary pods land on the workers only.

## The control plane runs as pods

kubeadm starts the control plane as static pods: the kubelet on the master runs them from files on that node. Their names end with the node name: `kube-apiserver-master1`, `etcd-master1` and so on. master1 runs an API server, a controller manager, a scheduler and an etcd member.

Production clusters run more than one etcd member. etcd accepts a change only when a majority of its members, the quorum, agree on it, and the Kubernetes guide to operating etcd asks for an odd number of members. With three, losing one leaves two of three, still a majority, so Kubernetes asks for at least three stacked control-plane nodes in a highly available cluster. This lab runs one, to give its memory to the workers. While master1 restarts, the API server is away: kubectl and Helm wait, and pods that already run keep serving. `lgtm/lab/docs/cluster.md`, section "One control-plane node", shows how to add masters back.

At this point the cluster holds only Kubernetes itself and Calico, in `kube-system`, `calico-system` and `tigera-operator`. Everything else comes in module m01.
</InLab>

<Trap>
Use labels, not pod counts, to check the control plane. Later modules add their own pods to `kube-system`, so "how many pods in kube-system" changes, while the etcd and API server pods stay at one each.
</Trap>

<Remember>
One endpoint through `lb`, five nodes `Ready`, and one of each control-plane pod on master1: that is a healthy lab.
</Remember>

<Do>
1. In WSL (bash), with the lab kubeconfig selected:
   <Cmd>{`export KUBECONFIG=~/.kube/lgtm-lab.config`}</Cmd>
2. Check the endpoint and the versions:
   <Cmd>{`kubectl cluster-info
kubectl version`}</Cmd>
   The control plane runs at `https://cluster-endpoint.k8s.local:6443`, and both versions start with v1.35.
3. List the nodes:
   <Cmd>{`kubectl get nodes -o wide`}</Cmd>
4. See the taint on master1:
   <Cmd>{`kubectl describe node master1 | grep Taints`}</Cmd>
5. List the control-plane pods with the node each runs on:
   <Cmd>{`kubectl get pods -n kube-system -l tier=control-plane -o wide`}</Cmd>
6. Count the etcd members and enter the number below:
   <Cmd>{`kubectl get pods -n kube-system -l component=etcd`}</Cmd>
</Do>

<Done>
Five nodes are `Ready`, the endpoint is the `lb` name, and master1 runs the `etcd-` and `kube-apiserver-` pods.
</Done>

<Question id="q-m00-s06" answer="a">
`kubectl cluster-info` prints `https://10.10.0.11:6443`. What does that tell you?

- kubectl talks to master1 directly and skips the load balancer

  10.10.0.11 is master1's own address. The lab's endpoint is the lb name, which still works when masters are added.

- kubectl talks to the load balancer, which is fine

  The load balancer has the address 10.10.0.5 and the name cluster-endpoint.k8s.local.

- etcd on master1 is the leader

  cluster-info prints the API address. It says nothing about the etcd leader.

- The lab's endpoint name resolves to 10.10.0.11

  cluster-endpoint.k8s.local resolves to lb, 10.10.0.5, and cluster-info would print the name itself.
</Question>
