<Problem>
The gateway's export queues fill up every evening, so the team doubles the replicas. The queues still fill up, and now the database behind the backend falls over too: twice as many Collectors push into a backend that was already the slowest part. Adding Collectors was the answer to a question nobody had checked.
</Problem>

The Collector reports on itself. Its own metrics say whether it is the bottleneck, and which kind of scaling it needs.

<Idea>
Scale on evidence from the Collector's own metrics: refused data and export queues that stay near their capacity. Stateless pipelines scale by adding replicas behind a load balancer; scrapers must split their targets; stateful components such as tail sampling or span metrics need a routing tier in front. When the backend is the slow part, more Collectors only push harder.
</Idea>

## When to scale, and when not to

Two signals say "this Collector needs help". Data refused by the memory limiter means the Collector is out of memory headroom. An export queue that keeps rising toward its capacity means data comes in faster than it goes out. The scaling guide suggests scaling up when `otelcol_exporter_queue_size` reaches 60 to 70% of `otelcol_exporter_queue_capacity`, scaling down when it stays low, and keeping a minimum, for example three replicas, for resilience. For scrapers, the sign is a scrape round that takes nearly as long as the scrape interval.

The same metrics also say when not to scale. If the queue stays near capacity even after you made it bigger, and `otelcol_exporter_send_failed_spans` keeps rising, the backend is the problem. More Collectors, or more export workers, put more pressure on a system that is already overloaded.

## Stateless pipelines: replicas and a load balancer

Most components are stateless, so most Collectors scale by adding replicas and spreading traffic among them. For OTLP over gRPC, the docs recommend a load balancer that understands gRPC. A plain layer 4 balancer, such as a Kubernetes ClusterIP Service, balances connections, and a gRPC client keeps one connection open for a long time, so one replica can end up with most of the traffic.

## Scrapers and stateful components

A scraping receiver cannot simply be copied: each copy scrapes the same targets, which doubles the data and can produce out-of-order samples in the backend. The targets must be sharded, either with a separate configuration per replica (for example one namespace each) or with the Operator's Target Allocator, which hands each Collector its share of the targets. All metric streams must keep a single writer.

Stateful components hold data across many requests: the tail sampling processor holds whole traces, the span metrics connector holds counters per service. A second replica would see only part of the data and compute different answers. Put a tier with the `load_balancing` exporter in front, routing by trace ID or service, as in step 9.

<InLab>
The lab gateway's two replicas get uneven traffic through their ClusterIP Service, and both scrape the same targets in `metrics/scraper`. The lab does not shard: `resource/scraper` gives each replica's copy its own `service.instance.id`, so the copies become two series and never collide. That keeps a single writer per series and doubles the scraped series.
</InLab>

<Trap practice>
The guide writes metric names without `_total`, as the Collector exposes them on its own endpoint. The same counters in Mimir carry `_total`; a query without it returns nothing.
</Trap>

<Remember>
Scale on refused data and on queues near capacity, not on a feeling; a full queue with rising send failures points at the backend. Stateless scales with replicas, scrapers with sharding, stateful components with a routing tier.
</Remember>

<Question id="q-m09-s11" answer="a">
Like the lab gateway, three replicas share one configuration that scrapes a PostgreSQL server, and each replica sets `service.instance.id` to its own pod name. What do you find in the metrics backend?

- Three series for each PostgreSQL metric, one per replica, with no out-of-order errors

  Each copy has its own identity, so the writes never collide, but the scraped series are tripled.

- One series per metric, because the backend merges identical samples

  The series differ in their instance label, so nothing is merged.

- Out-of-order sample errors, because three Collectors write the same series

  That is what happens without a distinct identity per replica; here each replica writes its own series.

- One series per metric, because only the leader replica scrapes

  The Collector has no leader election for scrapers; every replica scrapes every target in its configuration.
</Question>
