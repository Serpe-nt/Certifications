<Problem>
To chase a payment bug, a developer adds the customer's e-mail address and the full card number as span attributes and ships it on a Friday. On Monday the traces backend, run by another company in another country, holds three days of card numbers. Rolling back the code stops new leaks; the gateway could have stopped all of them.
</Problem>

A gateway that every span passes through is the one place where a rule about personal data can be enforced for all services at once.

<Idea>
The transform processor runs OTTL statements on every span, log record or metric that passes. A statement is a function call with an optional `where` condition, such as `delete_key(span.attributes, "user.email")`. With three functions you can delete a value, replace it with a hash, or mask part of it, before anything leaves the Collector.
</Idea>

## Statements, paths and contexts

The transform processor takes one list of statements per signal: `trace_statements`, `metric_statements`, `log_statements`. It runs them in order on each item. A path names a field, and its first word is the context: `span.attributes["user.email"]`, `resource.attributes["service.name"]`, `log.body`. Inside `trace_statements` you may use the contexts `resource`, `scope`, `span` and `spanevent`, but not `log`; the processor infers the context from the paths you use.

Statements can fail, for example when a function gets the wrong type. `error_mode` decides what happens: `ignore`, the default and the recommended mode, logs the error and goes on with the next statement; `silent` does the same without logging; `propagate` returns the error up the pipeline, and the whole payload is dropped.

## Delete, hash or mask

`delete_key(span.attributes, "demo.payment.card_cvv")` removes an attribute. `set(span.attributes["user.hash"], SHA256(span.attributes["user.email"]))` keeps something you can still group and compare by, since the same address always gives the same hash, without keeping the address. `replace_pattern(span.attributes["demo.payment.card_number"], "^\\d{4}-\\d{4}-\\d{4}-", "****-****-****-")` masks the first twelve digits and leaves the last four, the part support staff need.

Order matters inside the list. To keep a hash of the e-mail, the `set` with `SHA256` must run before the `delete_key` of the e-mail. A `where` clause such as `where span.attributes["user.email"] != nil` skips spans that do not have the field. Inside a Collector configuration a `$` must be written `$$`, which matters for `replace_pattern` with `$1` groups.

## Two processors in the lab gateway

The gateway's traces pipeline runs `transform/redact_sensitive_data` and then `redaction`. The transform deletes `demo.payment.card_cvv` and `user.email`, writes `user.hash`, and masks `demo.payment.card_number` with the statement above. Its statements use the older form with `context: span` and paths without a prefix, such as `attributes["user.email"]`; both forms are valid.

The `redaction` processor is a second line. With `allow_all_keys: true` it keeps every attribute key, but it masks the values of keys that match `blocked_key_patterns`: `demo.payment.card_pin`, `password`, `secret`. `demo.payment.card_number` is in `ignored_keys`, so the value the transform already masked passes untouched. `summary: info` lets the processor add count attributes, such as `redaction.masked.count`, when it masks something.

<Flow caption="A checkout span with emitRawPii on, through the gateway">
  <Stage title="checkout" kicker="Sends">user.email, demo.payment.card_number, demo.payment.card_cvv.</Stage>
  <Stage title="transform" kicker="Changes">Deletes the CVV and the e-mail, adds user.hash, masks the number.</Stage>
  <Stage title="redaction" kicker="Masks">Values of keys like password or secret; skips the card number.</Stage>
  <Stage title="Tempo" kicker="Stores">user.hash and ****-****-****-1234, nothing raw.</Stage>
</Flow>

<InLab>
The fault flag `emitRawPii` makes the checkout service add `user.email`, `demo.payment.card_number` and `demo.payment.card_cvv` to its order span, and the payment service add the card number and CVV to its `charge` span. Nothing in the shop's logs changes: these are span attributes only.
</InLab>

<Trap>
A plain SHA-256 of an e-mail address is not anonymous. Anyone with a list of addresses can hash them and compare. The redaction processor's README recommends HMAC hash functions, which need a secret key, for low-entropy data such as IP addresses, and e-mail addresses are just as easy to guess.
</Trap>

<Remember>
OTTL statements run in order, one function call each, with an optional `where`. Delete what nobody needs, hash what you must still match on, mask what people must partly see, and do it in the gateway before any exporter.
</Remember>

<Question id="q-m09-s06" answer="c">
A transform processor with `error_mode: ignore` runs `set(span.attributes["user.hash"], SHA256(span.attributes["user.id"]))` followed by `delete_key(span.attributes, "user.id")`. On some spans `user.id` is an integer. What happens to those spans?

- They are dropped, because a failed statement drops its payload

  Dropping the payload is what `propagate` does, not `ignore`.

- They keep `user.id`, because the processor stops at the first error

  With `ignore` the processor goes on with the next statement.

- They get no `user.hash`, and `user.id` is deleted by the next statement

  SHA256 accepts only strings; the failed statement is logged and skipped, and the delete still runs.

- They get a hash of the number's text, because SHA256 converts the value first

  SHA256 returns an error for any target that is not a string.
</Question>
