<Problem>
A gateway Collector is OOM-killed twice a night when a batch job floods it with spans. Its pipeline has only an exporter. Each restart loses everything held in memory, and the batch job's spans never arrive anyway. A few lines of processors would have made the Collector refuse the flood politely and keep running.
</Problem>

Most Collector pipelines in production share the same small set of processors. This step builds a practice Collector of your own and puts five of them to work.

<Idea>
The memory limiter protects the Collector by refusing data before memory runs out. Batching groups data into fewer, larger requests. The resource and attributes processors add, change or delete attributes, and the filter processor drops whole spans, points or records that match a condition. Their order in the pipeline decides what each one sees.
</Idea>

## The memory limiter refuses before it is too late

The memory limiter checks memory use every `check_interval`. Its hard limit is `limit_mib`; its soft limit is `limit_mib` minus `spike_limit_mib`. Above the soft limit it refuses new data, by returning an error to the component before it in the pipeline. That error is retryable: a well-behaved receiver passes it back to the sender, which retries later. Above the hard limit it also forces a garbage collection. When memory drops below the soft limit again, data flows normally.

So the memory limiter turns a crash into back-pressure. It must be the first processor, so that it refuses data before anything else stores it. The README also recommends the environment variable `GOMEMLIMIT` at 80% of the hard limit, and `limit_percentage` instead of `limit_mib` when the container has a memory limit. Refused data is lost for good only when the sender does not retry.

## Batching: in the exporter or in a processor

Fewer, larger requests compress better and need fewer connections. The `batch` processor sends a batch when it reaches `send_batch_size` items (8192 by default) or when `timeout` passes (200 ms by default), whichever comes first. `send_batch_max_size` sets an upper limit and splits larger batches.

Exporters can now batch by themselves, in their sending queue (`sending_queue` with a `batch` block). The processor guide says to prefer the exporter's batching where it exists, and the Collector warns at startup when one pipeline has both a batch processor and an exporter with queue batching turned on. You will meet the `batch` processor in many existing configurations, including the lab gateway, so you need to read both.

## Changing attributes: resource or attributes

The `resource` processor changes resource attributes, those that describe who produced the data: `service.name`, a host, a cluster. The `attributes` processor changes the attributes of each span, log record or data point. Both take a list of actions: `insert` (only if missing), `update` (only if present), `upsert` (either), `delete`, `hash` and a few more. Neither can rename a span: the attributes processor works only on attributes.

Both READMEs now say that the `transform` processor supersedes them, and to migrate to it. They still work in 0.165.0, and the lab gateway uses `resource`. Step 6 shows the same changes written in OTTL.

## Filtering: drop what nobody will read

The `filter` processor drops telemetry that matches OTTL conditions. Under `traces.span`, `logs.log_record` or `metrics.datapoint` you list conditions; if any one of them is true, the item is dropped. Put the filter early, right after the memory limiter, so that later processors do not spend work on data that will be thrown away.

<Question id="q-m09-s05" answer="b">
A memory limiter has `limit_mib: 1000` and `spike_limit_mib: 200`. Memory use reaches 850 MiB. What does the processor do?

- Nothing yet; it acts only when memory passes 1000 MiB

  1000 MiB is the hard limit. The processor already refuses data at the soft limit.

- Refuses new data until memory is below 800 MiB again

  The soft limit is 1000 - 200 = 800 MiB; above it the processor returns errors that senders should retry.

- Drops the oldest data in the exporter queues to free memory

  The memory limiter does not touch exporter queues; it refuses data at the front of the pipeline.

- Restarts the Collector process to release memory

  It never restarts the process; above the hard limit it forces a garbage collection.
</Question>
