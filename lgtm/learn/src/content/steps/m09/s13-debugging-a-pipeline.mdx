<Problem>
A change to the redaction rules went out at 16:00. At 16:05 one replica is in CrashLoopBackOff, and at 17:00 security finds e-mail addresses in the traces backend anyway: the replica that did start does not redact. Two faults, one change, and the dashboards show nothing wrong, because data still flows.
</Problem>

A Collector fails in a few typical ways, and for each one there is a place where it shows.

<Idea>
A Collector that does not start says why in its log. A Collector that starts but does the wrong thing shows its real pipelines on the zPages page `/debug/pipelinez` and its data in the debug exporter. A Collector that drops data shows it in its own metrics: accepted, refused, sent and failed counts for every receiver and exporter.
</Idea>

## It does not start: read the log

The Collector writes its own log to stderr. A configuration error stops it at startup with a line that starts with `Error: invalid configuration:` and names the path to the problem, such as `service::pipelines::traces: references exporter "debugg" which is not configured`. `otelcol-contrib validate --config=FILE` prints the same check without starting anything, so a pipeline in CI can run it before every rollout.

On Kubernetes, a rolling update helps you here: the new pod fails, the old one keeps running. You see one pod in CrashLoopBackOff next to a healthy one, and the healthy one still runs the old configuration.

## It runs but does the wrong thing: look inside

When the Collector starts but the data is wrong, compare what you meant with what runs. The zPages extension serves pages on port 55679: `/debug/servicez` for an overview, `/debug/pipelinez` for each pipeline with its receivers, processors and exporters in order, `/debug/extensionz` and `/debug/featurez`. A processor that is defined but missing from the pipeline shows at once. The column MutatesData also tells you whether any processor in the pipeline changes data.

The debug exporter shows the data itself. `verbosity: basic` prints one line per batch with counts, `normal` about one line per item, `detailed` every field. For OTTL in particular, the transform processor's README suggests the Collector's log level `debug` (`service::telemetry::logs::level`), which prints the data before and after each statement.

## It loses data: count it

Every receiver, processor and exporter built on the Collector's helpers counts what passes. Accepted and refused at the receivers, incoming and outgoing at the processors, sent, failed to send and failed to enqueue at the exporters. The metrics are on port 8888 by default, at the level `normal`; `basic` keeps only the essential ones and `detailed` adds more. Follow a signal along the counters and the first place where the numbers stop matching is where the data stops.

The troubleshooting page adds a checklist for each hop: errors in the log, how data comes in, how it is changed, how it goes out, in which format, how the next hop is configured, and whether a network policy is in the way.

<Layers caption="Where each kind of failure shows">
  <Layer title="Does not start">The log: Error: invalid configuration, and validate before rollout.</Layer>
  <Layer title="Starts, wrong result">zPages PipelineZ for what runs, the debug exporter for the data.</Layer>
  <Layer title="Loses data">Internal metrics: accepted, refused, sent, send_failed, enqueue_failed.</Layer>
</Layers>

<Question id="q-m09-s13" answer="a">
A Collector's metrics show `otelcol_receiver_accepted_spans` rising steadily, `otelcol_exporter_sent_spans` rising at the same rate, and no failures. The backend has no spans from one service. Where do you look first?

- At the data itself, since the Collector delivers all it receives

  Matching counts mean the Collector passes every span on; the cause lies in the data or after the export.

- At the exporter's queue, because sent spans can still be waiting in it

  A span counts as sent only after the backend accepted it.

- At the memory limiter, because it may refuse spans without counting them

  Refused data shows up in the receiver's refused counter, which stays at zero here.

- At the receiver's network policy, because the spans may never arrive

  The receiver accepts spans at the same rate as they are sent, so they arrive.
</Question>
