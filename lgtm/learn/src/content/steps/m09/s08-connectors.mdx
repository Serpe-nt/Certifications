<Problem>
A team has good traces but no metrics: the services were instrumented for tracing only. They want a request rate, an error rate and a latency percentile per endpoint on a dashboard, and an alert on them, this week. Re-instrumenting twenty services for metrics would take a quarter. Every request is already a span.
</Problem>

A processor works inside one pipeline and on one signal. Turning traces into metrics needs something that leaves one pipeline and enters another.

<Idea>
A connector is an exporter at the end of one pipeline and a receiver at the start of another. It can produce a different signal than it consumes, as `span_metrics` does when it turns spans into metrics, or pass data on unchanged to chosen pipelines, as `routing` does.
</Idea>

## Exporter here, receiver there

You define a connector under `connectors:` and then name it twice in `service`: in the `exporters` of one pipeline and in the `receivers` of another. It must be used on both sides. Each connector supports certain pairs of pipeline types: `span_metrics` and `service_graph` go from traces to metrics, `routing` from traces to traces, metrics to metrics or logs to logs. A pair the connector does not support is a configuration error.

A connector sits beside the normal exporters. The traces pipeline can send to Tempo and to `span_metrics` at the same time, so the spans are kept and the metrics are made from the same copy.

<Flow caption="Spans become metrics in your practice Collector">
  <Stage title="traces pipeline" kicker="otlp in">Spans from telemetrygen.</Stage>
  <Stage title="span_metrics" kicker="Connector">Counts spans and measures their duration.</Stage>
  <Stage title="metrics pipeline" kicker="Receives">The connector is its receiver.</Stage>

</Flow>

## span_metrics: rate, errors, duration

`span_metrics` aggregates request, error and duration (RED) metrics from spans. It emits `traces.span.metrics.calls`, a count of spans, and `traces.span.metrics.duration`, a histogram of span durations. Each has at least the dimensions `service.name`, `span.name`, `span.kind` and `status.code`; errors are the calls with an error status code. You can add dimensions from span or resource attributes, which multiplies the series, so choose them with the cardinality of module m02 in mind.

The connector keeps its counts in memory, so it is stateful. If two Collectors see spans of the same service, both write a series with the same labels and the counts fight. In 0.165.0 it adds a `collector.instance.id` dimension by default to keep each Collector's series apart, and the gateway docs show a first tier that routes spans by service name to keep all of a service on one Collector.

## service_graph and routing

`service_graph` looks for pairs of spans that form one request: a client span and the server span it called, a producer and a consumer, or a client span to a database. For each edge it emits metrics such as `traces_service_graph_request_total{client, server}` and latency histograms from both sides. It must see both spans of a pair, so all spans of a trace have to reach the same Collector.

`routing` evaluates OTTL conditions, for example `resource.attributes["env"] == "prod"`, and sends matching data to the pipelines a route names. The default action `move` takes matched data out of later routes; `copy` lets later routes see it too. Data that matches no route goes to `default_pipelines`.

<Trap practice>
Do not judge the counter by its first flush. On the lab, the first flush after a restart printed `Value: 0` for both `calls` data points while the duration histogram already showed `Count: 7`. From the second flush on, `calls` matched the histogram's count (15, 22, 30), and both grew by 7 or 8 at each flush. Both are cumulative, so each flush repeats the total since the Collector started.
</Trap>

<Remember>
A connector is the exporter of one pipeline and the receiver of the next. span_metrics and service_graph turn traces into metrics and keep state, so the spans they need must reach the same Collector; routing only chooses pipelines.
</Remember>

<Question id="q-m09-s08" answer="b">
A configuration defines `span_metrics` under `connectors` and lists it in the traces pipeline's exporters. No pipeline lists it as a receiver. What happens?

- The connector computes the metrics and drops them, with a warning

  A connector is not allowed to be used on one side only.

- The Collector rejects the configuration as invalid

  Each connector has to appear in two pipelines, once on each side.

- The metrics are sent to the traces pipeline's other exporters

  A connector never feeds the pipeline it exports from.

- The Collector starts a metrics pipeline for the connector by itself

  The Collector builds only the pipelines listed under `service.pipelines`.
</Question>
