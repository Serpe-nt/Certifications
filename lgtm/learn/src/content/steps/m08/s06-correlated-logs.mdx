<Problem>
A customer says a checkout failed at 14:02. The workshop service logged "checkout failed: card declined" at that minute, among a hundred other lines. In module m07 you would have searched Tempo for the trace. Now you want to start from the log line and land on the very trace that wrote it, without matching times by eye.
</Problem>

<Idea>
Solution `05-logs` changes no log call. It installs the logging instrumentation and turns the logs exporter on, so each Python log record also leaves over OTLP with the trace ID and span ID of the span that was active. Loki keeps those IDs and the record's attributes as structured metadata, and Grafana links the trace ID to Tempo.
</Idea>

## What solution 05 changes

The service already called `log.info`, `log.warning` and `log.exception`. The solution adds the package `opentelemetry-instrumentation-logging` and sets `OTEL_LOGS_EXPORTER=otlp`. The agent then attaches its handler to Python's root logger. Two small code changes make the records richer. Keys passed with `extra=` become attributes of the record, such as `workshop.sku`. And `log.exception` inside an `except` block adds the exception's type, message and stack trace, which the SDK sets as `exception.*` attributes.

A third setting, `OTEL_PYTHON_LOG_CORRELATION=true`, is only for the console. It changes the format of the lines on standard output so that they show `trace_id` and `span_id` too. Lines written outside any span, such as the startup messages, show `trace_id=0`.

## How a record lands in Loki

Loki maps an OTLP log record onto its own model. A short default list of resource attributes becomes index labels: `service_name`, `service_namespace`, `service_instance_id`, `deployment_environment_name` and the `k8s_*` names. The lab adds `cluster`. The body becomes the log line. Everything else is stored with the line as structured metadata: the other resource attributes, the scope name, and the record's fields and attributes, among them `trace_id`, `span_id`, `severity_text` and `severity_number`. Dots become underscores on the way, as in Mimir.

Structured metadata is not part of the stream selector. You filter on it after the selector, with a label filter such as `| severity_text="ERROR"`.

## From the line to the trace

The lab's Loki data source in Grafana has a derived field for trace IDs, provisioned with the lab. When you expand a line that carries `trace_id`, Grafana offers a link that opens the trace in Tempo. The span ID on the line is the span that was active when the line was written: for the slow-compute warning that is the server span `GET /compute`, because the `fibonacci` span had already ended.

<InLab>
The lab's gateway sends the workshop's logs to Loki's `/otlp` endpoint as tenant `lab`, the same way as the shop's. The shop's logs carry `trace_id` in the same place, which is how module m02 jumped from a trace to its logs.
</InLab>

<Trap>
Do not put `trace_id` inside the braces of a Loki query: it is structured metadata, not a stream label. Write `{service_name="workshop"} | trace_id="..."`; a selector with `trace_id` in the braces matches no stream.
</Trap>

<Question id="q-m08-s06" answer="a">
You have a trace ID from Tempo and want the workshop's log lines of that request in Loki. Which query works on this lab?

- `{service_name="workshop"} | trace_id="99f566aa8525156f8f9b7df8a1e4a232"`

  The stream selector picks the service by an index label, and the label filter then matches the structured metadata field trace_id.

- `{service_name="workshop", trace_id="99f566aa8525156f8f9b7df8a1e4a232"}`

  trace_id is structured metadata, not a stream label, so no stream matches this selector.

- `{trace_id="99f566aa8525156f8f9b7df8a1e4a232"}`

  A selector needs stream labels, and trace_id is not one. This matches nothing.

- `{service_name="workshop"} |= "trace_id=99f566aa8525156f8f9b7df8a1e4a232"`

  This searches the log line text, and the body holds only the message. The IDs on stdout come from the console format, not from the OTLP record.
</Question>
