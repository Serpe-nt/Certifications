<Problem>
You named the instrument `workshop.compute.duration`, with the unit `s`. In Grafana nobody will type that name: Mimir stores Prometheus series, and dots are not allowed in classic Prometheus names. Before you build a dashboard on your new metrics, you need to know what each instrument is called in Mimir and which labels came with it.
</Problem>

<Idea>
The metrics you record travel over OTLP to the collector gateway and on to Mimir, which translates each OpenTelemetry metric into Prometheus series. The name gets underscores, a unit suffix and, for counters, `_total`; attributes become labels; the resource becomes `job`, `instance` and a `target_info` series. Reading the translated names once makes every later query easy.
</Idea>

## Four instruments in the code

Solution `04-metrics` adds a meter to the service you finished in module m07. It gets the meter from the API, as the tracer: `metrics.get_meter("workshop")`. The agent you start with `opentelemetry-instrument` sets up the SDK behind it. Then it creates the instruments once, at module level:

- `workshop.checkouts`, a counter with the unit `{checkout}`, incremented once per checkout with the attribute `outcome` (placed, declined, out_of_stock and so on);
- `workshop.checkouts.active`, an up-down counter: `add(1)` when a checkout starts, `add(-1)` in a `finally` block when it ends;
- `workshop.compute.duration`, a histogram in seconds with suggested bounds from 0.001 to 5, recorded with the attribute `workshop.compute.n`;
- `workshop.inventory.stock`, an observable gauge whose callback reads every SKU's stock from SQLite.

Two settings in `workshop.env` turn the metrics on: `OTEL_METRICS_EXPORTER=otlp`, and `OTEL_METRIC_EXPORT_INTERVAL=15000`, so that a change shows within 15 seconds instead of 60.

## How the names change on the way into Mimir

Mimir follows the OpenTelemetry rules for turning OTLP metrics into Prometheus series. Characters that Prometheus names do not allow become `_`. The unit is turned into a word and added, unless the name already ends in it: `s` becomes `_seconds`. A unit in braces, such as `{checkout}`, is only an annotation and is dropped. A cumulative monotonic sum gets `_total`. An up-down counter is a sum that is not monotonic, so it follows the gauge rules and arrives as a gauge without `_total`. A histogram becomes the classic `_bucket`, `_sum` and `_count` series.

<Compare caption="One instrument, two names">
  <Col title="In the code">`workshop.checkouts` with unit `{checkout}`, `workshop.checkouts.active`, `workshop.compute.duration` with unit `s`, `workshop.inventory.stock` with unit `{item}`</Col>
  <Col title="In Mimir" hot>`workshop_checkouts_total`, `workshop_checkouts_active`, `workshop_compute_duration_seconds_bucket`, `workshop_inventory_stock`</Col>
</Compare>

Attributes become labels the same way: `workshop.compute.n` becomes `workshop_compute_n`. The resource is handled apart. `service.namespace` and `service.name` together become `job="workshop/workshop"`, and `service.instance.id`, which the Python SDK generates for each process, becomes `instance`. The lab's Mimir also copies a few resource attributes, `service_name` among them, onto every series. The others, such as `deployment.environment.name` and the SDK's version, go to a separate `target_info` series that you can join on `job` and `instance`.

<Question id="q-m08-s04" answer="d">
A service has an up-down counter named `queue.jobs.waiting` with the unit `{job}`. It is exported over OTLP with the default temporality into a backend that follows the OpenTelemetry rules for Prometheus. Which series do you query?

- `queue_jobs_waiting_total`, a counter

  Only monotonic sums get `_total` and become counters. An up-down counter can go down.

- `queue_jobs_waiting_jobs`, a gauge

  A unit in braces is an annotation and is dropped. It does not become a suffix.

- `queue.jobs.waiting`, a gauge

  With the default translation, dots in names are replaced with underscores.

- `queue_jobs_waiting`, a gauge

  A cumulative sum that is not monotonic follows the gauge rules, the dots become underscores, and the `{job}` unit is dropped.
</Question>
