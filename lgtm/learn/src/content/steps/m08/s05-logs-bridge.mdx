<Problem>
The workshop service already writes log lines with Python's `logging` module: an order placed, a charge declined, the shop unreachable. A large service has hundreds of such calls, and its team will not rewrite them for a new API. Yet those lines are exactly what you want next to a trace, with the trace's ID on them.
</Problem>

<Idea>
For traces and metrics, OpenTelemetry defined new APIs that your code calls. For logs it did not ask that. It defined a log data model and a Logs API built mainly for appenders: plug-ins that bridge an existing logging library into the OpenTelemetry SDK. The bridge adds the trace and span IDs of the current context and the resource to every record, so your existing log calls become correlated records.
</Idea>

## Why logs got a bridge, not a new API

The logging world is much older and more varied than tracing. Every language has popular libraries, Java alone has Log4j and Logback, and many programs write logs in formats their operators cannot change. The specification says it chose a different path for logs because of that legacy. It defines what a log record is, maps existing formats to it, and gives library authors an API to build appenders on.

The OpenTelemetry status page lists the parts as stable: the Logs Bridge API, the Logs SDK and the protocol. Language support differs: the logs page lists the Python implementation as in development, while Java, .NET, C++, PHP and Rust are stable.

The Logs API can also be called directly. The current specification allows applications and instrumentation libraries to emit records with it, for example structured events with a name that a logging library cannot express. The status page and the Python documentation still describe it as an API that end users do not call. For your application's own log lines, the advice is the same in every source: keep your logging library and add an appender.

## What a log record holds

A record has named top-level fields and free attributes:

- Timestamp, when the event happened, and ObservedTimestamp, when the collecting system saw it;
- TraceId, SpanId and TraceFlags, from the W3C trace context;
- SeverityText, the level as the source wrote it, and SeverityNumber;
- Body, the message, which can be a string or structured;
- Attributes, the extra fields of this event, and EventName for records that are events;
- Resource and InstrumentationScope, as on spans and metrics.

SeverityNumber puts every library's levels on one scale. Each level name owns four numbers, so a backend can sort and filter levels from any source.

## Where the trace ID comes from

When the appender emits a record, the Logs API takes the current context unless one is passed in. If a span is active, as it is inside a request handled by an instrumented framework, the SDK puts that span's trace ID and span ID on the record. Nothing in the log call names the span. The specification lists three ways a log ties to other signals: by time, by this execution context, and by the resource, which says which service and process wrote it.

From there the pipeline looks like the one for spans in module m07. A LoggerProvider holds the resource and one or more processors. The batching processor queues records, at most 2048, and exports at most 512 at a time, every second by default (`OTEL_BLRP_SCHEDULE_DELAY=1000`). An exporter, OTLP or the console, sends them on.

In Python, the logging instrumentation attaches an OpenTelemetry handler to the root logger, and since OpenTelemetry Python 1.40.0 the agent does that by default. In the shop, the Go service checkout bridges its `slog` logger with `otelslog`, and recommendation adds a `LoggingHandler` to Python's logging in code.

<Trap>
Correlation does not come from printing the trace ID into the message. The bridge sets TraceId and SpanId as fields of the record from the active context; a log call made outside any span, such as at startup, has no trace ID at all.
</Trap>

<Remember>
Keep your logging library and add an OpenTelemetry appender. The record gets its trace ID and span ID from the current context, its resource from the SDK, and its level as a SeverityNumber from 1 to 24.
</Remember>

<Question id="q-m08-s05" answer="b">
Why did OpenTelemetry give logs a bridge API for appenders, instead of a new logging API that every application calls, as it did for traces and metrics?

- Because log records cannot carry a trace ID unless they come from a logging library.

  A record emitted through the Logs API directly gets the trace context too. The reason is about existing code, not about the data.

- Because many logging libraries and log formats already exist, and OpenTelemetry chose to work with them rather than replace them.

  The specification explains the choice by the large and varied legacy in logging. Appenders bridge those libraries into the OpenTelemetry data model.

- Because the logs signal is still experimental in the specification.

  The status page lists the Logs Bridge API, the SDK and the protocol as stable.

- Because the Collector, not the SDK, is meant to create log records.

  The Collector can read and convert logs from files, but applications emit records through the SDK as well.
</Question>
