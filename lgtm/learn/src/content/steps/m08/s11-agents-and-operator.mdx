</Problem>

<Idea>
Each main language has a zero-code agent that loads the SDK and instrumentation libraries when the program starts and is configured with the `OTEL_` variables. On Kubernetes, the OpenTelemetry Operator injects that agent into a pod: an Instrumentation resource holds the shared settings, and an annotation on the pod template opts the workload in.
</Idea>

## What an agent does, and what it does not

An agent adds the API and SDK to a program from the outside. The mechanism depends on the language: bytecode changes in Java, monkey patching in Python, eBPF in some cases. It instruments the libraries the program uses, such as its HTTP server, its HTTP client and its database driver, so you get spans and metrics at the edges of the service. Your own code is not instrumented: for a span around your own function you add API calls, as you did with the workshop's manual spans in module m07. The OpenTelemetry pages list zero-code instrumentation for .NET, Go, Java, JavaScript, PHP and Python.

## Four agents, four ways to attach

- Java: a single JAR, `opentelemetry-javaagent.jar`, attached with `-javaagent:` on the command line or through `JAVA_TOOL_OPTIONS`, for Java 8 and later. Settings come as system properties such as `-Dotel.service.name`, as environment variables, or from a properties file.
- .NET: an installer script that you download, verify and run; it supports .NET Framework from 4.6.2 on and current .NET versions, for traces and metrics.
- Node.js: the package `@opentelemetry/auto-instrumentations-node`, loaded with `node --require @opentelemetry/auto-instrumentations-node/register app.js` or through `NODE_OPTIONS`.
- Python: `opentelemetry-distro` brings the SDK and the `opentelemetry-instrument` command, and `opentelemetry-bootstrap -a install` installs the instrumentation package for each library it finds.

All of them read the same `OTEL_` variables from step 8, so the Operator can configure them in one way.

## The Operator injects the agent

<Flow caption="How the Operator instruments a Python pod">
  <Stage title="Instrumentation" kicker="Custom resource">Exporter endpoint, propagators, sampler, extra env, in the namespace.</Stage>
  <Stage title="Annotation" kicker="Pod template">instrumentation.opentelemetry.io/inject-python: "true"</Stage>
  <Stage title="Pod starts" kicker="Operator">Init container opentelemetry-auto-instrumentation copies the agent in.</Stage>
  <Stage title="App container" kicker="Result">Runs with the agent and the OTEL_ variables from the resource.</Stage>
</Flow>

The Instrumentation resource lives in a namespace and is shared by every pod that points to it. The annotation goes on `spec.template.metadata.annotations` of the Deployment, not on the Deployment's own metadata. Its value is `"true"` for the namespace's resource, a name such as `"my-instrumentation"`, a `namespace/name` pair, or `"false"`. The Operator then adds an init container named `opentelemetry-auto-instrumentation`, which brings the agent into the application container. For a program no agent can handle, `inject-sdk` adds only the environment variables, for an SDK the program sets up itself.

A few details decide whether it works. The Instrumentation resource must exist before the pods start; pods created earlier stay uninstrumented until they are recreated. The injected agents do not all use the same protocol: for Java, .NET and Python the default is OTLP over HTTP, so the endpoint needs a port 4318 address, while Node.js uses gRPC on 4317. The Python agent does not support gRPC here at all. Without an endpoint, the default is `http://localhost:4317`, which reaches nothing in most pods. Go injection is off until its feature gate is enabled.

The Operator also sets resource attributes. `service.name` comes from an annotation `resource.opentelemetry.io/service.name` if present, otherwise from the Deployment's name and then other workload names, unless `OTEL_SERVICE_NAME` is set, which wins.

<Trap>
An annotation on the Deployment's own metadata does nothing. The Operator reads the pod's annotations, so the inject annotation must be in the pod template.
</Trap>

<Remember>
Agents instrument libraries at the edges of a service, never your own functions. The Operator injects the agent when an Instrumentation resource exists and the pod template carries an inject annotation.
</Remember>

<Question id="q-m08-s11" answer="a">
A team creates an Instrumentation resource with `spec.exporter.endpoint: http://otel-collector:4317` and annotates a Python Deployment with `inject-python: "true"`. Node.js pods in the same namespace send traces with the same resource; the Python pods send nothing. What should they change?

- Point the Python pods at the collector's OTLP/HTTP port, 4318.

  The Python agent injected by the Operator exports over http/protobuf and does not support gRPC. The Node.js agent uses gRPC by default, which is why 4317 works for it.

- Add the annotation to the Deployment's metadata as well as to the pod template.

  The pod template is the right place, and the Node.js pods show the setup works. The problem is the protocol and port.

- Set the annotation value to the name of the resource instead of "true".

  "true" uses the Instrumentation resource of the namespace, which is the one the Node.js pods already use.

- Enable the Python feature gate on the Operator.

  Python injection is enabled by default. Go is the language whose gate is off by default.
</Question>
