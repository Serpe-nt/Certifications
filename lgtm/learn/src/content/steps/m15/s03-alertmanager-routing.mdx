<Problem>
The database loses its network for two minutes. Within seconds, 40 checkout pods each fire `CheckoutSlow`, the checkout service fires `CheckoutDown`, and the database fires its own alert. Sent one by one, that is 42 messages on one phone, and the one that names the real problem is somewhere in the middle.
</Problem>

Prometheus decides that something is wrong. A second program decides who hears about it, and how often.

<Idea>
The Alertmanager receives alerts and turns them into notifications. A routing tree picks the receiver by labels, grouping puts alerts that belong together into one message, inhibition mutes alerts that another alert already explains, and silences mute alerts by hand for a fixed time.
</Idea>

## The routing tree picks the receiver

The configuration has one top-level `route`, which matches every alert and names a default receiver. Under it are child routes, each with `matchers` such as `severity="page"`. An alert walks down the tree and stops at the first child that matches; if no child matches, the parent handles it. With `continue: true` on a route, the alert goes on to the next sibling as well, which is how one alert reaches two teams.

A child route inherits what it does not set itself: the receiver, `group_by` and the three timers below.

## Grouping turns many alerts into one message

`group_by` names the labels that make a group. Alerts with the same values of those labels are sent together. With `group_by: [alertname, service]`, the 40 `CheckoutSlow` alerts are one group and one notification that lists all 40 pods.

Three timers decide when a group is sent:

- `group_wait`, 30 seconds by default: how long to wait after the first alert of a new group, so that its neighbours arrive and go into the same message.
- `group_interval`, 5 minutes: how long to wait before sending an update when alerts join or leave a group that was already sent.
- `repeat_interval`, 4 hours: how long before a notification that did not change is sent again.

<Flow caption="One alert through the Alertmanager">
  <Stage title="Route" kicker="matchers">The first matching child route gives the receiver.</Stage>
  <Stage title="Group" kicker="group_by">Alerts with the same labels wait together.</Stage>
  <Stage title="Mute" kicker="inhibit, silence">Muted alerts are left out of the message.</Stage>
  <Stage title="Notify" kicker="receiver">One message per group.</Stage>
</Flow>

## Inhibition and silences mute what is explained

An inhibition rule has source matchers, target matchers and an `equal` list. While a source alert fires, target alerts are muted if they have the same values for the labels in `equal`. In the scene above, `CheckoutDown` as source, `severity="ticket"` as target and `equal: [service]` mute the 40 slow-pod alerts of checkout, and only of checkout.

A silence does the same by hand: a set of matchers, a start, an end, an author and a comment. It is for planned work and for an alert someone is already handling. It is set on the Alertmanager's web page, with `amtool silence add`, or through the API, and it ends by itself.

Muted alerts are still active in the Alertmanager. They only leave the notifications, and the web page and `amtool` show them as suppressed.

               body = self.rfile.read(int(self.headers.get("Content-Length", 0))).decode()

                   msg = json.loads(body)

               pass

<Trap practice>
`amtool alert add` sends an alert without an end time, so the Alertmanager ends it after `resolve_timeout`, 5 minutes by default. That is why the log of action 8 shows `resolved` lines, and none for the silenced `CheckoutErrors`: muted alerts are left out of notifications, the resolved ones too.
</Trap>

<Remember>
Routes pick the receiver, `group_by` and the three timers decide what goes into one message and when, inhibition mutes what another alert explains, and a silence mutes by hand until it ends.
</Remember>

<Question id="q-m15-s03" answer="d">
A route has `group_by: [alertname]`. Alerts `DiskFull` for host `a` and for host `b` arrive one second apart, then `DiskFull` for host `c` arrives two minutes after the first notification was sent. With the default timers, how many notifications are sent in the first ten minutes?

- Three, one per host, because each alert has its own instance label

  The group is made by alertname only, so the three hosts share one group.

- One, because a group is sent only once until repeat_interval

  A group is sent again when its content changes, after group_interval.

- One with all three hosts, because group_wait waits for the third

  group_wait is 30 seconds by default; host c arrives long after it.

- Two: hosts a and b after group_wait, then an update with c after group_interval

  The first message waits group_wait for a and b; the change to the group is sent when group_interval, 5 minutes, has passed.
</Question>
