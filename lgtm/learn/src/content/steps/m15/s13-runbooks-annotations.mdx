<Problem>
The phone shows `CheckoutErrorBudgetBurn severity=page window=1h`, nothing else. The person on call has never touched checkout. How bad is it, which numbers, where to look first? Every minute spent finding that out is budget burnt.
</Problem>

<Idea>
An alert carries text for the person it wakes: a summary with the live numbers, a description with what it means and the first checks, and a link to its runbook. Write them as annotations with templates, so each notification says what is happening now, and keep a runbook entry for every paging alert.
</Idea>

## What a page must answer

A page should answer four questions before the laptop opens: what is broken for users, how bad it is now, where to look first, and where the full instructions are. Grafana's documentation asks for annotations a first responder can act on without knowing how the alert was built. It names three common ones: `summary` for what was detected, `description` for what happened and how to respond, and `runbook_url` for the page that guides the response.

The SRE workbook adds that each new alert should come with its playbook entry, and that playbooks age as fast as production changes. Keep the entry short and structured, so it can be kept current.

## Templates put the numbers in

Annotations are templates, filled in at every evaluation. In a Prometheus or Mimir rule, `{{ $value }}` is the value of the alert and `{{ $labels.x }}` a label of the series the expression returned. `humanizePercentage` prints the ratio `0.0153` as `1.53%`. For your SLO alert, `$value` is the left side of the `and`: the long window's error ratio.

A label that the rule adds itself, under `labels`, is not in `$labels`. A first version of this file used `{{ $labels.window }}`, and on the lab the page read "over : the error budget burns fast". The recorded series have no labels at all, so each alert carries its own text instead: "over the last hour" and "over the last 6 hours".

## Updating a loaded group

`mimirtool rules load` replaces a group of the same name in the same namespace. Its output says which rule changed. The recorded series continue, because the recording rules did not change; alerts already firing are re-evaluated with the new text.

<Question id="q-m15-s13" answer="c">
An alert's annotation is `summary: "Error ratio is {{ $value }}"`. The expression is `job:errors:ratio_rate5m > 0.05`. The ratio is 0.12. What does the summary say?

- "Error ratio is 0.05", the threshold

  $value is the value of the alert's series, not the number it was compared with.

- `"Error ratio is {{ $value }}"`, because annotations are not templated

  Annotation values are templates; Prometheus fills them in at each evaluation.

- "Error ratio is 0.12", the value of the series after the comparison

  A comparison keeps the left side's value, so $value is the error ratio itself.

- "Error ratio is 12%", because Prometheus formats ratios

  Plain $value prints the number as it is; humanizePercentage would print 12%.
</Question>
