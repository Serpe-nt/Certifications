<Problem>
A team lead wants a small table: one row per beacon slot, its current value, sorted by name. The query returns nine time series, and the table panel shows a drop-down to pick one series at a time. The data is all there; it just has the wrong shape.
</Problem>

Some answers need no new query, only a new shape. Grafana can reshape data after it arrives.

<Idea>
A transformation reshapes the result of a panel's queries before the visualization draws it: it can reduce, filter, join, rename and sort. Transformations run one after another, each on the result of the one before. When the change is maths across queries, a server-side expression or the query language itself is often the better place.
</Idea>

## A chain, in order

Transformations sit on their own tab next to the queries in the panel editor. You add as many as you need, and Grafana applies them in the order they are listed, so the order changes the result. A **Reduce** that turns every series into one number leaves later steps only that number to work with.

A few cover most needs:

- **Reduce** turns each series into one value, such as the last one, the mean or the maximum. In the mode **Series to rows** it makes one row per series, which is what a summary table needs.
- **Labels to fields** turns the labels of time series into table columns.
- **Filter data by values** keeps or drops rows by a condition.
- **Organize fields by name** renames, reorders and hides columns.
- **Sort by** orders the rows by one or more fields.

All text fields in transformations accept dashboard variables, so a filter can follow the variable the viewer picked.

<Flow caption="A table built by transformations">
  <Stage title="Query" kicker="Nine series">One time series per slot, many points each.</Stage>
  <Stage title="Reduce" kicker="Series to rows">One row per series, with its last value.</Stage>
  <Stage title="Organize" kicker="Rename">The columns get names a reader understands.</Stage>
  <Stage title="Sort by" kicker="Order">The rows in the order you want to read them.</Stage>
</Flow>

## Transformations or expressions

Transformations work on the result after the data source has returned it, for one panel. Server-side expressions run on the Grafana server and become part of the query. An expression takes other queries as input by their RefID, the letter that names each query. A Math expression such as `$A / $B` divides one result by another, even when A and B come from different data sources. There are also Reduce, Resample and SQL expressions. Because they run on the server, they work without a browser session, so Grafana Alerting can use them, and alerting is where they are used most.

Grafana's own advice is to do the processing in the data source when you can. Copying data from storage to Grafana to compute it there is slow. A ratio of two Prometheus metrics belongs in PromQL; an expression earns its place when the inputs come from two different data sources.

<Compare caption="Where to change the data">
  <Col title="In the query" hot>PromQL, LogQL or TraceQL, in the data source. The default, and the fastest.</Col>
  <Col title="Expression">On the Grafana server, by RefID. For maths across data sources, and for alerts.</Col>
  <Col title="Transformation">After the data arrives, for this panel. For shape: rows, columns, names and order.</Col>
</Compare>

## Keep the chain stable

Some transformations, such as merges and joins, name their output after the RefIDs of their inputs. When a query is added, removed or renamed, that name changes, and a later step that filters on it stops matching. Grafana 13.3 can keep these generated RefIDs fixed, so chains survive changes to the queries. The **Table view** switch above the preview shows the data after every transformation, which is the quickest way to see what each step did.

<InLab>
The beacon publishes all its metric tokens as one metric, `lab_beacon_value`, with the slot in the label `slot`. Asking for the slots of one module returns nine series: the right input for a summary table.
</InLab>

<Trap>
A transformation does not reduce the work of the data source: the data source still returns the full result first. If a panel is slow because the query returns too much, fix the query, not the transformations.
</Trap>

<Remember>
Shape in transformations, maths in the query, and an expression when the inputs come from different data sources or an alert needs it.
</Remember>

<Question id="q-m05-s07" answer="b">
A panel has a Reduce transformation (Series to rows, Last) followed by a Filter data by values that keeps rows above 100. You swap the order of the two. What happens?

- Nothing changes, because Grafana sorts transformations by type

  Grafana applies transformations in the order they are listed. It does not reorder them.

- The filter now works on the raw points before they are reduced

  Each transformation works on the output of the one before, so the filter now sees every point, not one value per series.

- The panel fails, because Filter must always come last

  Any transformation can come first. Only the result changes with the order.

- The data source runs the filter, so the query gets faster

  Transformations work on data the data source has already returned. The query is unchanged.
</Question>
